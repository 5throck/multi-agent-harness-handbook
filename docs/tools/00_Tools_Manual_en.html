This handbook was originally written around the Gemini command-line interface (CLI) before that date, but has since been fully updated to the Antigravity command-line interface (CLI) as of the current date. 1. Claude Desktop App vs Claude Code (CLI)

This handbook treats Claude Desktop App as its default hands-on tool. Because the flow of creating and invoking subagents through the GUI is the same, you can follow the content below just as easily using Claude Code (CLI). Both tools run on the same Claude engine, but since their execution environments differ, some of the mechanisms that make up a multi-agent harness only work in the CLI. The biggest differences are in automation hooks and Agent Teams execution modes.

Claude Desktop App (or Claude Code) — .claude/agents/*.md Subagents

Claude Desktop App defines custom subagents via .claude/agents/*.md files and invokes them with the Agent/Task tool, exactly as Claude Code does. However, the PostToolUse/TeammateIdle/TaskCompleted hooks defined in .claude/settings.json do not fire in Claude Desktop App. They only auto-fire on events like file saves or task completion within a CLI session. Teams using Claude Desktop App must manually run whatever the hook would have done (e.g., running an audit script) after the session ends.

Let's look at a concrete accident this difference can cause. Suppose a team has set up a PostToolUse hook in the CLI so that "every time a file is saved, bun scripts/audit.ts runs automatically to catch secret leaks or rule violations." When the same team member makes the identical edit in Claude Desktop App, the hook never fires at all — yet on screen it looks exactly like the CLI: "the file was saved," with no visible sign the hook didn't run. If that state carries through to a commit, an issue the hook was supposed to catch quietly slips through. The real danger isn't "we forgot to run the audit" — it's "we thought the audit ran, but it didn't."

teammateMode — Claude Desktop App Supports Only in-process, Claude Code Also Supports tmux

Agent Teams, an experimental feature, launches multiple Claude instances in parallel. Claude Desktop App can only use the in-process mode, which parallelizes within the same process, and some keyboard navigation (e.g., Shift+Down) is restricted. The tmux mode, which uses a terminal split-pane, is additionally supported only in Claude Code (CLI).

FeatureClaude Desktop AppClaude Code (CLI)
Invoking subagents via Agent/Task tool Supported Supported
Custom subagents via .claude/agents/*.md Supported Supported
PostToolUse / TeammateIdle / TaskCompleted hooks Unsupported (manual execution required) Supported (fires automatically)
Agent Teams — teammateMode: in-process Supported (some shortcuts limited) Supported
Agent Teams — teammateMode: tmux Unsupported Supported
To use Agent Teams in the Desktop App, you must explicitly set teammateMode to in-process. Your team's rules should also reflect the fact that hooks don't fire. Be careful not to mistake a silently-skipped automated audit for a "pass."

2. Antigravity (Desktop) vs Antigravity CLI (agy)

On the Google side too, this handbook treats Antigravity (Desktop) as its default hands-on tool. It's a standalone desktop app designed from the ground up to supervise multiple agents across multiple workspaces simultaneously. Antigravity CLI (agy) is the CLI face of the same platform, structured so that a single terminal session receives a goal and breaks it into subtasks on its own. Both tools also share the same configuration folder (antigravity-cli/ under ~/.gemini).

Workspaces · Inbox · Playground — Antigravity (Desktop) Agent Manager

Antigravity's Agent Manager is a top-level interface that supervises multiple workspaces from a single screen. The principle is to assign one agent per workspace, and messages needing approval or feedback collect in the Inbox. The Playground is a space to try things out lightly before committing to a formal workspace. When launching an agent, you choose between Local Mode, which works directly in the active folder, and New Worktree Mode, which works in an isolated git worktree.

While you can assign multiple agents to the same workspace (same folder) at once, there are real reports of different agents confusing and mixing up the codebase's context ("cognitive overlap"). It's safer to separate parallel work by workspace or by git worktree.

Antigravity CLI (agy) Slash Commands — /goal, /agent, /agents

Unlike Claude Code/App, which predefines subagents in files such as .claude/agents/*.md, the Antigravity command-line interface (CLI) works by having the orchestrator agent decide on its own how to split a goal into tasks once given one, creating subagents on the fly and running them in parallel. Each subagent has its own independent context window, preventing the main session's context from getting diluted.

To use an analogy: Claude Code/App works with "a pre-hired roster of full-time team members," while the Antigravity command-line interface (CLI) is closer to "hiring a freelancer on the spot for whatever job comes up." The former makes it easy to control permissions because you always know who your team members are; the latter offers the flexibility of sourcing new talent each time, but you need a way to check after the fact "who exactly got brought in this time." That's what /agents below is for.

One thing worth noting here: the ability to dynamically create subagents is not unique to Antigravity CLI. Claude Code/App's Agent(Task) tool also spawns subagents on the fly from natural-language requests alone, judging what task is needed at the time (Chapter 1 §3b), and Antigravity (Desktop)'s Agent Manager likewise lets you give a goal in natural language without a predefined file (§1). The /goal·/agent·/agents introduced in this section are simply syntax for handling that same dynamic orchestration capability via slash commands on the CLI screen. Claude Code/App does the same thing through chat sentences instead of this syntax, and Antigravity Desktop does the same thing through GUI buttons (Inbox approvals, Playground, etc.) instead of this syntax.

Below are four CLI-specific slash commands you'll frequently use when actually working with agy. Read the table below not as "a list of features unique to Antigravity CLI" but as "the names given to the same capability on the command-line interface (CLI)."

CommandAction
agyStarts a TUI session.
/goal <goal>Runs a goal to completion without intermediate confirmation. The orchestrator splits subtasks on its own.
/agent <task>Delegates a long-running task to a background agent and lets you move on to another prompt without waiting for completion.
/agentsShows a list of subagents created so far, with their running/completed/blocked status.

Here is the actual flow of starting a session and running a goal.

agy

Inside the session (interactive):

/goal Add a summary to every text file in this folder

If, as in CI/automation, you want a single run with no conversation (non-interactive):

agy -p "Draft a commit message"

On the CLI side, too, it's safer to keep sessions separate. If one agy session is refactoring the API layer while another writes tests, they won't conflict as long as they don't touch the same files.

3. Codex Desktop App vs Codex CLI

The OpenAI camp is Codex. Both Codex Desktop App and Codex CLI read the repository root's CODEX.md for behavioral instructions, but there's one structural difference from the four tools above — Codex has no native subagent tool. There's nothing in Codex equivalent to Claude's Agent/Task tool or Antigravity's dynamic subagent spawning, so the harness pattern of orchestrating multiple specialist agents has to be implemented a different way.

No subagents — the PM runs roles sequentially instead

In Codex, the PM (orchestrator) role works by loading each specialist agent's definition file (agents/<name>.md) as role context, then carrying out that role's work in order, within the same session. Rather than spawning a separate process or subagent, the PM itself steps through the work by "putting on" each role in turn — thinking like the design agent for one stage, then like the implementation agent for the next. There's no parallel execution and no separate context window per role; every step happens inside one linear session.

If Claude Code/App is "calling a different employee for each task," and Antigravity CLI is "hiring a freelancer on the spot for whatever comes up," Codex is "one person working through a manual, switching hats as needed." There's no role-switching overhead, but genuine parallel execution or direct role-to-role communication (SendMessage and the like) is off the table from the start.

No hooks — self-enforced via the prompt

Codex does not run the workspace's hook suite. It has nothing corresponding to Claude Code's PostToolUse/TeammateIdle/TaskCompleted auto-firing events, so governance — running audit scripts, enforcing gate rules — instead relies on the PM recognizing and carrying out the instructions in CODEX.md itself, every session (prompt self-enforcement). This is a different failure mode from how Antigravity Desktop handles the gap with its GUI: Antigravity simply has no equivalent feature, while Codex needs the same governance but implements it via prompt instructions instead of hooks.

FeatureCodex Desktop AppCodex CLI
Native subagent tool Unsupported — PM loads agents/<name>.md as role context and runs it sequentially within the session Same (no structural difference from the Desktop App)
Automation hooks (PostToolUse, etc.) Unsupported — governance is self-enforced via CODEX.md prompt instructions Unsupported (same)
Parallel execution Unsupported (single linear session) Cross-session parallelism is possible by opening multiple terminals — no within-session parallelism
Settings/skills location .codex/skills/, .codex/prompts/, .codex/config.toml Same
When following this handbook's multi-agent exercises with Codex, read "invoke a subagent" as "the PM loads that role's definition file and performs the role." You can still produce the same deliverables, but because the execution model is fundamentally different, exercises that rely on communicating with another subagent mid-run (Agent Teams, SendMessage, etc.) cannot be reproduced as-is in Codex.

There's one criterion that separates the two rows above. Is the subagent a "one-shot call that only returns a result once delegated" or "a teammate-like entity that stays alive"? Claude Code/App's single Agent(Task) call and Antigravity command-line interface (CLI)'s dynamic subagents are closer to the former. Once spawned, they handle everything alone through to the end and return only a summary, so there's no way to give new instructions midway or have them converse with another subagent. Claude Code/App's Agent Teams, by contrast, are the latter — each teammate can send messages directly to another via SendMessage (already covered in the P-1 exercise in Chapter 2 §1). Antigravity (Desktop) doesn't support agent-to-agent communication at all, but instead lets a human converse individually with each in-progress agent through the Inbox — this is what sets it apart from the other three tools. Codex sits outside this spectrum entirely — there's no subagent concept to begin with, so the "one-shot vs. teammate" question doesn't even apply.

5. Which Tool to Choose for This Handbook

This handbook guides you using Claude Desktop App and Antigravity (Desktop) as its default hands-on tools, because starting with a GUI has a lower barrier to entry. Chapter 2 likewise shows these two Desktop tools first, then immediately follows with the Claude Code (CLI)·Antigravity CLI (agy) procedures side by side, with Codex (Desktop/CLI) differences noted per §3 where they diverge. You can pick just one tool and follow along, or compare and practice with several together. The following criteria make the choice easier.

  1. If you just want to get a feel for it via GUI first. Start with Claude Desktop App or Antigravity (Desktop). This is the handbook's default path.
  2. If you want to supervise several different projects at once. Antigravity (Desktop)'s Agent Manager (isolation per workspace) is designed exactly for this scenario.
  3. If you need hook-based automation (audit/QA gates). Move to Claude Code (CLI). Claude Desktop App and the Antigravity/Codex families have no corresponding automatic hooks.
  4. If you want an orchestrator to split things up on its own without defining subagents one by one. Antigravity CLI (agy) dynamically creates subagents just from a goal. In exchange, fine-grained control is relatively limited.
  5. If you already have a Codex subscription/environment and want to stick with it. You can follow along in Codex (Desktop/CLI). Exercises that rely on subagents, parallel execution, or hooks (Agent Teams, SendMessage, etc.) should be re-read using the sequential-role-switching approach described in §3.

The decision flow above shows the choice among the four Claude/Antigravity tools. Codex (Desktop/CLI) has no subagent or hook axis to place on this diagram — whether you already have a Codex environment is effectively the only deciding factor, and if so, see §3 for how to re-read the exercises using the sequential-role-switching approach.

💡 Key takeaway: All six tools share the same basic harness-engineering structure: "give roles a narrow scope and let an orchestrator coordinate them." What changes is which execution environment (CLI/GUI, hooks or not, whether subagents are predefined, created on the fly, or don't exist at all) that structure is laid on top of.

6. AGENTS.md — Tying the Six Tools Together

The hooks, parallel execution, and subagent-definition methods compared so far differ from tool to tool, but the repository-root configuration can still be unified into one. AGENTS.md is an open standard created in August 2025 by OpenAI together with Google, Cursor, and Factory, and donated to the Linux Foundation's Agentic AI Foundation in December 2025. It's supported by more than 30 tools, including Codex, Cursor, GitHub Copilot, and Google Jules, as well as Claude Code (via import) and the Antigravity family. Notably, Codex is one of the standard's original co-creators — it reads AGENTS.md natively, and layers a tool-specific CODEX.md on top of it.

Placing a single AGENTS.md at the repository root lets all six tools read it at session start and share common rules such as build/test commands, code style, and off-limits areas. Tool-specific behavior (hooks, teammateMode, where subagents are defined, etc.) is still recorded separately, as compared in the table above, in tool-specific files such as CLAUDE.md, GEMINI.md, and CODEX.md. AGENTS.md handles the common denominator, and tool-specific files handle the differences.

FileRoleTools that read it
AGENTS.md Tool-neutral common rules (build/test commands, code style, off-limits areas) Claude Code (import) · Antigravity family · Codex (native) · Cursor · Copilot, and 30+ others
CLAUDE.md Claude Code/App-specific detailed behavior (hooks, slash commands, agent-dispatch rules) Claude Code, Claude Desktop App
GEMINI.md Antigravity CLI/Desktop-specific detailed behavior Antigravity CLI, Antigravity (Desktop)
CODEX.md Codex CLI/Desktop App-specific detailed behavior — sequential PM role-switching instead of native subagents, prompt self-enforcement instead of hooks Codex CLI, Codex Desktop App

💡 Key takeaway: The ai-workspace-standards repository covered in Chapter 5 §1 implements exactly this structure. The root AGENTS.md serves as the single source of truth (SSOT) for the agent roster, and the .agents/ folder sits alongside .claude/·.gemini/·.codex/, holding tool-agnostic commands and skills.
