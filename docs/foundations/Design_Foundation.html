디자인 기반과 표준 UI 패턴

AI가 만든 화면을 ‘그럴듯한 시안’에서 재사용 가능한 제품 경험으로 바꾸는 방법을 배운다.

이 장에서 다루는 것
  • 디자인 시스템이 필요한 이유
  • 원칙·토큰·결정 기록
  • 표준 컴포넌트와 화면 상태
  • AI 산출물 검토와 개선 실습

디자인은 화면 꾸미기가 아니라 계약이다

같은 제품을 여러 사람이 만들 때 디자인 규칙은 팀이 공유하는 계약이다. 색, 간격, 글자 크기, 정보의 우선순위를 매 화면마다 다시 정하면 기능은 같아도 사용 경험은 흔들린다. 디자인 시스템은 건축 도면처럼 재료와 치수를 먼저 정해 두어, 사람과 AI가 같은 결과를 반복하게 한다.

좋은 디자인 판단은 ‘예쁜가’보다 ‘사용자가 다음 행동을 바로 알 수 있는가’에서 시작한다. 따라서 화면을 만들기 전에는 사용자의 목표, 성공 상태, 실패 상태, 그리고 담당자가 확인할 증거를 한 문장씩 적는다.

검토 항목의도
과업 사용자가 이 화면에서 끝내야 하는 행동
위계 제목·설명·행동·보조 정보의 읽는 순서
제약 접근성, 작은 화면, 긴 번역문, 오류 상황
표준: 화면 요청 → 사용자 과업 → 표준 패턴 선택 → 구현 → 실제 상태 검토

원칙과 토큰으로 재작업을 줄인다

원칙은 판단의 방향이고 토큰은 판단을 구현에 연결하는 이름이다. 예를 들어 ‘경고는 행동을 막지 말고 해결 방법을 함께 보여 준다’는 원칙이다. `--bg-warn`, `--border-warn`처럼 의미 있는 토큰은 그 원칙을 코드와 문서에서 일관되게 재사용하게 한다.

토큰에는 특정 색상값이나 임의의 픽셀값이 아니라 역할을 붙인다. 그래야 다크 모드, 브랜드 변경, 접근성 보정이 필요할 때 화면마다 고치는 대신 토큰 정의를 바꿀 수 있다.

검토 항목의도
일관성 같은 의미에는 같은 모양을 쓴다.
명료성 한 화면에 가장 중요한 행동은 하나로 제한한다.
접근성 색만으로 상태를 구분하지 않고 문장과 아이콘을 함께 쓴다.
되돌림 위험한 행동에는 취소·미리 보기·확인 단계를 둔다.
표준: 원칙 → 의미 토큰 → 컴포넌트 규칙 → 화면 검토 기준

실습

토큰에는 특정 색상값이나 임의의 픽셀값이 아니라 역할을 붙인다. 그래야 다크 모드, 브랜드 변경, 접근성 보정이 필요할 때 화면마다 고치는 대신 토큰 정의를 바꿀 수 있다.

# design-contract.yaml
screen: report-review
primary_task: approve-or-return-a-report
states: [default, loading, empty, error, forbidden]
components:
  - status-panel
  - review-summary
  - primary-action
acceptance:
  - one-primary-action
  - keyboard-reachable
  - semantic-tokens-only

표준 컴포넌트와 표준 화면을 함께 정의한다

버튼, 입력칸, 카드, 표, 알림은 부품이다. 목록, 상세, 생성, 검토, 오류, 빈 상태는 부품을 조합한 화면 패턴이다. 부품만 표준화하면 실제 사용 중 자주 누락되는 로딩·빈 상태·권한 없음·저장 실패 화면이 제각각 남는다.

각 컴포넌트에는 목적, 허용되는 변형, 상태, 접근성 이름을 기록한다. 각 화면에는 진입 조건, 사용자의 다음 행동, 성공·실패·대기 상태, 필요한 검증 증거를 기록한다. 이 두 계약을 프롬프트와 리뷰 기준에 넣으면 AI의 출력도 검토 가능한 산출물이 된다.

검토 항목의도
주요 버튼 한 화면의 핵심 행동만 강조한다.
폼 필수 여부와 오류 이유를 입력칸 가까이에 둔다.
상태 패널 로딩·빈 결과·오류·권한 없음에 다음 행동을 제공한다.
검토 화면 변경 내용, 영향 범위, 승인 또는 되돌림 행동을 분리한다.
표준: 토큰 → 버튼·폼·상태 패널 → 목록·상세·검토 화면 → 사용자 행동

AI 산출물은 결과가 아니라 검토 가능한 초안이다

AI에게 ‘깔끔한 화면’을 요청하면 프로젝트마다 다른 해석이 나온다. 대신 목표, 표준 컴포넌트, 금지 사항, 상태 목록, 접근성 기준, 완료 증거를 함께 준다. 생성 뒤에는 코드의 모양이 아니라 실제 화면에서 긴 텍스트, 키보드 이동, 오류 상태, 다크 모드를 확인한다.

리뷰는 의견 모으기가 아니라 약속을 확인하는 절차다. 발견한 문제는 ‘어느 화면의 어떤 상태에서 어떤 사용자가 막히는가’로 기록한다. 수정 후에는 전후 화면과 검사 결과를 연결해 다음 작업자가 같은 판단을 재사용하게 한다.

검토 항목의도
1. 과업과 한 가지 주요 행동이 보이는가?1. 과업과 한 가지 주요 행동이 보이는가?
2. 기본·로딩·빈·오류·권한 없음 상태가 있는가?2. 기본·로딩·빈·오류·권한 없음 상태가 있는가?
3. 색 이외의 단서와 키보드 조작이 가능한가?3. 색 이외의 단서와 키보드 조작이 가능한가?
4. 토큰·표준 컴포넌트·화면 계약을 지켰는가?4. 토큰·표준 컴포넌트·화면 계약을 지켰는가?
표준: 요청 계약 → AI 초안 → 상태별 미리 보기 → 접근성·일관성 검토 → 증거 기록
자기 점검
  1. 과업: 사용자가 이 화면에서 끝내야 하는 행동
  2. 주요 버튼: 한 화면의 핵심 행동만 강조한다.
  3. 4. 토큰·표준 컴포넌트·화면 계약을 지켰는가?
