Design philosophy: a screen is a contract for a user task

A design rule is a shared contract for people and AI. If color, spacing, type, and information priority are chosen again for every screen, the feature may work but the experience drifts. A design system is like an architectural drawing: it fixes the materials and dimensions before construction so the result can be repeated.

Start with a user task, the success state, the failure state, and the evidence an owner will inspect. The first question is not whether a screen looks attractive. It is whether a user can identify the next action without guessing.

Review itemIntent
Task the action a user must finish
Hierarchy the reading order of title, explanation, action, and support
Constraints accessibility, narrow screens, long translations, and failure
Standard: Screen request → user task → standard pattern → implementation → state review

Design principles: consistency, clarity, and recovery

Principles explain how to decide; tokens give the decision a reusable implementation name. ‘Show a remedy with a warning’ is a principle. Semantic names such as --bg-warn and --border-warn let the same intent survive in code, documentation, and dark mode.

Name a role rather than a raw color or an arbitrary pixel. A later accessibility adjustment or brand change then updates a definition instead of forcing a screen-by-screen repair.

Review itemIntent
Consistency one meaning has one visual treatment.
Clarity emphasize only one primary action per screen.
Accessibility never use color as the only signal.
Recovery provide preview, cancel, or confirmation for risky actions.
Standard: Principle → semantic token → component rule → review criterion

Practice

Name a role rather than a raw color or an arbitrary pixel. A later accessibility adjustment or brand change then updates a definition instead of forcing a screen-by-screen repair.

# design-contract.yaml
screen: report-review
primary_task: approve-or-return-a-report
states: [default, loading, empty, error, forbidden]
components:
  - status-panel
  - review-summary
  - primary-action
acceptance:
  - one-primary-action
  - keyboard-reachable
  - semantic-tokens-only

Design guides: spacing, hierarchy, language, and responsive layout

Design guides are a working language that lets many people and screens complete the same task consistently. Spacing exposes relationships; heading, body, and supporting text establish reading order. Wording states the action first, and narrow screens reflow information by priority.

Copy established rules for a new screen and record only necessary differences. Do not add arbitrary spacing, isolated icon meanings, fixed widths, or vague button labels without a review reason.

ElementRule
SpacingUse smaller space for closer relationships.
HierarchyGive heading, body, and support text role-specific type.
LanguageState action and outcome before decorative wording.
ResponsivePrefer flexible width and priority-based reflow.
Guide: User task → hierarchy → spacing and wording rules → responsive-screen review

Color System and Accessibility

A color system is a contract for meaning, not a palette. Raw palette tokens provide color steps only; screens use semantic tokens such as text, surface, border, action, success, warning, and error. This separation prevents a brand or dark-mode change from redefining the meaning of failure, warning, and completion on every screen.

Accessibility is a validation condition for the color system. Do not communicate success, error, or selection with color alone: pair it with wording, icons, borders, or patterns. Review text, icons, focus rings, and input-error boundaries for contrast and keyboard focus in both light and dark modes.

LayerPurpose
Raw paletteDefines color steps; screens do not use it directly.
Semantic tokenExpresses the role of text, surface, border, action, and state.
Component tokenDefines state tokens for buttons, fields, and notices.
Accessibility reviewChecks non-color cues, contrast, and focus together.
Standard: Raw palette → semantic tokens → component states → light/dark accessibility review

State-color review practice

Ask AI to use semantic tokens rather than raw color values. Preview default, hover, focus, disabled, and error states on one screen, then verify that state and next action remain clear when color is removed.

{
  "color": {
    "brand": { "$value": "#0969da", "$type": "color" },
    "action-primary": { "$value": "{color.brand}", "$type": "color" },
    "status-error": { "$value": "#cf222e", "$type": "color" },
    "focus-ring": { "$value": "{color.action-primary}", "$type": "color" }
  }
}

Typography and font system

Fonts are interface infrastructure for reading speed and information hierarchy. Separate body, heading, supporting, and code roles, and manage family, weight, size, line height, and letter spacing as tokens. Multilingual products define glyph coverage and fallback order.

A document must remain readable when a web font loads slowly or fails. Review system fallbacks, monospace code, wrapping of long translations, and minimum readable sizes in tables and buttons.

ElementRule
BodyKeep a readable size and generous line height.
HeadingExpose structure through size and weight levels.
CodeUse monospace type and wrapping rules.
FallbackPlan for glyph coverage and load failure.
Guide: Font role → type token → multilingual fallback → reading review

Standard components and standard screens

Buttons, fields, cards, tables, and notices are parts. List, detail, create, review, error, and empty states are patterns made from those parts. Component-only standards leave loading, empty, forbidden, and save-failure screens inconsistent.

For each component, record its purpose, allowed variants, states, and accessible name. For each screen, record its entry condition, next action, success/failure/waiting states, and required evidence.

Review itemIntent
Primary action emphasize one decisive action.
Forms keep required status and error reason close to the field.
Status panels offer a next action for loading, empty, error, and forbidden.
Review separate change summary, impact, approval, and reversal.
Standard: Tokens → buttons, forms, status panels → list, detail, review → user action

Accessibility and AI-output review

A request for a ‘clean screen’ produces a different interpretation every time. Provide the task, allowed components, forbidden patterns, state list, accessibility criteria, and acceptance evidence instead. Then review the rendered screen with long text, keyboard movement, failures, and dark mode.

A review records where a user is blocked, in which state, and why. Link the repair to before-and-after evidence so the next contributor can reuse the decision.

Review itemIntent
1. Is the task and one primary action visible?To confirm the purpose of the screen lands at first glance.
2. Are default, loading, empty, error, and forbidden states covered?To require every state so AI drafts leave no gaps.
3. Are non-color cues and keyboard operation available?To guarantee accessibility without relying on color or a mouse.
4. Are tokens, components, and screen contracts respected?To make consistency a contract check, not a matter of taste.
Standard: Request contract → AI draft → state previews → accessibility and consistency review → evidence
Self-check
  1. What does a screen contract contain, and why define it before drafting?
  2. Why must default, loading, empty, error, and forbidden states all be designed?
  3. How do you verify non-color cues and keyboard operation?
  4. What are the benefits of using tokens and standard components?
