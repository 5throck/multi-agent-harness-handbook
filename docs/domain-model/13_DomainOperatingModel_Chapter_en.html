Chapter 13

Domain Operating Model — How Templates Become Executable SOPs

Chapters 11 and 12 covered how to build and promote a variant template. As of September 2026, official variant templates are held to a new standard. A template is no longer just "a bundle of agents, skills, and configuration": it declares, in machine-readable form, what happens in which order (stages), who is accountable (RACI), and which verdicts must pass before work moves on (decision gates). The official name of this structure is the Domain Operating Model, and its design rationale lives in ADR-0083 and ADR-0084.

Source: ai-workspace-standards (GitHub)

What this chapter covers
  • What the Domain Operating Model is, and why it is never abbreviated
  • The four core groups (Process · Governance · Execution · Graph) and the files each one owns
  • The difference between the PM execution axis phase (0–6) and the domain workflow axis stage
  • How the RACI matrix and decision gates connect to procedures and the skill graph
  • The difference between "governed" and "core" templates, and the validation commands

A template as a domain operating system

The workspace owner once made this proposal: "Let each variant template behave like its domain's operating system — gather process, skills, agent team, accountability, artifacts, and decision rules in one place, and add a graph that ties them together." A verification pass on 2026-09-19 confirmed something interesting: thanks to the Procedure Schema (ADR-0063) and the Skill Graph (ADR-0060), much of the proposed structure already shipped. The genuine gaps were narrower — a domain stage axis, RACI's Consulted/Informed, generalized artifact and decision models, and the graph vocabulary tying them together. ADR-0083 executed the fill-in as a five-phase plan (P1–P5).

A template is no longer a bundle of files — it is an operating system that declares its domain's workflow, accountability, and verdicts. — the new definition of a template under ADR-0083

The name is always spelled out

The framework's official name is Domain Operating Model, and the workspace forbids abbreviating it. Shortened to "DOM" it collides with the browser's Document Object Model — live terminology for variants like co-deck, co-design, and co-game that handle HTML and CSS. "AOM" is also banned: "Agent" already denotes the PM Gateway's specialist agents, and a framework should not be named after one of its own sub-components. No acronym is permitted in any document, schema, script, or commit message. It is a fine example of the rule from Chapter 2 — one term, one meaning.

The four core groups

The Core of the Domain Operating Model has four groups. Each group maps to specific files inside a template.

GroupWhat it coversFilesStatus
ProcessStage → Activity → Skill. How work flows in orderprocess/stages.yaml, procedures/*/schema.yamlImplemented (P2)
GovernanceRACI. Who is accountable and who executes, per stage and activitygovernance/raci.yamlImplemented (P4)
ExecutionArtifact · Decision. What gets produced and which verdicts must passprocedures/_output-types.yaml, decisions/gates.yamlImplemented (P5)
GraphDomain Execution Graph. The relationship layer tying the other three togetherDEG profile of docs/skill-graph.jsonImplemented (P3)
Agent is not one of the four groups. An agent is an actor reference inside RACI: each role slot holds an agent key, and the structure does not force a human-versus-AI distinction (that distinction is an opt-in extension handled by the actor model, covered below).

Think of it as an assembly line. Process is the line layout that fixes the order of stations; Governance is the nameplate posted at each station; Execution is the part each station produces and the quality checkpoint it must clear before moving to the next station. And Graph is the control tower overlooking the whole line, able to answer at a glance "where is this part now, who made it, and which checks has it passed." The diagram below shows how these four groups come together into a single graph.

Figure 13-1. Data from the Process, Governance, and Execution groups comes together in the Graph as one connected body of executable knowledge.

The layering is explicit too. The AI Workspace owns schemas and contracts (layers L0·L1), the Domain Operating Model defines each domain's operating principles on top of them, a Template (templates/co-*/) packages exactly one domain, and a Project (L3) instantiates it for real work. This is how the L0→L1→L2→L3 hierarchy from Chapter 5 and the Domain Operating Model nest into each other.

Process — the stage axis

The first gap filled was the stage axis. The procedure schema always had a phase field, but that is the PM's work-execution axis (0–6, from design approval through execution and QA) — not the domain's workflow. A consulting project flowing "research → analysis → report", or a deck flowing "research → storyline → build → export", had nowhere to declare its domain-specific progression. ADR-0083 declares this axis in process/stages.yaml.

# templates/co-deck/process/stages.yaml (excerpt)
schema_version: '1.0'
variant: co-deck
stages:
  - id: S1
    title: Deck Source Research
    order: 1
    owner_agent: version
  - id: S2
    title: Version Export Control
    order: 2
    owner_agent: version
  - id: S3
    title: Deck Publish and Versioning
    order: 3
    owner_agent: pdf-export

Figure 13-2. phase is the PM execution order common to every variant; stage is the domain workflow that differs per variant — the two axes are independent.

Machine first, human refinement

The stage axis was produced by bootstrap-stages.ts, which clusters procedures by analyzing their artifact handoff flow — where one procedure's output becomes the next procedure's input — rather than naively grouping by phase. The machine's first pass deliberately leaves purpose and entry/exit criteria as PENDING_REVIEW: structure is automated, meaning is human. That is the workspace's consistent division of labor.

There is a minimal qualification too. Invariant DEG-P-01 requires the stage axis to be genuinely distinct from phase. When the procedure count, phase count, and stage count are all equal (a 1:1 mapping), the "stage axis" is just phase renamed. The nine variants that pass (co-abap, co-consult, co-deck, co-design, co-export, co-game, co-hr, co-price, co-security) earn the governed grade; the four that fail (co-develop, co-news, co-safety, co-work) stay at core until a human authors their stages. Maturity is expressed as a grade, not enforced as a gate.

Governance — the RACI matrix

The second group is accountability. governance/raci.yaml declares, for each activity (procedure) in each stage, who is Accountable and who is Responsible. RACI is a classic project-management tool — Responsible, Accountable, Consulted, Informed — for answering "who does what". What is new here is that the matrix is not a document people read; it is generated and validated data.

# templates/co-deck/governance/raci.yaml (excerpt)
schema_version: '1.0'
variant: co-deck
generated_from: procedures/
rows:
  - stage: S2
    activity: procedure.co-deck.deck-build-and-export
    accountable: version
    responsible:
      - html-build
      - measure
      - pdf-export

generate-raci.ts derives the matrix from each procedure's owner_agent and stage data. True to workspace principles, it does not fabricate values without evidence: Consulted and Informed are deliberately empty today because no source data exists — a documented gap for a later human pass, not a hole the machine papered over. validate-raci.ts checks the result fail-closed, including whether each declared role key resolves to an actual agent file or the human-roles registry (DEG-R-04).

ADR-0084 adds an actor model on top as an opt-in extension. Whether each role key is a human or an agent (actor_type: human|agent) is not hand-authored — the generator derives it from the governance/_human-roles.yaml registry and the existence of agent files. A companion rule (DEG-R-06) says an activity whose accountable key types as human must have a matching decision gate — a human checkpoint must be declared to be kept.

Execution — artifacts and decision gates

The third group answers "what comes out, and what must it pass". Two pieces. One is the artifact model: procedures/_output-types.yaml, the closed list of output types a variant can produce, bumped to schema 1.1 so each type records which procedure actually produces it (owner_agent, description). The other is the decision gate: decisions/gates.yaml declares go/no-go checkpoints in the workflow.

# templates/co-deck/decisions/gates.yaml (excerpt)
schema_version: "1.0"
variant: co-deck
gates:
  - id: DG-DECK-01
    title: "Layout gate passes with zero violations before export."
    stage: S2
    decider_agent: version
    inputs:
      - pdf_deck
    outcomes:
      - proceed
      - rework
    record_kind: DEC

This is easy to confuse with the Decision Records (DEC-*.md) covered in Reference B. The relationship: a gate is a verdict point inside the procedure (a declared rule such as "the layout check must pass before export"), while a decision record is the log of a verdict actually made ("2026-09-20 verdict: proceed"). record_kind: DEC is the bridge between the two worlds — verdicts produced at gates leave a paper trail as decision records.

Figure 13-3. A gate is the declaration of a rule that must be passed; a decision record is the trace of the verdict actually made.

With this migration, the prose quality_gates field was removed entirely from the procedures of the nine governed templates: quality criteria stopped being scattered sentences and became data with a name, a decider, inputs, and outcomes.

Graph — the Domain Execution Graph

The fourth group is the relationship layer. The skill relationship graph (docs/skill-graph.json) you met in Reference C is a projection regenerated from source files at every /sync — never a primary store. The Domain Execution Graph is a vocabulary profile layered on top of it: the graph gains a graph_profile: "deg/v1" marker plus new node and edge types.

  • stage nodes with in_stage·stage_follows edges — which activity belongs to which stage, and the order of stages
  • step_uses_skill·step_by_agent·produces — which skill a procedure step uses, who performs it, what it produces (already present since ADR-0060 Amendment 5)
  • accountable_for·consulted_on·informed_of — accountability edges derived from RACI
  • decision_gate nodes with gated_by·decides_on — which activity waits on which gate's verdict

The point: data that used to live in four separate groups becomes connected executable knowledge in one graph. "This activity is in S2, performed by html-build, uses skill X, produces pdf_deck, and must pass gate DG-DECK-01" becomes answerable with a single graph query. Reference C's principles — regenerated from source, advisory — carry over unchanged. ADR-0084 adds a graph delta log on top: recording the structural diff of the graph at every /sync yields a chronological trace of how the operating model itself evolved.

Extensions — actor model · evidence backporting · delta log

ADR-0083 left extension candidates such as the actor model, a richer evidence model, and the SkillHone evolution loop as "named, not designed". The follow-up ADR-0084 implemented the actor model and added two more routes: evidence backporting and the graph delta log.

  • Actor model — the actor_type derivation from s3. Human versus agent is resolved from the registry and file existence, never hand-recorded.
  • Evidence backporting — a read-only scanner (evidence-backport-scan.ts) that finds evidence accumulated in projects (L3) worth routing back into templates (L2). This adds "evidence" as a named surface of the project-resync pipeline's selective backport review.
  • Graph delta log — the graph change history described in s5.

The remaining extensions — a richer evidence model and the SkillHone evolution loop — stay undesigned until real data demonstrates the need. "Don't build it in advance" is the same principle as the roadmap story in Chapter 8.

In practice — validation and new variants

You will touch this structure in two situations: inspecting or validating an existing governed template's operating model, and promoting a new variant built in Chapter 11. A promoted official template now records its stage/RACI/gate status as a grade. The validation commands, collected:

# Run from the workspace root
bun scripts/validate-process.ts    # stage axis validation (incl. DEG-P-01)
bun scripts/validate-raci.ts       # RACI matrix + actor model validation (DEG-R family)
bun scripts/validate-procedures.ts # procedure schema validation (ADR-0063, existing)
bun scripts/verify-skill-graph.ts  # graph regeneration consistency (ADR-0060, existing)

The grade system, summarized:

GradeMeaningTemplates
governedA stage axis genuinely distinct from phase exists, with RACI and gates in data formco-abap, co-consult, co-deck, co-design, co-export, co-game, co-hr, co-price, co-security (9)
coreProcedures, skills, and graph are in place; the stage axis awaits human authoring (mechanical bootstrap impossible — no distinct grouping exists)co-develop, co-news, co-safety, co-work (4)

"governed" is not superior to "core" — core is an honest status marker meaning "awaiting human authoring because the machine could not produce a distinct axis". The instinct it asks you to practice — settling the order (stage), accountability (RACI), and verdicts (gates) up front — is exactly the Domain Operating Model's instinct. Apply what the templates taught you to your own design.
