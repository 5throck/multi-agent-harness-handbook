Governance Enforcement Layers — How Rules Become Rules

Chapter 3's permission model tells you "what not to do". This document answers the next question — "how are violations reliably prevented?" The workspace applies the same rule across three layers — hook, prompt, and skill — so that when one layer is unavailable, another holds the line.

Source: ai-workspace-standards CONSTITUTION.md §11 · ECC governance Phase 1–3 designs (docs/designs/ecc-phase*.md) · scripts/hooks/gateguard-fact-force.ts v1.2.0 · scripts/audit.ts v2.28.0

What This Reference Bovers
  • The hook/prompt/skill three-layer enforcement model — strength and coverage of each
  • GateGuard's pre-edit fact-forcing — what it makes agents investigate
  • How the governance infrastructure matured across three phases
  • The validator script family and the fail-closed vs warn distinction
  • Why enforcement differs per platform, and what to do when blocked

Overview — Defense Is Not Once, but Three Times

Consider a single rule: "an agent must not edit files carelessly." If it lives only in the system prompt, everything ends the moment the agent misses or ignores the instruction. The workspace solves this with a three-layer enforcement model.

LayerMeansStrengthCoverage
1. HookDeterministic scripts (Claude PreToolUse, Gemini BeforeTool)Strongest — cannot proceed until the gate passesClaude Code CLI and Gemini CLI full support; Desktop App conditional; Antigravity and Codex unsupported
2. PromptSystem instructions embedded in CLAUDE.md/GEMINI.md/CODEX.mdMedium — relies on agent self-complianceAll four platforms
3. SkillOn-demand manual invocation such as /gateguardWeakest (optional) — human-initiatedAll four platforms

The design intent is clear. The strongest layer, hooks, has uneven platform support — so where hooks are missing, the prompt layer provides minimum defense, and the skill layer leaves a human-driven inspection tool. The failure of one layer is not the failure of the whole.

GateGuard — Pre-Edit Fact-Forcing

GateGuard is a pre-edit quality gate. It fires the first time any file edit is attempted in a session, and forces the agent to investigate three things before editing.

  • Which files import or reference the target
  • What schemas, interfaces, or types the file exports
  • Whether user instructions impose scope constraints on this task

Once the investigation completes, it emits a structured [GATEGUARD] Pre-edit investigation complete block with a risk level and recommendation. There are two modes — ask mode (Claude default) holds progress until the agent presents its findings, while deny mode (Gemini default; opt-in for Claude via --mode deny) hard-blocks the edit with exit code 2. Session state persists as PID-keyed JSON in .gateguard-state/, surviving hook process re-spawns. Safe paths such as memory/ and CHANGELOG.md are exempt.

The core insight of GateGuard: "most agent mistakes come from insufficient investigation." Just checking who imports a file before editing it filters out a large share of schema-breaking edits. The device does not make rule-breaking impossible — it makes proceeding without thinking properly impossible.

Three Stages of Governance Maturation

This infrastructure was not built in a day. It accumulated through three phases of the ECC governance roadmap.

  • Phase 1 — Core infrastructure (P0): the three-layer model, GateGuard hook + prompt + skill, JSON schemas for agent/skill frontmatter, prompt-defense baselines (encoding vigilance, abuse-pattern detection), and CONSTITUTION §11
  • Phase 2 — Hardening (P1): command frontmatter schema, GateGuard --mode ask|deny configurability, Gemini AfterTool integration (post-write-lifecycle-check.ts), hook-reliability subprocess unit tests
  • Phase 3 — Maturation (P2): PID-keyed state persistence (.gateguard-state/), automated encoding vigilance in audit.ts (CRLF, homoglyphs, zero-width characters), and gating of high-value config files (CLAUDE.md, CONSTITUTION.md, package.json) via GOVERNED_CONFIG_PATHS

The lesson is simple — governance is software too. Don't aim for completeness in the first version; grow it through core → hardening → maturation, absorbing real blockage cases along the way.

The Validator Script Family

If hooks are the gates of the "editing moment", the validator scripts are the gates of the "commit and sync moment".

  • scripts/audit.ts — the master workspace standards auditor: structural checks, dead links, encoding vigilance, frontmatter schema validation, spec-registry checks, and more; exits 1 on any FAIL
  • scripts/qa-gate.ts — the Phase 6 quality gate: runs audit.ts as step 1 (hard fail), then project tests, documentation consistency, and governance-record deployment verification; any failure halts the pipeline
  • scripts/validate-agents.ts / validate-skills.ts / validate-templates.ts — validate agent, skill, and template frontmatter and their governance records (docs/lifecycle/)
  • scripts/verify-adr-governance.ts — detects ADRs accepted without governance-doc references and marker-hash drift against constitution sources (detailed in Reference B)

fail-closed vs warn — Where to Stop and Where to Let Slide

audit.ts results come in three grades.

  • Pass — passed
  • Fail — increments an error counter and ends in process.exit(1), halting the entire pipeline (fail-closed)
  • Warn — prints a yellow warning and passes

What stays at Warn is a policy choice. Variant script drift, context commonization, and CRLF (temporarily, during the Windows rollout) are Warn — auto-failing them risks false positives, but they must remain visible. Schema errors like missing required fields, by contrast, are Fail. Within schema validation, error (required missing) and warning (recommended missing) are distinguished, and only errors lead to Fail.

Platform Differences in Enforcement

Part of this design's maturity is honestly admitting that the same rule feels different per platform.

  • Claude Code CLI / Gemini CLI — full hook support; mechanical blocking works.
  • Claude Desktop App — hooks fire conditionally; the prompt layer is the main line of defense.
  • Antigravity — no hook support; only prompt instructions remain. Ignoring the rule there triggers no mechanical block, but it is recorded as a governance violation.
  • Codex (CLI · Desktop App) — no hook support. Instead, CODEX.md is injected directly as the system prompt, so the prompt layer is the baseline defense. Ignoring the rule there triggers no mechanical block, but likewise it is recorded as a governance violation.

So the correct reading is not "rules are optional where hooks are missing" but "the enforcement layer weakens; the nature of the violation does not."

What to Do When Blocked

  1. Read the gate message — in GateGuard ask mode, the reason states what to investigate (referencers, schemas, scope).
  2. Investigate and present findings — confirm importers, schemas, and scope constraints, then answer with that evidence to be allowed through.
  3. In deny mode — the edit is hard-blocked. Investigate, then retry the same edit. Bypasses (--no-verify etc.) are forbidden — they skip secret scanning and every quality gate.
  4. Blocked at qa-gate — fix the first item in the FAIL list. If two iterations don't clear it, escalation to the PM is the defined procedure (maximum 2 retries).
