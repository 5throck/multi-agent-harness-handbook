The Decision System — How Decisions Are Recorded and Verified

An organization's architecture is an accumulation of decisions. But when decisions live only in meeting notes and memory, three months later everyone asks "why did we do it this way?" again. This document covers the mechanisms by which the workspace treats decisions as first-class assets — Decision Records, the spec registry, the governance backlog, and reflection validation.

Source: ai-workspace-standards ADR-0061 Decision Record Standard · ADR-0055 Spec Registry Enforcement · ADR-0059 Governance Reflection Validators · docs/designs/2026-08-16-governance-backlog-design.md · scripts/validate-decisions.ts · scripts/ticket.ts

What This Reference Bovers
  • The structure of a Decision Record and the Agent→Skill→Knowledge→Evidence→Rule→Decision chain
  • The evidence ledger and the supersession-only mutation model
  • The spec registry, the spec-relevance gate for code changes, and E1–E5 exemption codes
  • Governance backlog tickets and not_before scheduling
  • Reflection validation that catches ADRs never linked into governance docs

Overview — Decisions Are Assets

Code gets reviewed and tested, but decisions often don't. Judgments like "keep this skill as an experimental relation only" or "hold this variant's promotion" that exist only in conversations and memories make the organization relitigate the same arguments. The workspace's answer: write decisions as files, bind their rationale into a chain, and verify them mechanically. This is also why Reference C's graph embraces decision records as nodes — relations and rationale must share one map to be navigable.

Structure of a Decision Record

A Decision Record is a file at docs/decisions/DEC-YYYYMMDD-NN.md that closes the Agent → Skill → Knowledge → Evidence → Rule → Decision chain. Required frontmatter is id, date, agent, decision, alternatives, status, with optional arrays evidence_refs, knowledge_refs, rules_applied, skills_used.

  • Evidence ledger — docs/evidence/ledger.md. Rows of (claim, source, url/ref, verification, status) with row IDs of the form EV-YYYYMMDD-NN. A record's evidence_refs may only point at these ledger row IDs
  • Gate-moment recording — the PM agent must emit a record for gate-moment decisions (specialist selection, design approval) before dispatch continues
  • Supersession-only mutation — decision records are never deleted. A reversed decision is a new record superseding the old one. The history of decisions is linked, not overwritten

The Seven Checks of validate-decisions.ts

scripts/validate-decisions.ts checks every DEC-*.md for the following.

  1. Presence of frontmatter
  2. Completeness of the six required fields
  3. Alignment of id with the filename stem
  4. status vocabulary (proposed | accepted | superseded)
  5. evidence_refs being a subset of ledger row IDs
  6. knowledge_refs resolving to existing files
  7. rules_applied format (<PREFIX>-R<N>) and skills_used resolving to real skills

This validation is fail-closed — any error-level issue means exit 1. Unlike soft checks that only warn, sync does not proceed with a broken decision record.

Spec Registry and E1–E5 Exemptions

Before a decision comes its design (spec). The ADR-0055 spec registry (docs/specs/registry.json) tracks design documents by id, title, file, status (proposed | approved | implemented), and last-updated date.

The core is the spec-relevance gate. If a change touches code but shows no related spec activity — touching docs/specs/ or docs/designs/, or an approved/implemented spec updated within 7 days — the audit fails. It structurally catches the state of "the code changed but the design record froze".

Of course, demanding a design document for every change would be excessive. So exemptions are limited to exactly five codes.

CodeTarget
E1memory-log — session log entries
E2changelog — CHANGELOG.md updates only
E3hotfix-typo — single-line trivial fixes
E4pure-readme — README body text, no structural change
E5sync-only — lifecycle finalization (/sync) execution only

Ad-hoc exemptions are forbidden, and using a non-existent exemption code is itself a hard fail. Abuse of exemptions is a governance violation.

The Governance Backlog

Not every decision must be made now. Things that "will need a judgment someday" are deferred as governance backlog tickets. Where a service ticket (Chapter 7) is a one-off work request, a governance backlog ticket is a future decision tracked in git.

  • Managed via scripts/ticket.ts, stored as git-tracked files in tickets/governance/
  • A kind: manual ticket with a not_before date stays hidden from list --ready --kind manual until that date passes — a soak reservation
  • The state machine is backlog → waiting → review → done
  • When ready tickets surface at session start or the weekly check, the PM resolves pure decisions via review→done and dispatches implementation needs through the normal PM Gateway

It is a device that records "we choose not to decide now" itself. Not forgetting — reserving.

Governance Reflection Validation

ADR-0059 was born from a concrete incident — an ADR was accepted without a single reference in any governance document, so nobody actually followed it. scripts/verify-adr-governance.ts detects two things.

  • Unlinked ADRs — ADRs accepted on or after the cutoff date (2026-08-23) with no mention in CONSTITUTION, docs/constitution/, or docs/governance/. The "accepted but never reflected" state
  • Marker-hash drift — document sections duplicated from constitution sources (marker-bound intentional duplicates) whose hashes no longer match the source. A signal that the source changed but the copy didn't follow

Under --strict, both block /sync. The remedy procedure for marker drift is fixed — review and update the duplicated section, re-seed hashes with --update-marker-hashes, and re-sync.

The Lifespan of a Decision

Two time rules govern decisions. They are easy to confuse, so let's scope them precisely.

  • 7-day soak (ADR-0055) — the grace period during which spec-registry enforcement ran at warn-only level for burn-in. A spec updated within the last 7 days counts as "active"
  • 90-day rule (ADR-0060) — specific to experimental relations in skill-graph overrides. After 90 days without promotion to frontmatter, a staleness warning fires (Reference C)

Practical — The Journey of One Decision

  1. Design — if the change isn't trivial, write a design document and register it (proposed → approved).
  2. Implement + record — alongside implementation, record the gate-moment judgment as a Decision Record. Evidence goes into the ledger first, referenced by EV- IDs.
  3. Verify — /sync runs the audit (spec relevance), validate-decisions.ts, and governance reflection validation. Any Fail blocks progress.
  4. Reflect — an accepted ADR must be linked into the governance docs. Leave it unlinked and the ADR-0059 validator catches it.
  5. Defer — if the evidence to decide now is lacking, reserve it as a backlog ticket with not_before. The ticket takes responsibility, not memory.
