6장 §2-C · Codex-Focused Multi-Agent Team Practice

이 과정 전체가 따르는 원칙 — 아래 모든 시나리오는 먼저 역할을 도구 중립적인 AGENTS.md 명세로 적고, Codex에서는 그 명세를 사전 정의 서브에이전트로 "구현"하지 않는다. 대신 워크스페이스 공통 폴더 agents/<name>.md에 같은 명세를 옮겨두고, PM이 세션 중에 그 파일을 읽기 전용 역할 컨텍스트로 불러와 "그 역할처럼 사고하며" 직접 작업을 수행한다. 정의는 하나, 실행 방식만 도구별로 다르다는 원칙을 손으로 확인하는 것이 이 실습의 핵심 목표다 — Claude·Antigravity에서의 대응 방법은 6장 §2-A·6장 §2-B를 참조한다.
Codex에는 서브에이전트를 스폰하는 도구 자체가 없다. 이 문서에서 "역할을 호출한다"는 표현은 전부 "PM이 해당 역할의 정의 파일을 불러와 그 역할을 수행한다"는 뜻이고, "병렬로 실행한다"는 표현은 세션 하나 안에서가 아니라 여러 터미널/창에 걸친 별도 세션을 뜻한다. 이 차이를 계속 의식하면서 아래 시나리오를 따라간다.

준비: 필요한 프로그램 설치

아래 실습은 Codex Desktop App과 Codex CLI 위주로 진행된다. 로컬 환경에 이 도구들이 아직 없다면, 이 핸드북에 함께 담아 둔 환경 설정 자동화 도구인 setup 가이드가 이 장의 실습에 정확히 필요한 구성을 자동으로 설치해준다. 안내에 따라 스크립트를 내려받아 로컬에서 실행하면 된다.

📦 설치 전 확인 사항

스크립트를 실행하기 전에 사전 설치 체크리스트를 먼저 읽어본다. 이 문서에는 다음 전제 조건이 정리되어 있다.

  • 활성 상태의 OpenAI 계정 및 Codex 사용 권한 (구독제/계정 기반 플랜 또는 API 키 — 조직 정책에 따라 다름)
  • gh auth login을 진행할 수 있는 GitHub 계정
  • 최소 5GB의 여유 디스크 공간
  • 관리자(admin) 또는 sudo 권한
GitHub 계정이 아직 없다면
① 브라우저에서 github.com/signup에 접속한다.
② 이메일 주소, 비밀번호, 사용자 이름(username)을 입력한다 — username은 나중에 저장소 URL(github.com/<username>/...)에 그대로 쓰이므로 신중히 정한다.
③ 자동 가입 방지를 위한 퍼즐/코드 인증을 통과한다.
④ 가입 시 입력한 이메일로 온 인증 메일을 열어 이메일 인증을 완료한다 — 이 단계를 건너뛰면 이후 gh auth login이나 저장소 생성이 막힐 수 있다.
⑤ 무료(Free) 플랜으로 가입하면 충분하다 — 이 핸드북의 실습·PR 연습에는 유료 플랜이 필요 없다.
가입이 끝나면 GitHub CLI(gh)가 위 설치 스크립트에 포함돼 함께 설치되고, 아래 gh auth login 명령으로 터미널을 그 계정과 연결한다. 
gh auth login
# 안내에 따라: GitHub.com 선택 → HTTPS 선택 → 브라우저로 로그인(권장) 선택
# 브라우저가 열리면 방금 만든 계정으로 로그인하고 인증 코드를 확인한다

Windows에서 설치하기

이 핸드북의 경로 표기가 Windows 기준이므로, Windows 사용자는 아래 명령으로 5throck/setup 저장소를 클론한 뒤, PowerShell을 관리자 권한으로 실행해서 이어지는 명령을 돌린다.

PowerShell을 관리자 권한으로 여는 법
① 시작 메뉴를 열고 PowerShell을 검색한다.
② 검색 결과의 "Windows PowerShell"을 마우스 우클릭한다.
③ 나오는 메뉴에서 "관리자 권한으로 실행"을 선택한다.
④ 사용자 계정 컨트롤(UAC) 창이 뜨면 "예"를 눌러 승인한다.
창 제목 표시줄에 관리자: Windows PowerShell처럼 "관리자"가 붙어 있으면 제대로 연 것이다. winget 설치 등 일부 단계는 관리자 권한 없이 실행하면 오류가 나거나 조용히 건너뛰어질 수 있다. 
git clone https://github.com/5throck/setup.git
cd ./setup
powershell -ExecutionPolicy Bypass -File .\setup-windows.ps1
# 선택 옵션: -WSL2, -WezTerm, -Docker, -Force (이미 설치된 도구도 재설치)

스크립트가 끝나면 터미널을 완전히 닫았다가 다시 열어야 PATH 변경 사항이 적용된다.

macOS / Linux에서 설치하기

아래 명령으로 5throck/setup 저장소를 클론해서 사용한다. macOS는 setup-mac.sh, Linux는 setup-linux.sh를 실행하며, 둘 다 --wezterm, --docker 선택 플래그를 지원한다.

git clone https://github.com/5throck/setup.git

# macOS
cd ./setup && bash setup-mac.sh

# Linux
cd ./setup && bash setup-linux.sh

설치 검증하기

운영체제와 무관하게 setup-common.ts를 bun으로 실행하면 설치 상태를 점검하는 체크리스트 표가 출력된다. 모든 항목이 ✅로 표시되면 아래 실습을 진행할 준비가 된 것이다.

cd ./setup && bun setup-common.ts

이 프로젝트가 설치하는 도구 중 이 장의 실습과 직접 관련된 것은 다음과 같다. Codex Desktop App, codex(Codex CLI), 그리고 워크스페이스 공통 agents/*.md 참조에 필요한 bun, 이후 장에서 쓰이는 gh(GitHub CLI)까지 함께 설치된다.

설치 중 문제가 생기면 Windows 기준 %USERPROFILE%\workshop-setup-logs\ 폴더에 로그가 남는다. 문제를 해결할 때 이 로그부터 확인한다.
● 초급 Getting Started 역할 정의 하나를 읽어들여 Codex Desktop App PM이 그 역할처럼 작업을 수행하는 첫 단계
G-1 초급 첫 역할 정의를 읽고 PM이 그 역할을 수행하기
하네스를 처음 써보는 개발자가 실습 전용 빈 폴더 harness-lab/를 새로 만들고, reviewer 역할을 도구 중립적인 AGENTS.md 명세로 먼저 적어 둔 뒤, 같은 내용을 agents/reviewer.md에도 옮겨 둔다. Codex Desktop App에서 PM이 이 파일을 읽기 전용 역할 컨텍스트로 불러와 "리뷰어처럼 사고하며" 직접 검토를 수행하는 과정을 관찰한다. 이 폴더는 실습 전용이므로 다른 프로젝트 파일과 섞이지 않는다.
사용 요소
AGENTS.md (2장) 역할 정의하기 (Codex) 역할 수행/전환하기 (Codex)
단계별 실행
  1. ① 실습 폴더 생성 및 진입

    현재 폴더 아래 harness-lab 폴더를 새로 만들고 그 안으로 이동한다. 이후 모든 명령은 이 폴더 안에서 실행한다.

    mkdir -p harness-lab
cd harness-lab
  2. ② 공통 역할 명세 작성 — AGENTS.md

    Claude나 Antigravity, Codex, 그 외 AGENTS.md 표준을 지원하는 어떤 도구로 열어도 같은 의미로 읽히도록, reviewer 역할을 도구 종속적인 표현 없이 순수 텍스트로 적는다. 이 파일 하나가 "무엇을 하는 역할인가"의 유일한 원본이 된다. macOS/Linux/Git Bash에서는 아래 명령을 그대로 쓴다.

    cat > AGENTS.md << 'EOF'
## Agent: reviewer

역할: 텍스트 파일의 오탈자, 논리적 허점, 개선점을 검토한다.
입력: 검토 대상 텍스트 파일 경로
출력: 오탈자 · 논리적 허점 · 개선점 목록
권한: 읽기 전용 — 파일을 직접 수정하지 않는다.
EOF

    Windows PowerShell에서는 cat 명령 자체는 Get-Content의 별칭으로 파일 읽기에 그대로 쓸 수 있다. 다만 << 'EOF'처럼 여러 줄을 직접 넣는 heredoc 문법은 지원하지 않으므로, 같은 내용은 따옴표 있는 here-string(@'...'@)으로 만들어 Set-Content로 파일에 쓴다.

    @'
## Agent: reviewer

역할: 텍스트 파일의 오탈자, 논리적 허점, 개선점을 검토한다.
입력: 검토 대상 텍스트 파일 경로
출력: 오탈자 · 논리적 허점 · 개선점 목록
권한: 읽기 전용 — 파일을 직접 수정하지 않는다.
'@ | Set-Content AGENTS.md
  3. ③ 워크스페이스 공통 역할 파일로 옮기기 — agents/reviewer.md

    Codex는 .claude/agents/ 같은 플랫폼 전용 폴더 대신, 워크스페이스 루트의 agents/<name>.md를 읽기 전용 역할 컨텍스트로 참조한다. AGENTS.md의 명세를 그대로 frontmatter 형식으로 옮겨 적는다.

    mkdir -p agents
cat > agents/reviewer.md << 'EOF'
---
name: reviewer
description: 텍스트 파일의 오탈자, 논리적 허점, 개선점을 검토한다
tools: Read, Grep
tier:
  codex: medium
---

## 역할
텍스트 파일의 오탈자, 논리적 허점, 개선점을 검토한다.

## 입력
검토 대상 텍스트 파일 경로

## 출력
오탈자 · 논리적 허점 · 개선점 목록

## 권한
읽기 전용 — 파일을 직접 수정하지 않는다.
EOF
Codex Desktop App — PM이 agents/reviewer.md를 역할 컨텍스트로 불러와 직접 검토

터미널이나 별도 에디터에서 미리 파일을 만들지 않는다. 아래 두 단계를 그대로 따라간다 — 회색 코드 상자는 전부 "복사" 버튼으로 그대로 복사해서 붙여넣으면 되는 내용이다.

  1. ① Codex Desktop App에서 프로젝트 열기

    Codex Desktop App을 실행하고, 방금 만든 harness-lab/ 폴더를 프로젝트로 연다.

  2. ② 검토 대상 파일 생성 + 역할 컨텍스트로 검토 요청 — 채팅창에 아래 문장을 그대로 붙여넣고 전송 
    notes.txt 파일을 만들고 "이 프로젝트는 매우 좋다. 이것은 아주 좋다."라고 써넣은 뒤, agents/reviewer.md에 정의된 reviewer 역할을 읽기 전용 컨텍스트로 불러와서 그 역할대로 notes.txt를 검토해줘.
    Codex Desktop App의 PM은 별도의 서브에이전트를 스폰하지 않는다. 대신 agents/reviewer.md를 Read 도구로 열어 "역할/입력/출력/권한" 명세를 컨텍스트에 적재하고, 이후 응답을 그 역할의 제약(읽기 전용, 오탈자·논리적 허점·개선점만 보고)에 맞춰 생성한다 — 파일을 실제로 수정하지 않는 것도 스스로 지켜야 한다. 화면에는 서브에이전트 스폰 과정 대신, PM이 agents/reviewer.md를 읽는 도구 호출과 그 뒤를 잇는 검토 결과가 하나의 연속된 세션으로 표시된다.

Codex CLI에서도 완전히 동일하게 — 터미널에서 codex를 실행한 뒤 ②의 문장을 그대로 채팅으로 붙여넣으면, CLI가 똑같이 agents/reviewer.md를 읽고 그 역할대로 응답한다. Codex Desktop App과 CLI 사이에 역할 정의·수행 방식의 차이는 없다 — 둘 다 자동 발화하는 훅도 없다.

결과 확인 — 화면에 PM이 agents/reviewer.md를 읽는 도구 호출이 실제로 보이는지 확인한다. 마지막 응답에는 오탈자·논리적 허점·개선점을 나눈 목록이 보여야 정상이다 — PM이 "수정했습니다" 같은 답을 하거나 notes.txt를 직접 고쳤다면 agents/reviewer.md의 "읽기 전용" 권한 제약을 스스로 지키지 않은 것이다(Codex에는 이를 강제하는 tools 제한 메커니즘이 없다 — 역할 문서의 지침을 PM이 스스로 지키는 구조다).
흔한 실패 — PM이 agents/reviewer.md를 읽지 않고 곧바로 notes.txt를 검토해버린다면, ② 단계 문장에 agents/reviewer.md에 정의된 reviewer 역할을 읽기 전용 컨텍스트로 불러와서라는 표현이 빠진 경우다. Claude 계열의 "서브에이전트 호출"과 달리, Codex는 역할 파일을 명시적으로 참조하라고 요청하지 않으면 그냥 기본 PM 페르소나로 응답할 수 있다.
● 중급 Daily Workflow PM이 하나의 세션 안에서 writer 역할과 reviewer 역할을 순서대로 전환해가며 지휘하는 실무 패턴
D-1 중급 writer → reviewer 2단계 순차 역할 전환
G-1을 마친 실무자가 같은 harness-lab/ 폴더에서, 두 번째 역할 writer도 G-1과 같은 방식으로 AGENTS.md와 agents/writer.md에 먼저 명세한다. Codex PM이 writer 역할로 먼저 초안을 쓰고, 같은 세션 안에서 reviewer 역할로 전환해 그 결과를 비평하는 과정을 순서를 지켜 관찰한다 — 두 역할 모두 같은 PM이 순차적으로 "연기"할 뿐, 별도의 인스턴스가 스폰되지 않는다는 점이 Claude/Antigravity와의 핵심 차이다.

Claude/Antigravity는 writer.md/reviewer.md 각각의 인스턴스를 스폰하지만, Codex는 단일 PM 세션이 역할만 바꿔 순서대로 "연기"한다 — 상자 4개 전부 같은 PM이다.

사용 요소

  1. ① writer → reviewer 순차 전환 요청 — 채팅창에 아래 문장을 그대로 붙여넣고 전송 
    agents/writer.md에 정의된 writer 역할을 읽기 전용 컨텍스트로 불러와서, 그 역할대로 draft.txt에 '원격 근무의 장점' 주제 초안을 써줘. 완료되면 agents/reviewer.md에 정의된 reviewer 역할로 전환해서 draft.txt를 검토해줘. 두 단계를 순서대로 진행해.
    PM은 먼저 agents/writer.md를 읽어 writer 역할의 제약(쓰기 허용, 초안만 작성)을 컨텍스트에 적재하고 draft.txt를 생성한다. 그 작업이 끝난 뒤에야 agents/reviewer.md를 새로 읽어 이번에는 읽기 전용 리뷰어로 "역할을 바꿔 입고" draft.txt를 검토한다 — 별도 인스턴스가 스폰되는 것이 아니라, 같은 세션·같은 PM이 참조하는 역할 파일만 바뀌는 것이다. 두 역할 사이의 순서를 조율하는 것도 이 PM 자신의 몫이다.
Codex에는 병렬 스폰 자체가 없으므로 "writer와 reviewer를 동시에 실행해줘" 같은 요청은 성립하지 않는다 — PM은 어차피 한 세션 안에서 한 번에 한 역할만 수행할 수 있다. 의존 관계가 있는 작업은 원래부터 순차적으로만 진행되므로, ①처럼 "두 단계를 순서대로 진행해"라고 명시하지 않아도 결과적으로 순차 실행되지만, 어떤 순서로 어떤 역할을 거칠지는 명확히 지시하는 것이 좋다.
결과 확인 — 채팅 화면에 agents/writer.md 읽기 → draft.txt 작성 → agents/reviewer.md 읽기 → 검토 결과 순서로 도구 호출이 표시되어야 정상이다. 완료 후 harness-lab/draft.txt를 열어 초안이 실제로 저장돼 있는지도 확인한다.

Codex CLI에서도 완전히 동일하게 — 같은 agents/writer.md/agents/reviewer.md를 그대로 쓰고, 터미널에서 ①의 문장을 그대로 붙여넣으면 동일하게 순차 전환된다.

D-2 중급 요청에 따라 호출되는 역할·순서가 달라지는 것 관찰하기
2장 §4b에서 다룬 "동적 팀 구성"과 "다양한 워크플로우 조합"을 Codex에서도 직접 눈으로 확인하는 시나리오다. D-1에서 만든 agents/writer.md·agents/reviewer.md는 그대로 두고, 요청의 성격만 바꿔가며 같은 PM이 실제로 어떤 역할을, 몇 번, 어떤 순서로 참조하는지 관찰한다 — 역할 정의 파일은 한 번도 새로 만들지 않는다는 점이 핵심이다. Codex에는 병렬 팬아웃 자체가 없으므로, "두 관점 동시 검토" 같은 요청도 실제로는 PM이 한 관점씩 순차적으로 처리한다.

동적 팀 구성과 다양한 워크플로우
Codex Desktop App — 같은 역할 명단, 다른 요청 세 번

D-1을 마친 같은 채팅에서 이어서 진행한다. 매번 PM이 어떤 역할 파일을 읽고, 몇 번 전환하는지 화면에 표시되는 도구 호출 과정을 눈여겨본다.

  1. ① 단순 요청 — reviewer 역할 한 번만 필요한 경우 
    draft.txt의 오탈자만 훑어봐줘.
    PM은 이번 요청에 writer 역할로 전환할 필요가 없다고 판단해 agents/reviewer.md만 참조하고 끝낸다. 같은 역할 명단(writer+reviewer)이 정의돼 있어도, 실제로 어떤 역할을 "연기"할지는 요청마다 PM이 그때그때 결정한다는 것을 보여주는 가장 단순한 예다.
  2. ② 복합 요청 — writer 역할과 reviewer 역할을 두 관점으로 순차 조합 
    draft2.txt에 '4일 근무제' 주제로 새 초안을 써줘. 초안이 완료되면, 그 초안을 문법 관점과 논리 관점 두 가지로 각각 검토해줘. Codex는 동시 실행을 지원하지 않으니 한 관점씩 순서대로 진행해.
    이번에는 PM이 agents/writer.md를 참조해 초안을 쓴 뒤, agents/reviewer.md로 전환해 "문법 관점"으로 한 번, 이어서 다시 "논리 관점"으로 한 번 — 같은 역할을 서로 다른 지시로 두 차례 순차 수행한다. Claude/Antigravity의 "팬아웃(동시 병렬 검토)"과 달리, Codex에서는 이것이 항상 순차적인 2회 반복으로 나타난다 — 같은 두 역할로 ①과는 완전히 다른 모양의 워크플로우가 만들어졌다는 점은 동일하다.
①과 ②를 나란히 비교하면 "역할 명단(어떤 역할을 agents/에 정의해 뒀는가)"과 "이번 작업에 실제로 쓰이는 구성(어떤 역할을 몇 번, 어떤 순서로 참조하는가)"이 서로 다른 층위라는 게 뚜렷해진다. 전자는 워크스페이스에 미리 고정돼 있지만, 후자는 매 요청마다 PM이 새로 결정한다 — 다만 Codex는 항상 순차적으로만 결정한다는 제약이 있다.

Codex CLI에서도 완전히 동일하게 — 같은 agents/writer.md/agents/reviewer.md를 그대로 쓰고, 터미널에서 ①②의 문장을 그대로 붙여넣으면 동일하게 동작한다.

흔한 실패 — ②에서 "동시에 검토해줘"라고 요청하면 PM이 실제로는 순차 처리하면서도 "동시에"라는 표현 때문에 결과를 한 번에 뭉뚱그려 보고할 수 있다. Codex에서는 항상 "순서대로", "한 관점씩" 같은 표현으로 순차성을 명시하는 것이 결과를 예측 가능하게 만든다.

Codex CLI — 터미널 두 개, 세션 두 개

  2. ② 두 번째 터미널 — 동시에 writer 역할로 topic-b.txt 작성

    ①과 별개인 두 번째 터미널을 새로 열고, 같은 harness-lab/로 이동해 codex를 또 실행한다. 이 세션은 ①의 세션과 완전히 독립적이다 — 같은 워크스페이스를 보고 있을 뿐, 대화 맥락도 진행 상태도 공유하지 않는다.

두 세션은 서로 다른 프로세스로 실행되기 때문에 실제로 동시에 진행된다 — 다만 이것은 "하나의 오케스트레이터가 두 팀메이트를 공유 작업 목록으로 조율하는" Claude Agent Teams의 병렬과는 성격이 다르다.     같은 방식으로 tier.codex를 high로 바꾼 뒤 검토한다. 응답 시간과 지적의 깊이가 ②③과 어떻게 다른지 기록한다.

    agents/reviewer.md의 tier.codex 필드를 high로 바꿔줘. 그리고 그 reviewer 역할로 argument.txt를 검토해줘.
간단한 오탈자 검토라면 세 티어의 결과 차이가 거의 없지만, 이번처럼 "논증 구조의 허점을 짚어야 하는" 작업에서는 티어가 낮을수록 순환 논증을 순환 논증이라고 정확히 짚지 못하고 표면적인 문장만 지적하는 경향이 뚜렷해진다. 반대로 gpt-5.6-luna는 셋 중 가장 빠르게 응답한다 — 7장에서 설명하는 "판단이 무거운 역할일수록 높은 티어, 정형화된 작업일수록 낮은 티어"라는 원칙이 왜 존재하는지, 속도와 깊이의 트레이드오프를 직접 겪어보면 훨씬 분명해진다.
매번 Codex Desktop App에 "tier.codex 필드를 바꿔줘"라고 요청하면 된다 — 정의 파일을 직접 열 필요 없고, PM이 알아서 agents/reviewer.md를 수정한 뒤 그 역할로 검토를 수행한다.
흔한 실패 — tier.codex 필드에 존재하지 않는 값(haiku/sonnet/opus 같은 Claude 계열 이름을 그대로 쓰는 실수 등)이 들어가면 PM이 값을 무시하고 기본 티어로 조용히 대체할 수 있다. ②③④를 마친 뒤에는 agents/reviewer.md를 직접 열어 tier.codex 값이 low/medium/high 중 의도한 값과 정확히 일치하는지 확인한다.

실습 마무리 정리

5개 시나리오를 모두 마쳤다면, harness-lab/ 폴더를 어떻게 할지 정리한다. 다음 장(7장)에서 새 실습 폴더를 쓰기 때문에 반드시 남겨둘 필요는 없지만, 지금까지 만든 AGENTS.md·agents/*.md 정의를 비교해보고 싶다면 삭제 전에 한 번 훑어보는 것을 권장한다.

🧹 harness-lab 폴더 정리

더 이상 필요 없다면 폴더 전체를 삭제한다. macOS/Linux/Git Bash에서는 아래 명령을 그대로 쓴다.

cd ..
rm -rf harness-lab

Windows PowerShell에서는

cd ..
Remove-Item -Recurse -Force harness-lab
보존하고 싶다면 — 폴더를 지우는 대신 git init && git add -A && git commit -m "harness-lab 실습 기록"으로 로컬 커밋만 남겨두는 방법도 있다. 이후 참고자료로 두고, 다음 장 실습은 별도의 새 폴더에서 시작해도 된다.
P-1에서 두 번째 터미널에 열어 둔 Codex CLI 세션은 harness-lab/ 폴더를 지우면 다음 명령에서 오류를 낸다. 폴더를 정리하기 전에 두 세션을 모두 종료(Ctrl+C 또는 exit)했는지 확인한다.
