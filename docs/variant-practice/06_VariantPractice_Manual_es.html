Recorrido por la estructura del repositorio — 5 lugares para verificar primero después de clonar

Después de clonar el repositorio en la raíz del espacio de trabajo con git clone, recorramos en orden los 5 directorios principales que debe verificar primero. Este orden coincide con el "flujo de ejecución" cubierto en el Capítulo 5.

  1. CONSTITUTION.md — El archivo que debe leerse primero. Define los estándares compartidos para todo el espacio de trabajo (gobernanza, flujo de trabajo de PR, principios multiagente).
  2. CLAUDE.md / GEMINI.md — Verifique el archivo que coincide con la herramienta de codificación con IA que usa. Cada uno define el comportamiento específico de la plataforma (ganchos, comandos de barra, reglas de despacho de agentes).
  3. AGENTS.md — El registro de agentes invocables en este espacio de trabajo. Permite ver de un vistazo "quién hace qué."
  4. templates/ — Todas las 9 variantes disponibles se encuentran bajo este directorio. Abra cada carpeta de variante para examinar su composición de agentes y su pipeline de gobernanza.
  5. scripts/ — new-project.ts se encuentra aquí. Este script es el comando principal que clona una variante en un proyecto real.
Este recorrido es una guía breve destinada a darle una idea de "qué contiene este repositorio" antes de trabajar de forma práctica con agentes en los ejercicios del Capítulo 4. Durante el ejercicio, abra primero estos 5 lugares, y vuelve para explorar el resto de la estructura según sea necesario.

1. Configuración del entorno local

git clone. Clonar en la raíz del espacio de trabajo

ai-workspace-standards no está diseñado para colocarse dentro de un proyecto como una biblioteca típica — está diseñado para clonarse como la raíz del espacio de trabajo mismo. Por ejemplo, si clona este repositorio en una ubicación como C:\git en Windows o ~/git en macOS/Linux, cada proyecto que cree debajo hereda automáticamente las reglas compartidas de CONSTITUTION.md.

¿Qué pasa si ignora esta regla y lo coloca en una carpeta de proyecto específica como un submódulo (por ejemplo, mi-proyecto/ai-workspace-standards/)? Scripts como new-project.ts verifican por sí mismos si se ejecutaron "desde la raíz del espacio de trabajo," y dado que esta condición se rompe, el andamiaje se rechaza de plano, o los cálculos de ruta salen mal y el proyecto se crea en la ubicación equivocada. Peor aún, solo ese proyecto heredaría las reglas compartidas, mientras que cualquier otro proyecto que cree más adelante no heredaría ninguna de ellas — socavando la razón misma por la que existe este repositorio: que todo el espacio de trabajo use los mismos estándares.

git clone https://github.com/5throck/ai-workspace-standards.git C:\git
cd C:\git

bun. Instalar el runtime

Cada script operativo del espacio de trabajo (scripts/*.ts) está escrito en TypeScript y se ejecuta con bun. No hay versiones .sh/.ps1 separadas, por lo que necesita instalar bun antes de poder ejecutar cualquier script.

bun --version
git --version

💡 Clave: una vez que ambos comandos imprimen un número de versión con éxito, su entorno local está listo.

Lista de verificación de inicio de sesión

La lista de verificación de inicio de sesión definida en CONSTITUTION.md sigue este orden.

  1. Establecer la ruta de los ganchos de git: git config core.hooksPath .githooks
  2. Leer CONSTITUTION.md: confirmar los estándares compartidos del espacio de trabajo
  3. Leer el docs/context.md del proyecto: confirmar la única fuente de verdad del proyecto
  4. Leer AGENTS.md: confirmar el registro de agentes del proyecto
  5. Verificar memory/MEMORY.md: confirmar el contexto dejado por sesiones anteriores
  6. Cargar las habilidad(es) especificadas por docs/context.md

2. Comandos de andamiaje de proyecto

bun scripts/list-template-versions.ts. Verificar las variantes disponibles

Antes de crear un nuevo proyecto, verifique primero qué variantes existen en el espacio de trabajo y con qué versiones está etiquetada cada una.

bun scripts/list-template-versions.ts

bun scripts/new-project.ts. Crear un proyecto a partir de una variante existente

El comando más utilizado con frecuencia. Elija una variante y ejecútela junto con un nombre de proyecto, y toda la composición debajo de templates/<variante>/ (definiciones de agentes, habilidades, comandos, pipeline de gobernanza) se clona en un nuevo repositorio independiente.

bun scripts/new-project.ts "mi-nombre-de-proyecto" --variant co-develop

Si desea fijar una versión específica al crear el proyecto, también especifique --version.

bun scripts/new-project.ts "mi-nombre-de-proyecto" --variant co-develop --version 1.4.0
OpciónDescripciónNotas
--variant Especifica qué plantilla de proyecto usar (co-develop, co-design, co-work, etc.) Si se omite, se usa una selección interactiva o un valor predeterminado (depende del comportamiento del script)
--version Fija una etiqueta template-vX.Y.Z específica para la variante dada Si se omite, se usa la versión más reciente

Andamiaje Repositorio git independiente Hereda estándares compartidos

Un proyecto creado se genera como un repositorio git independiente separado de la raíz del espacio de trabajo. Tenga cuidado de no mezclar ediciones a archivos de la raíz del espacio de trabajo y archivos del nuevo proyecto dentro de la misma tarea/commit.

Si desea crear una variante completamente nueva

Si ninguna de las variantes existentes se ajusta y necesita una composición de equipo de dominio completamente nueva, puede primero crear un prototipo independiente de Fase A bajo Projects/<nombre-de-variante>/ usando la habilidad create-variant junto con el comando bun scripts/create-l3-scaffold.ts <nombre-de-variante> --domain <tipo>. Este prototipo puede desarrollarse libremente hasta que se promocione a una variante oficial templates/. Los pasos detallados de este flujo y el procedimiento de promoción se cubren en el Capítulo 11 (Nueva creación D-1) y el Capítulo 12 (Promoción P-1).
