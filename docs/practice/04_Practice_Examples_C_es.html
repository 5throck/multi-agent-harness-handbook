Capítulo 4 §2-C · Práctica de Equipos Multiagente Centrada en Codex

Una guía práctica que comienza desde una carpeta de práctica vacía y recorre escenarios centrados en Codex Desktop App/Codex CLI — ambas herramientas no tienen diferencias en cómo se definen y ejecutan los roles, así que esta sección las cubre juntas  |  ← Volver al documento de referencia del Cap.4 §1  |  Cap.4 §2-A Centrado en Claude →  |  Cap.4 §2-B Centrado en Antigravity →

Propósito de Este ArchivoUn recorrido práctico de 5 pasos en Codex Desktop App/CLI que cubre: leer y ejecutar una definición de rol, cambio de rol secuencial, observar cómo varía el orden de invocación de roles según la solicitud, paralelismo entre sesiones y comparación de niveles de modelo

El Principio que Sigue Todo Este Recorrido — cada escenario a continuación primero escribe el rol como una especificación AGENTS.md neutral respecto a la herramienta, y en Codex esa misma especificación no se "implementa" como un subagente predefinido. En su lugar, la especificación idéntica se copia en la carpeta común del espacio de trabajo agents/<nombre>.md, y durante la sesión el PM carga ese archivo como contexto de rol de solo lectura para "pensar como ese rol" y realizar el trabajo directamente. El objetivo central de esta práctica es confirmar a mano que la definición sigue siendo única mientras solo difiere la mecánica de ejecución según la herramienta — ver Cap.4 §2-A y Cap.4 §2-B para los equivalentes en Claude/Antigravity.
Codex no tiene ninguna herramienta para generar subagentes. Cada vez que este documento dice "invocar un rol", significa "el PM carga el archivo de definición de ese rol y ejecuta el rol", y "ejecutar en paralelo" significa sesiones separadas distribuidas en múltiples terminales/ventanas, no algo que ocurre dentro de una sola sesión. Ten esta distinción presente mientras recorres los escenarios siguientes.

Preparación: Instalación de las Herramientas Necesarias

La práctica siguiente se centra en Codex Desktop App y Codex CLI. Si aún no tienes estas herramientas localmente, la automatización de configuración de entorno incluida en este manual — la guía de setup — instala automáticamente exactamente lo que necesita la práctica de este capítulo. Sigue las instrucciones para descargar y ejecutar el script localmente.

📦 Antes de Ejecutar el Script

Lee primero la lista de verificación previa a la instalación. Enumera estos requisitos previos.

  • Una cuenta de OpenAI activa con acceso a Codex (plan basado en suscripción/cuenta, o una clave de API — depende de la política de la organización)
  • Una cuenta de GitHub con la que puedas ejecutar gh auth login
  • Al menos 5GB de espacio libre en disco
  • Privilegios de administrador (admin) o sudo
Si Aún No Tienes una Cuenta de GitHub
① Ve a github.com/signup en tu navegador.
② Introduce tu dirección de correo, contraseña y nombre de usuario — el nombre de usuario pasa a formar parte de la URL de tu repositorio (github.com/<username>/...), así que elígelo con cuidado.
③ Supera la verificación de rompecabezas/código que evita registros automatizados.
④ Abre el correo de verificación enviado a la dirección con la que te registraste y completa la verificación de correo — omitir esto puede bloquear más tarde gh auth login o la creación de repositorios.
⑤ El plan gratuito (Free) es suficiente — la práctica y los ejercicios de PR de este manual no necesitan un plan de pago.
Una vez completado el registro, la GitHub CLI (gh) se instala junto con el script de setup anterior, y el comando gh auth login de abajo conecta tu terminal a esa cuenta. 
gh auth login
# Sigue las indicaciones: elige GitHub.com → HTTPS → Iniciar sesión con un navegador web (recomendado)
# Cuando se abra el navegador, inicia sesión con la cuenta que acabas de crear y confirma el código de autenticación

Instalación en Windows

Dado que la notación de rutas de este manual sigue convenciones de Windows, los usuarios de Windows deben clonar el repositorio 5throck/setup con el comando de abajo, y luego ejecutar PowerShell como Administrador para los comandos que siguen.

Cómo Abrir PowerShell como Administrador
① Abre el menú Inicio y busca PowerShell.
② Haz clic derecho en "Windows PowerShell" en los resultados de búsqueda.
③ Selecciona "Ejecutar como administrador" en el menú.
④ Haz clic en "Sí" cuando aparezca el aviso de Control de Cuentas de Usuario (UAC).
Si la barra de título muestra algo como Administrador: Windows PowerShell, lo abriste correctamente. Algunos pasos, como las instalaciones de winget, pueden fallar o saltarse silenciosamente sin privilegios de administrador. 
git clone https://github.com/5throck/setup.git
cd ./setup
powershell -ExecutionPolicy Bypass -File .\setup-windows.ps1
# Flags opcionales: -WSL2, -WezTerm, -Docker, -Force (reinstalar herramientas aunque ya estén presentes)

Después de que el script termine, cierra completamente y reabre tu terminal para que los cambios de PATH surtan efecto.

Instalación en macOS / Linux

Clona el repositorio 5throck/setup con el comando de abajo. Ejecuta setup-mac.sh en macOS y setup-linux.sh en Linux; ambos soportan los flags opcionales --wezterm y --docker.

git clone https://github.com/5throck/setup.git

# macOS
cd ./setup && bash setup-mac.sh

# Linux
cd ./setup && bash setup-linux.sh

Verificar la Instalación

Independientemente del sistema operativo, ejecutar setup-common.ts con bun imprime una tabla de verificación que muestra el estado de la instalación. Una vez que cada elemento muestre ✅, estás listo para comenzar la práctica de abajo.

cd ./setup && bun setup-common.ts

Entre las herramientas que este proyecto instala, las directamente relevantes para la práctica de este capítulo son: Codex Desktop App, codex (Codex CLI), además de bun (necesario para referenciar los archivos comunes del espacio de trabajo agents/*.md) y gh (GitHub CLI), usado en capítulos posteriores.

Si algo sale mal durante la instalación, se dejan registros en %USERPROFILE%\workshop-setup-logs\ en Windows. Revisa primero ese registro al solucionar problemas.
● Principiante Getting Started El primer paso: cargar una definición de rol y hacer que el PM de Codex Desktop App ejecute ese rol
G-1 Principiante Leer una Definición de Rol y Dejar que el PM la Ejecute
Un desarrollador nuevo en el harness crea una carpeta vacía dedicada a la práctica llamada harness-lab/, primero escribe un rol reviewer como especificación AGENTS.md neutral respecto a la herramienta, y luego copia ese mismo contenido en agents/reviewer.md. En Codex Desktop App, observa cómo el PM carga este archivo como contexto de rol de solo lectura y "piensa como un revisor" para realizar la revisión directamente. Esta carpeta es solo para práctica, así que se mantiene separada de otros archivos del proyecto.
Elementos Utilizados
AGENTS.md (Cap.2) Definir Roles (Codex) Ejecutar/Cambiar Roles (Codex)
Paso a Paso
  1. ① Crear la Carpeta de Práctica y Entrar en Ella

    Crea una nueva carpeta harness-lab bajo tu directorio actual y entra en ella. Cada comando a partir de ahora se ejecuta dentro de esta carpeta.

    mkdir -p harness-lab
cd harness-lab
  2. ② Escribir la Especificación de Rol Común — AGENTS.md

    Escribe el rol reviewer como texto plano sin frases específicas de una herramienta, para que se lea igual sin importar si se abre en Claude, Antigravity, Codex o cualquier otra herramienta que soporte el estándar AGENTS.md. Este único archivo se convierte en la fuente única de verdad de "qué hace este rol". En macOS/Linux/Git Bash, usa el comando de abajo tal cual.

    cat > AGENTS.md << 'EOF'
## Agent: reviewer

Rol: Revisar archivos de texto en busca de errores tipográficos, vacíos lógicos y áreas de mejora.
Entrada: Ruta al archivo de texto a revisar
Salida: Una lista de errores tipográficos, vacíos lógicos y sugerencias de mejora
Permisos: Solo lectura — nunca modifica el archivo directamente.
EOF

    En Windows PowerShell, el comando cat en sí es un alias de Get-Content, usable para leer archivos. Sin embargo, la sintaxis heredoc << 'EOF' para escribir varias líneas directamente no está soportada, así que construye el mismo contenido como un here-string entre comillas (@'...'@) y escríbelo con Set-Content.

    @'
## Agent: reviewer

Rol: Revisar archivos de texto en busca de errores tipográficos, vacíos lógicos y áreas de mejora.
Entrada: Ruta al archivo de texto a revisar
Salida: Una lista de errores tipográficos, vacíos lógicos y sugerencias de mejora
Permisos: Solo lectura — nunca modifica el archivo directamente.
'@ | Set-Content AGENTS.md
  3. ③ Trasladarlo al Archivo de Rol Común del Espacio de Trabajo — agents/reviewer.md

    En lugar de una carpeta específica de plataforma como .claude/agents/, Codex referencia agents/<nombre>.md en la raíz del espacio de trabajo como contexto de rol de solo lectura. Copia la especificación de AGENTS.md textualmente en formato frontmatter.

    mkdir -p agents
cat > agents/reviewer.md << 'EOF'
---
name: reviewer
description: Revisa archivos de texto en busca de errores tipográficos, vacíos lógicos y áreas de mejora
tools: Read, Grep
tier:
  codex: medium
---

## Rol
Revisar archivos de texto en busca de errores tipográficos, vacíos lógicos y áreas de mejora.

## Entrada
Ruta al archivo de texto a revisar

## Salida
Una lista de errores tipográficos, vacíos lógicos y sugerencias de mejora

## Permisos
Solo lectura — nunca modifica el archivo directamente.
EOF
Codex Desktop App — El PM Carga agents/reviewer.md como Contexto de Rol y Revisa Directamente

No crees archivos de antemano en una terminal o editor separado. Sigue los dos pasos de abajo tal cual — cada caja de código gris se puede pegar tal cual mediante su botón "Copiar".

  1. ① Abrir el Proyecto en Codex Desktop App

    Inicia Codex Desktop App y abre la carpeta harness-lab/ que acabas de crear como un proyecto.

  2. ② Crear el Archivo a Revisar + Solicitar la Revisión mediante Contexto de Rol — Pega el Texto de Abajo en el Chat y Envíalo 
    Crea notes.txt con el texto "Este proyecto es muy bueno. Esto es muy bueno.", luego carga el rol reviewer definido en agents/reviewer.md como contexto de solo lectura y revisa notes.txt según ese rol.
    El PM de Codex Desktop App no genera un subagente separado. En cambio, abre agents/reviewer.md con la herramienta Read, carga la especificación de "rol/entrada/salida/permisos" en el contexto, y moldea su respuesta posterior según las restricciones de ese rol (solo lectura, reportando solo errores tipográficos/vacíos lógicos/mejoras) — también debe respetar por sí mismo "nunca modificar realmente el archivo". En lugar de una secuencia de generación de subagente, la pantalla muestra la llamada de herramienta del PM leyendo agents/reviewer.md seguida del resultado de la revisión, todo como una sesión continua.

Idéntico en Codex CLI — ejecuta codex en una terminal y pega la misma oración del paso ② en el chat; la CLI lee agents/reviewer.md de la misma manera y responde en ese rol. No hay diferencia entre Codex Desktop App y CLI en cómo se definen y ejecutan los roles — ninguno tiene hooks que se disparen automáticamente tampoco.

Verificar el Resultado — confirma que la pantalla realmente muestra la llamada de herramienta del PM leyendo agents/reviewer.md. La respuesta final debe ser una lista dividida en errores tipográficos, vacíos lógicos y mejoras — si el PM responde con algo como "Lo he corregido" o edita notes.txt directamente, no ha respetado por sí mismo la restricción de permiso "solo lectura" en agents/reviewer.md (Codex no tiene un mecanismo de aplicación como la restricción tools de Claude — la guía del documento de rol se respeta voluntariamente por el PM).
Fallo Común — si el PM revisa notes.txt directamente sin leer primero agents/reviewer.md, probablemente a la solicitud del paso ② le faltaba la frase "carga el rol reviewer definido en agents/reviewer.md como contexto de solo lectura". A diferencia de la "invocación de subagente" explícita de Claude, Codex simplemente responderá como su persona de PM por defecto a menos que se le pida explícitamente que referencie el archivo de rol.
● Intermedio Daily Workflow Un patrón práctico donde el PM alterna, en orden, entre el rol writer y el rol reviewer dentro de una sola sesión
D-1 Intermedio Cambio de Rol Secuencial en Dos Etapas: writer → reviewer
Habiendo terminado G-1, un practicante en la misma carpeta harness-lab/ primero especifica un segundo rol, writer, en AGENTS.md y agents/writer.md de la misma manera que en G-1. Observa cómo el PM de Codex primero redacta el texto como el rol writer, y luego cambia — dentro de la misma sesión — al rol reviewer para criticar el resultado, manteniendo el orden intacto. La diferencia clave con Claude/Antigravity es que ambos roles son simplemente "ejecutados" secuencialmente por el mismo PM — nunca se genera una instancia separada.

Claude/Antigravity generan una instancia separada para cada uno de writer.md/reviewer.md, pero Codex tiene una única sesión de PM "ejecutando" cada rol por turno — las cuatro cajas son el mismo PM.

Elementos Utilizados
AGENTS.md (Cap.2) Definir Roles (Codex) Ejecutar/Cambiar Roles (Codex)
Paso a Paso
  1. Añadir a la Especificación de Rol Común — Agregar una Entrada writer a AGENTS.md

    Agrega el rol writer al mismo AGENTS.md de G-1. Deja la entrada de reviewer intacta y añade solo el contenido de abajo. En macOS/Linux/Git Bash, usa el comando de abajo tal cual.

    cat >> AGENTS.md << 'EOF'

## Agent: writer

Rol: Escribir un borrador corto de 3 a 5 oraciones sobre un tema dado.
Entrada: Tema, ruta donde guardar el archivo
Salida: Un archivo de texto con el borrador
Permisos: Escritura permitida — guarda solo en el archivo especificado.
handoff_to: reviewer (pasa a revisión una vez completado el borrador)
EOF

    En Windows PowerShell, añade el here-string con Add-Content (usar Set-Content en su lugar sobrescribiría el archivo, así que Add-Content es necesario para no borrar la entrada de reviewer).

    @'

## Agent: writer

Rol: Escribir un borrador corto de 3 a 5 oraciones sobre un tema dado.
Entrada: Tema, ruta donde guardar el archivo
Salida: Un archivo de texto con el borrador
Permisos: Escritura permitida — guarda solo en el archivo especificado.
handoff_to: reviewer (pasa a revisión una vez completado el borrador)
'@ | Add-Content AGENTS.md
  2. Añadir el Archivo de Rol Común del Espacio de Trabajo — agents/writer.md 
    cat > agents/writer.md << 'EOF'
---
name: writer
description: Escribe un borrador corto de 3 a 5 oraciones sobre un tema dado
tools: Write, Read
tier:
  codex: medium
---

## Rol
Escribir un borrador corto de 3 a 5 oraciones sobre un tema dado.

## Entrada
Tema, ruta donde guardar el archivo

## Salida
Un archivo de texto con el borrador

## Permisos
Escritura permitida — guarda solo en el archivo especificado.

## handoff_to
reviewer (pasa a revisión una vez completado el borrador)
EOF
Codex Desktop App — El Mismo PM Cambia del Rol writer al Rol reviewer

Como en G-1, no prepares archivos de antemano. Continúa en el mismo chat de harness-lab/ que dejaste abierto desde G-1.

  1. ① Solicitar el Cambio Secuencial writer → reviewer — Pega el Texto de Abajo en el Chat y Envíalo 
    Carga el rol writer definido en agents/writer.md como contexto de solo lectura, y escribe un borrador sobre 'los beneficios del trabajo remoto' en draft.txt en ese rol. Una vez hecho eso, cambia al rol reviewer definido en agents/reviewer.md y revisa draft.txt. Haz estos dos pasos en orden.
    El PM primero lee agents/writer.md, carga las restricciones del rol writer (escritura permitida, solo borrador) en el contexto, y genera draft.txt. Solo después de que eso termina lee de nuevo agents/reviewer.md y "se pone" el rol de revisor de solo lectura esta vez para revisar draft.txt — no se genera ninguna instancia separada; en cambio, solo cambia qué archivo de rol referencia la misma sesión/el mismo PM. Coordinar el orden entre los dos roles también es tarea de este mismo PM.
Dado que Codex no tiene ninguna generación en paralelo, una solicitud como "ejecuta writer y reviewer al mismo tiempo" simplemente no es válida — el PM solo puede ejecutar un rol a la vez dentro de una sola sesión de todos modos. El trabajo dependiente es por tanto siempre secuencial por naturaleza, así que los resultados salen secuenciales incluso sin decir explícitamente "haz estos dos pasos en orden" como en ①, pero sigue siendo buena práctica detallar exactamente por qué orden y qué roles pasar.
Verificar el Resultado — el chat debería mostrar llamadas de herramienta en este orden: leer agents/writer.md → escribir draft.txt → leer agents/reviewer.md → resultado de la revisión. Después de completarse, abre también harness-lab/draft.txt para confirmar que el borrador se guardó realmente.

Idéntico en Codex CLI — usando los mismos agents/writer.md/agents/reviewer.md, pegar la oración de ① en una terminal cambia a través de la misma secuencia.

D-2 Intermedio Observar Cómo Varían los Roles y el Orden Según la Solicitud
Este escenario te permite ver, también en Codex, la "composición dinámica de equipo" y las "combinaciones variadas de flujo de trabajo" cubiertas en el Cap.2 §4b. Deja intactos los agents/writer.md·agents/reviewer.md de D-1 y varía solo la naturaleza de la solicitud, observando qué roles referencia realmente el mismo PM, cuántas veces y en qué orden — el punto clave es que los archivos de definición de rol nunca se vuelven a crear. Dado que Codex no tiene fan-out en paralelo, una solicitud como "revisar desde dos perspectivas al mismo tiempo" sigue siendo manejada por el PM una perspectiva a la vez, secuencialmente.

Composición Dinámica de Equipo y Flujos de Trabajo Variados
Codex Desktop App — Mismo Plantel de Roles, Tres Solicitudes Diferentes

Continúa en el mismo chat de D-1. Presta atención cada vez a qué archivo de rol lee el PM y cuántas veces cambia, tal como se muestra en la salida de llamadas de herramienta en pantalla.

  1. ① Una Solicitud Simple — Solo se Necesita un Paso con el Rol reviewer 
    Solo escanea draft.txt en busca de errores tipográficos.
    El PM decide que no hay necesidad de cambiar al rol writer para esta solicitud y solo referencia agents/reviewer.md, luego se detiene. Este es el ejemplo más simple que muestra que incluso cuando está definido el mismo plantel de roles (writer+reviewer), el PM decide caso por caso, por solicitud, qué rol "ejecutar" realmente.
  2. ② Una Solicitud Compuesta — Combinando el Rol writer y el Rol reviewer Secuencialmente desde Dos Ángulos 
    Escribe un nuevo borrador en draft2.txt sobre el tema 'la semana laboral de cuatro días'. Una vez hecho el borrador, revísalo una vez desde un ángulo gramatical y una vez desde un ángulo lógico. Como Codex no soporta ejecución concurrente, avanza un ángulo a la vez en secuencia.
    Esta vez el PM referencia agents/writer.md para escribir el borrador, luego cambia a agents/reviewer.md y lo ejecuta dos veces secuencialmente bajo instrucciones diferentes — una vez como "ángulo gramatical" y una vez como "ángulo lógico". A diferencia del "fan-out" (revisión paralela simultánea) de Claude/Antigravity, en Codex esto siempre aparece como una repetición secuencial de 2x — los mismos dos roles aún producen una forma de flujo de trabajo completamente diferente de ①, tal como en el caso de Claude/Antigravity.
Comparar ① y ② lado a lado deja claro que "el plantel de roles (qué roles están definidos bajo agents/)" y "la composición realmente usada para esta tarea (qué rol se referencia cuántas veces, en qué orden)" son dos capas diferentes. La primera está fijada de antemano en el espacio de trabajo, pero la segunda se decide de nuevo por el PM en cada solicitud — con la restricción de que en Codex siempre se decide secuencialmente.

Idéntico en Codex CLI — usando los mismos agents/writer.md/agents/reviewer.md, pegar las oraciones de ①② en una terminal se comporta de la misma manera.

Fallo Común — incluso cuando el PM maneja ② secuencialmente por debajo, pedir "revisarlos al mismo tiempo" puede hacer que reporte los resultados agrupados como si se hubieran hecho simultáneamente. En Codex, una redacción explícita como "en orden" o "un ángulo a la vez" mantiene el resultado predecible.

● Avanzado Power User Operación en paralelo entre sesiones — ejecutar el rol writer y el rol reviewer contra dos archivos independientes a la vez, en terminales/ventanas separadas
P-1 Avanzado Dividir Trabajo Independiente Entre Ventanas — Paralelismo Entre Sesiones
Habiendo terminado hasta D-1, un usuario experimentado quiere trabajar en dos tareas independientes que no dependen entre sí (redactar topic-a.txt y topic-b.txt) al mismo tiempo. Dado que Codex no tiene ninguna función para generar compañeros de equipo en paralelo dentro de una sola sesión, abre dos ventanas de terminal separadas (o sesiones de Codex CLI) apuntando a la misma carpeta harness-lab/ y asigna cada tarea de forma independiente — la unidad de "paralelo" aquí es la propia sesión, no un compañero de equipo.
Elementos Utilizados
Ejecución en Paralelo — Paralelismo Entre Sesiones (Codex)
Codex CLI — Dos Terminales, Dos Sesiones

Abre dos ventanas de terminal apuntando a la misma carpeta harness-lab/ (o usa una ventana dividida con tmux o similar — la propia Codex CLI no tiene soporte integrado como el teammateMode: "tmux" de Claude Code, así que configuras el multiplexor de terminal tú mismo).

  1. ① Primera Terminal — Redactar topic-a.txt como el Rol writer

    En la primera terminal, entra en harness-lab/, ejecuta codex, y pega la oración de abajo.

    cd harness-lab
codex
    Como el rol writer definido en agents/writer.md, escribe un borrador sobre 'el trabajo remoto' en topic-a.txt. Una vez hecho, cambia al rol reviewer en agents/reviewer.md y revísalo también.
  2. ② Segunda Terminal — Redactar topic-b.txt como el Rol writer, al Mismo Tiempo

    Abre una segunda terminal separada de ①, entra en la misma harness-lab/, y ejecuta codex de nuevo. Esta sesión es completamente independiente de la de ① — simplemente mira el mismo espacio de trabajo, sin compartir ni contexto de conversación ni estado de progreso.

    cd harness-lab
codex
    Como el rol writer definido en agents/writer.md, escribe un borrador sobre 'la semana laboral de cuatro días' en topic-b.txt. Una vez hecho, cambia al rol reviewer en agents/reviewer.md y revísalo también.
Como las dos sesiones se ejecutan como procesos separados, realmente avanzan al mismo tiempo — pero esto es diferente en naturaleza del paralelismo de Claude Agent Teams, donde un único orquestador coordina a dos compañeros de equipo mediante una lista de tareas compartida. Las dos sesiones de Codex no tienen conciencia una de la otra, no hay lista de tareas compartida y no hay canal de comunicación directo entre sesiones como SendMessage. Si ambas sesiones tocan el mismo archivo a la vez (por ejemplo, ambas intentando editar AGENTS.md), puede ocurrir un conflicto simple a nivel del sistema de archivos — asignar archivos objetivo completamente separados es una práctica de seguridad tan importante aquí como lo es para Claude/Antigravity.
Si quieres ver el progreso de ambas sesiones de un vistazo, dividir las ventanas lado a lado con un multiplexor de terminal como WezTerm o tmux ayuda — esto es un asunto de configuración del entorno de terminal, no una característica propia de Codex.
Fallo Común — si ambas sesiones intentan modificar agents/writer.md en sí (por ejemplo, enviando solicitudes de "cambiar el nivel" desde ambas a la vez), puede ocurrir una carrera de escritura y el cambio de un lado puede quedar sobrescrito. Al ejecutar en paralelo, haz que cada sesión toque solo su propio archivo objetivo (topic-a.txt/topic-b.txt), y evita solicitudes que cambien el propio archivo de definición de rol en una sesión paralela.
Ver También: Cap.4 §1-C Detalle de Codex — Por Qué No Hay Ejecución en Paralelo, y la Alternativa Entre Sesiones
P-2 Avanzado Construir Intuición de Costos Comparando Niveles de Modelo
Este escenario te permite sentir, de primera mano y antes de que se te digan los números, qué diferencia real hacen los niveles de modelo (high/medium/low) cubiertos en detalle en el Capítulo 8, en Codex. Referencia el mismo rol reviewer tres veces, cambiando solo el modelo, y compara visualmente la velocidad de respuesta y la calidad del resultado. Ten en cuenta que los nombres de nivel de modelo de Codex difieren de los de la familia Claude (haiku/sonnet/opus).

Prepara un pasaje con un vacío lógico, un poco más complejo que el notes.txt de G-1. Pega el texto de abajo en el chat tal cual.

  1. ① Preparar el Archivo a Revisar 
    Crea argument.txt con el siguiente texto: "El trabajo remoto siempre es más productivo que el trabajo de oficina. Esto es porque las personas que trabajan remotamente dicen que el trabajo remoto es bueno. Por lo tanto, cada empresa debería ser totalmente remota."
  2. ② Revisar en el Nivel low (gpt-5.6-luna)

    Pega el texto de abajo en el chat tal cual. El PM cambia el campo tier.codex en agents/reviewer.md a low y luego revisa en ese rol.

    Cambia el campo tier.codex en agents/reviewer.md a low. Luego revisa argument.txt en ese rol reviewer.
  3. ③ Repetir la Misma Solicitud en el Nivel medium (gpt-5.6-terra)

    Cambia tier.codex a medium de la misma manera y revisa de nuevo. Compara con el resultado de low para ver si señala con precisión un vacío lógico como el razonamiento circular.

    Cambia el campo tier.codex en agents/reviewer.md a medium. Luego revisa argument.txt en ese rol reviewer.
  4. ④ Repetir la Misma Solicitud en el Nivel high (gpt-5.6-sol)

    Cambia tier.codex a high de la misma manera y revisa de nuevo. Anota cómo difieren el tiempo de respuesta y la profundidad de la crítica respecto a ②③.

    Cambia el campo tier.codex en agents/reviewer.md a high. Luego revisa argument.txt en ese rol reviewer.
Para una simple revisión de errores tipográficos, los tres niveles apenas difieren, pero para un trabajo como este — "detectar un fallo en la estructura de un argumento" — cuanto más bajo el nivel, más claramente tiende a fallar en señalar el razonamiento circular como tal y en su lugar comenta solo sobre la redacción superficial. Por el contrario, gpt-5.6-luna responde más rápido de los tres — vivir la compensación entre velocidad y profundidad deja mucho más claro por qué existe el principio del Capítulo 5: "un juicio más pesado requiere un nivel más alto, las tareas más rutinarias requieren uno más bajo".
Simplemente puedes decirle a Codex Desktop App "cambia el campo tier.codex" cada vez — no necesitas abrir el archivo de definición tú mismo; el PM edita agents/reviewer.md por su cuenta y luego revisa en ese rol.
Fallo Común — si el campo tier.codex recibe un valor que no existe (un error como usar nombres de la familia Claude tales como haiku/sonnet/opus, por ejemplo), el PM puede ignorarlo silenciosamente y volver a un nivel por defecto. Después de terminar ②③④, abre agents/reviewer.md tú mismo y confirma que el valor de tier.codex coincide exactamente con el previsto — low/medium/high.

Cierre de la Práctica

Una vez completados los cinco escenarios, decide qué hacer con la carpeta harness-lab/. Como el siguiente capítulo (Capítulo 5) usa una nueva carpeta de práctica, no tienes que conservarla, pero si quieres comparar las definiciones de AGENTS.md/agents/*.md que construiste hasta ahora, vale la pena revisarlas una vez antes de borrarlas.

🧹 Limpieza de la Carpeta harness-lab

Si ya no la necesitas, borra la carpeta completa. En macOS/Linux/Git Bash, usa el comando de abajo tal cual.

cd ..
rm -rf harness-lab

En Windows PowerShell:

cd ..
Remove-Item -Recurse -Force harness-lab
Si Quieres Conservarla — en lugar de borrar la carpeta, también puedes simplemente dejar un commit local con git init && git add -A && git commit -m "registro de práctica harness-lab". Consérvalo después como referencia, y siéntete libre de comenzar la práctica del siguiente capítulo en una nueva carpeta separada.
La segunda sesión de Codex CLI abierta en una terminal separada durante P-1 dará un error en su siguiente comando si borras harness-lab/ debajo de ella. Asegúrate de que ambas sesiones estén cerradas (Ctrl+C o exit) antes de limpiar la carpeta.
