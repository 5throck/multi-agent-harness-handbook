Appendix D · Hermes Agents Operations

Use Hermes Agent inside the existing workspace governance model without creating a second source of instructions.

In this chapter
  • Hermes platform surface
  • Trust and context budget
  • Skill mirrors and AGENTS.md
  • Verification and troubleshooting

Hermes uses a fifth platform directory

In the current standard Hermes Agent is a provider-neutral CLI harness. A project uses .hermes/skills/ as its primary skill path. That directory must be a synchronized mirror of the skills/ source of truth; pointing Hermes directly at the source would bypass security exclusions and country- or variant-scoped pruning.

Hermes discovers skills from directories and invokes them as /skill-name. It needs neither a command mirror nor a skills.json registration file.

Review itemIntent
Project skills .hermes/skills/ mirror
Invocation /skill-name
Registration file do not create one
Command/prompt mirror do not create one
Standard: skills/ SSOT → sync-skills → .hermes/skills → /skill-name

The user owns trust and context settings

Hermes loads project skills only when the project root is listed in user-side skills.trusted_project_dirs. This is a prompt-injection defense, not a nuisance to bypass. Documentation should instruct a user to register a trusted path; the repository must not modify or evade the setting.

The default context-file limit can silently truncate a large AGENTS.md. The standard therefore makes AGENTS.md a thin dispatcher with pointers and a small safety floor. Check context_file_max_chars and Hermes logs, and move detailed policy to referenced governance documents.

Review itemIntent
Trust is user-owned configuration.It shows the trust boundary against prompt injection is controlled by the user, not the repository.
AGENTS.md offers first-screen pointers and minimum safety rules.To pack only the essential rules into the first load within the context budget.
Detailed policy stays in referenced documents.To load deep rules only when needed, avoiding truncation and cost.
Check truncation warnings before delivery.To catch the silent misbehavior a truncated AGENTS.md causes before delivery.
Standard: Trusted project → AGENTS.md pointers → selected governance files → skill execution

Practice

# User-side Hermes onboarding
hermes config set context_file_max_chars 100000

# Then add the project root to skills.trusted_project_dirs
# using the Hermes user configuration. Do not commit user configuration
# or bypass the trust control from the project repository.

Why no HERMES.md is created

Hermes searches HERMES.md before AGENTS.md. Adding a HERMES.md twin would shadow the shared instruction source and create long-term divergence. The standard deliberately uses Hermes’ native AGENTS.md support instead.

For the same reason .hermes/skills/ is a deployed mirror, not an independent editing area. Review changes in skills/ and use synchronization to publish them.

Review itemIntent
HERMES.md do not create it; it would shadow AGENTS.md.
.hermes/skills synchronized deployment copy.
AGENTS.md thin dispatcher and pointer table.
Detailed governance one source in separate documents.
Standard: Single AGENTS.md instruction → pointer resolution → canonical policy → Hermes execution

Verify mirror, instruction, and safety boundaries

Installation is not proof of safe operation. Confirm the mirror exists, prohibited skills are absent, AGENTS.md exposes the expected pointers, and the user has reviewed trust and context settings. Preserve synchronization and validation results as operational evidence.

When a skill is missing, inspect trust, mirror freshness, and context loading before rewriting prompts or changing models. A stale mirror or truncated instruction remains the root cause.

Review itemIntent
1. Is the root trusted by the user?To verify the precondition of automatic skill loading first.
2. Is .hermes/skills synchronized with its SSOT?To prevent stale mirrors from running outdated skills.
3. Does HERMES.md avoid shadowing AGENTS.md?To keep a single source of truth for the instruction file.
4. Are there no context-truncation or synchronization failures?To finish acceptance in a clean state with no warnings.
Standard: Scaffold → trust registration → mirror check → context check → skill call → audit evidence
Self-check
  1. When is the .hermes/skills mirror refreshed, and which check confirms synchronization?
  2. Why should HERMES.md not be created?
  3. Who owns the project trust setting (skills.trusted_project_dirs), and why must the repository not change it?
  4. If a context-truncation warning appears, what must be done before delivery?

Setup procedure and verification commands

The repository never changes trust settings for the user. Explicitly trust the project root in Hermes settings, then verify the synchronized .hermes/skills/ mirror and a thin AGENTS.md.

# User-owned configuration
hermes config set context_file_max_chars 100000
# Add the project root to skills.trusted_project_dirs in user configuration.
# Do not commit user configuration or create HERMES.md.

Troubleshooting: check load order before symptoms

If skills are absent, check the trusted path and mirror. If rules are missing, check AGENTS.md size and pointers. If instructions conflict, first check for HERMES.md.

SymptomFirst check
Skill unavailabletrusted_project_dirs and .hermes/skills mirror
Rule missingthin AGENTS.md and its pointer targets
Conflicting instructionremove HERMES.md; retain AGENTS.md as SSOT
