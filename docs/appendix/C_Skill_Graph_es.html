Referencia C

Grafo de Relaciones de Habilidades — Estructura y Operación

Cuando las habilidades superan la decena, "qué habilidad presupone qué" desaparece de la memoria organizacional. Este documento consolida en un solo capítulo la estructura concreta del grafo de relaciones de habilidades presentado en el Capítulo 10 §2 — fuentes de datos, esquema, vocabulario de relaciones, pipeline de generación, validación y flujo de trabajo operativo.

Fuente: ai-workspace-standards ADR-0060 Skill Relationship Graph as Generated Projection (Enmiendas 1–6) · ADR-0061 Decision Record Standard · scripts/generate-skill-graph.ts v1.7.1

Qué Cubre Este Apéndice
  • Por qué el grafo es una "proyección regenerada constantemente", no un almacén primario
  • Las cinco fuentes de datos de las que se derivan las relaciones, y su prioridad
  • El esquema de nodos/aristas y el vocabulario de diez relaciones tipificadas
  • El modelo de tres capas explícito/experimental/proyección y la regla de 90 días
  • El pipeline de generación/verificación/sincronización y el procedimiento para añadir una relación

Resumen — Por Qué un Grafo

Si las relaciones entre habilidades, agentes y ADR ("esta habilidad debe ejecutarse antes que aquella", "este agente usa esa habilidad") se guardan como texto libre, inevitablemente ocurren tres cosas. Primero, la fuente cambia pero la prosa permanece, así que envejece. Segundo, las relaciones se dispersan entre archivos y se vuelven inbuscables. Tercero, salvo que un humano cure la lista, nada queda verificado.

El grafo de relaciones de habilidades lo resuelve derivando en lugar de escribir. Las fuentes de las relaciones son datos estructurados que ya existen (frontmatter de SKILL.md, archivos de agentes, manifiestos de variant), y el grafo es su proyección. Siempre puede borrar los archivos del grafo — volver a ejecutar el generador los hace nacer de nuevo exactamente igual. Por eso ADR-0060 fija el principio con el nombre Generated Projection.

Fuentes de Datos y Prioridad

El generador escanea las siguientes fuentes en orden de prioridad. Las primeras son más explícitamente intencionales; las últimas, derivaciones más implícitas.

  1. Frontmatter de SKILL.md — prerequisites (habilidades predecesoras obligatorias) y relates_to tipificado (vocabulario de relación + objetivo + nota opcional). La fuente más explícita.
  2. required_skills de los archivos de agentes — produce relaciones used_by agente → habilidad.
  3. skill_manifest de variant.json — el manifiesto de qué habilidades asocia una variante a qué agentes y fases. Fuente de las relaciones phase.
  4. Referencias entre comillas invertidas en la prosa — un documento que menciona una habilidad por su nombre exacto entre backticks produce una arista references (solo coincidencia exacta, para evitar falsos positivos).
  5. docs/skill-graph.overrides.json — vía de escape para añadir relaciones no derivables de las fuentes anteriores, o suprimir las auto-derivadas. También admite overrides por ámbito.

Las aristas provenientes del frontmatter llevan provenance: {file, field, index?}. Rastrear "por qué existe esta relación" siempre lleva de vuelta a un campo concreto de un archivo fuente concreto.

Esquema de Nodos y Aristas

Los artefactos confirmados del grafo son dos — el docs/skill-graph.json legible por máquina y la tabla de relaciones legible por humanos docs/skill-graph.md. La estructura JSON de nivel superior es {version, nodes[], edges[]}.

{
  "version": "1.7",
  "nodes": [
    { "id": "handbook", "type": "skill", "layer": "common" },
    { "id": "handbook-reviewer", "type": "agent", "layer": "common" },
    { "id": "ADR-0060", "type": "adr", "layer": "L0" }
  ],
  "edges": [
    {
      "from": "handbook",
      "to": "research",
      "type": "requires",
      "provenance": {
        "file": "skills/handbook/SKILL.md",
        "field": "prerequisites",
        "index": 0
      }
    },
    {
      "from": "handbook-reviewer",
      "to": "handbook",
      "type": "used_by"
    }
  ]
}

Los nodos llevan id, type y layer. Los tipos incluyen skill, agent, adr, decision, procedure y output_type; las capas son L0 (raíz del workspace), common (plantilla común), variant:<name> y L3 (proyecto individual).

Tipos de Aristas en Detalle

El vocabulario completo de relaciones crecido a lo largo de las Enmiendas 1–6, con dirección, simetría y fuente. Todas las aristas son consultivas (advisory) — informan el enrutamiento y la planificación, pero nunca bloquean la ejecución de forma absoluta.

El error más común es confundir la dirección de requires. A requires B significa "necesitas B antes de A", no "A produce B". Si la dirección no está clara, comprueba el frontmatter fuente mediante el campo provenance.

El Modelo de Relaciones de Tres Capas

En el mismo grafo coexisten tres clases de relaciones. Sus vidas útiles y niveles de confianza difieren, por lo que se tratan como capas distintas.

  • L-A Explícito — relates_to tipificado en el frontmatter. Permanente por intención, la fuente primaria del grafo.
  • L-B Experimental — relaciones en el archivo de overrides. reason y since son obligatorios, y una advertencia de obsolescencia se activa tras 90 días. Es la sala de espera de las relaciones "que probablemente pertenecen al grafo pero aún se observan antes de entrar al frontmatter".
  • L-C Proyección — el grafo generado en sí. Siempre regenerado, con una verificación de determinismo que confirma que "misma entrada → misma salida" se mantiene.

Cuando una relación experimental se considera estable, se mueve al frontmatter para promoverla a L-A. Para eliminar una L-A, bórrala del frontmatter — no existe ninguna vía que edite los archivos del grafo directamente.

Pipeline de Generación

El grafo se engarza con el pipeline en cuatro puntos.

  • scripts/generate-skill-graph.ts — escanea las fuentes y produce skill-graph.json/.md. --scope <name> crea un grafo de ámbito por plantilla (común + cada variante, 14 ámbitos en total).
  • scripts/verify-skill-graph.ts — verifica el grafo confirmado contra sus fuentes (deriva) y las invariantes.
  • dev-sync.ts paso 4.65 — regenera y comprueba la deriva de todos los grafos de ámbito en cada /sync. Mantener el grafo al día está integrado en el flujo de commits.
  • new-project.ts paso 7.6 — genera el docs/skill-graph.json del proyecto en el momento del scaffolding, sin esperar al primer /sync.

Un grafo de ámbito es una vista acotada del grafo L0 unificado. Como una plantilla de variante envía su propio grafo de ámbito, un proyecto nacido de ella empieza desde el primer día con un mapa de relaciones relevante para sí mismo.

Estrategias Declarativa vs Inferencial

Hay dos estrategias para de dónde salen las relaciones.

  • Declarativa — las relaciones se declaran directamente en el frontmatter (Enmienda 3). La intención es explícita y la validación simple, pero depende de la disciplina de los autores de habilidades.
  • Inferencial — las relaciones se derivan de datos estructurados existentes (Enmienda 4, precedente co-newbiz), basándose en la adyacencia de fases de los esquemas de procedimiento o en predicados de reglas. La cobertura crece sin añadir ningún frontmatter.

El experimento comparativo (scripts/experiments/infer-graph-from-phases.ts, de solo lectura) concluyó con un veredicto dividido — la inferencia funciona bien en áreas ricas en esquemas de procedimiento, pero la estrategia declarativa gana en el resto. No se adoptó ningún nuevo modo de extracción predeterminado; ambos coexisten: derivar donde hay esquemas, declarar para el resto.

Cadena de Decisión y Validación

La razón por la que el grafo abraza los ADR y los registros de decisión es poner "relaciones" y "fundamento" en un solo mapa. La cadena de decisión de ADR-0061 — Agent, Skill, Knowledge, Evidence, Rule, Decision — se valida de forma fail-closed mediante scripts/validate-decisions.ts.

  • Presencia del frontmatter obligatorio en los registros de decisión y de referencias al libro de evidencias (evidence ledger)
  • Formato de los ID de reglas y resolubilidad de las referencias a habilidades
  • Regla de acoplamiento de propagación — una habilidad publicada en L1 no debe relacionarse con objetivos ausentes de L1. De lo contrario, cada copia descendiente crece con aristas colgantes (dangling edges).

Mediante las aristas supersedes y cites_skill, el grafo muestra "sobre qué habilidades se tomó esta decisión y qué documentos sucedió". Es un dispositivo estructural que impide que las relaciones se acumulen sin fundamento.

Flujo de Trabajo Práctico — Añadir una Relación

El procedimiento mínimo cuando realmente se añade una relación.

  1. Declarar — escribe la relación en el frontmatter de SKILL.md de la habilidad objetivo: 
    relates_to:
  - { skill: research, type: requires }
  - { skill: pdf-export, type: enables, note: "produces layout spec" }
  2. Validar — ejecuta bun scripts/validate-skills.ts (verificación de forma de relaciones) y luego bun scripts/generate-skill-graph.ts.
  3. Confirmar — ejecuta bun scripts/verify-skill-graph.ts para confirmar que no hay deriva, y comprueba visualmente la tabla de relaciones de la habilidad en docs/skill-graph.md.
  4. Confirmar (commit) — /sync realiza la regeneración y verificación de todos los ámbitos en el paso 4.65, así que solo asegúrate de no haber editado los archivos del grafo directamente antes del commit.

Para una relación de la que aún no estás seguro, escríbela en el archivo de overrides en lugar del frontmatter. Dejar reason y since hace que el sistema pregunte "¿aún observando?" a los 90 días.

Hoja de Ruta

La visión Phase 2+ de ADR-0060 es la siguiente; ninguna está implementada todavía.

  • Máquina de estados del ciclo de vida — rastrear las transiciones draft/active/retired de las habilidades como estado del nodo del grafo
  • Versionado y migración — herramientas para moverse entre versiones del esquema del grafo
  • Inteligencia del grafo — sugerencias de enrutamiento basadas en relaciones y composición automática de paquetes de contexto
  • Instantáneas de pista de auditoría — instantáneas puntuales del grafo para consultar el historial de relaciones

La clave es que el diseño actual no bloquea estas extensiones. Como el grafo es una proyección, no un almacén primario, añadir consumidores o estado a los nodos solo requiere cambiar las fuentes y el generador.
