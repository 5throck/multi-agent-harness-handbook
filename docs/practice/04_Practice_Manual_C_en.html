Ch.4 §1-C

Sub-Agent Usage Details — Codex-Focused

A detailed document, limited to the Codex family, covering how to perform, sequence, and scale to automation the work that corresponds to "subagents" in Codex CLI / Codex Desktop App  |  Shared concepts are covered in the Ch.4 §1 reference, the Claude family in Ch.4 §1-A, and the Antigravity family in Ch.4 §1-B.

Target versionCodex CLI / Codex Desktop App — see §1-A for the Claude counterpart, §1-B for Antigravity
Reference doc URLdevelopers.openai.com/codex
Docs collected on2026-09-12
How to check versionCodex CLI: codex --version · Codex Desktop App: the app's About screen
Codex has no native subagent tool. That's why this document uses the term "role" throughout instead of "subagent" — a subagent as described in the Claude/Antigravity documents is an independent entity with its own process and context window, but a role the PM "takes on" in Codex is just a shift in thinking that continues within the same session. See Tool Comparison §3 for the full background.

1. Defining Roles

Codex CLI and Codex Desktop App require no definition file to be created in advance. Instead, the PM reads the existing definition file for each specialist agent from agents/<name>.md at the workspace root when the session starts, and uses it as role context. The format resembles the Claude family's .claude/agents/*.md, but the purpose differs — in Claude it's an "executable definition" referenced by subagent_type at invocation time, whereas in Codex it's material the PM loads for reference, to think like that role.

Codex Desktop App agents/<name>.md — Read-Only Role Context

In Codex Desktop App, the PM loads a file like the workspace's agents/reviewer.md directly mid-conversation and declares "I will work the way this role defines." The file itself may share the same frontmatter format as the Claude family, but Codex does not spawn it as an executable subagent — it's just a referenced document. Codex CLI uses the exact same file in the exact same way — there is no difference in how roles are defined between the two.

Contents of agents/reviewer.md (may share
the same format as the Claude version):
---
name: reviewer
description: Reviews text files for typos
  and logical gaps.
---

You are acting as a reviewer. Read the
given file and report a list of improvements.

Codex CLI — Same agents/<name>.md as Codex Desktop App

References the exact same agents/<name>.md file used in Codex Desktop App. There is no difference in role-definition method between the Desktop App and the CLI.

Comparison itemClaude family (.claude/agents)Codex family (agents/<name>.md)
File location .claude/agents/*.md (platform-specific folder) agents/<name>.md (workspace-common folder — no platform-specific copy)
Purpose Executable subagent definition — invoked via subagent_type Read-only role context — the PM references it to think like that role
Invocation mechanism Agent/Task tool None — the PM simply reads the file and declares "I will perform this role"

2. Performing/Switching Roles

Neither Codex CLI nor Codex Desktop App spawns a subagent with its own context. Instead, the PM changes roles within the same session — stepping through work in order, e.g. "analyze this file as the designer role now, then write the code as the implementer role next."

Codex Desktop App — Sequential Role-Switching by the PM

When you ask the PM in Codex Desktop App for work that needs multiple areas of expertise, the PM loads the relevant role's definition file at each stage, works from that role's perspective, then moves on to the next role. Multiple roles never exist in parallel; each stage picks up the previous stage's results. Codex CLI runs the exact same sequential-switching approach — making the same request in a terminal instead of a chat window is handled identically.

User: "Review the session-expiry logic in
src/auth/login.ts and fix any bugs you find."

PM's internal progression (sequential,
within one session):
1. Loads agents/reviewer.md as role context
   to review the code
2. Summarizes the issues found
3. Switches role to agents/automation-
   engineer.md to implement the fix

Codex CLI — Same Sequential Switching as Codex Desktop App

The exact same sequential role-switching approach as Codex Desktop App. Making the same natural-language request in a terminal is handled the same way, with the PM changing roles as it works.

Copying the Claude/Antigravity examples verbatim and saying "Codex invokes the reviewer subagent" for this exercise would be inaccurate. The Codex "intro exercise" isn't about invoking a subagent — it's about giving the PM work that needs several roles and observing it switch roles sequentially.

3. Parallel Execution

The Codex family does not support within-session parallel execution. Every role switch happens in order, inside a single linear session.

Codex has nothing corresponding to Claude's Agent Teams or Antigravity's Agent Manager/dynamic subagents — no "within-session parallelism." To run multiple things at once, you have to open several terminals (or windows) and separate the sessions themselves — this is closer to placing several independent sessions side by side than to parallel execution proper.

Codex Desktop App — Cross-Session Parallelism via Multiple Windows

To work on different tasks at the same time in Codex Desktop App, open several app windows (or tabs), each as a separate session. As long as multiple sessions don't touch the same file at once, there's no conflict. Codex CLI implements cross-session parallelism the same way, by opening multiple terminals.

Codex CLI — Cross-Session Parallelism via Multiple Terminals

The exact same principle as Codex Desktop App. If one codex session is refactoring the API layer while another writes tests, they won't conflict as long as they don't touch the same files.

ItemCodex Desktop AppCodex CLI
Parallel execution unit No within-session parallelism / cross-session parallelism via multiple windows only No within-session parallelism / cross-session parallelism via multiple terminals only

4. Automation/Hooks

In the Codex family, automation and hooks show no difference between the Desktop App and CLI — neither runs the workspace hook suite at all.

Codex Desktop App — No Hooks, Self-Enforced via the Prompt

Codex Desktop App has nothing corresponding to Claude Code's auto-firing events like PostToolUse/TeammateIdle/TaskCompleted. Governance — running audit scripts, enforcing gate rules — instead relies on the PM recognizing and carrying out the instructions in CODEX.md itself, every session (prompt self-enforcement). Codex CLI is identical — there's no hook mechanism at all.

Codex CLI — Same Lack of Hooks as Codex Desktop App

Exactly the same as Codex Desktop App. The PM must recognize and carry out instructions written in CODEX.md itself within the session (e.g., "always run bun scripts/audit.ts after modifying a file") — there's no mechanism that fires automatically in response to an event.

# Example instruction in CODEX.md (not
# auto-fired — the PM recognizes and runs
# it directly):
# "Always run bun scripts/audit.ts after
#  writing/editing a file."

bun scripts/audit.ts
When following this handbook's multi-agent exercises with Codex, always read "invoke a subagent" as "the PM loads that role's definition file and performs the role," and "the hook fires automatically" as "the PM recognizes and carries out the CODEX.md instructions itself."
