Chapter 4 §2-C · Codex-Focused Multi-Agent Team Practice

The Principle Behind This Whole Track — every scenario below first writes the role as a tool-neutral AGENTS.md specification, and on Codex that same specification is not "implemented" as a pre-defined subagent. Instead, the identical specification is copied into the workspace-common folder agents/<name>.md, and during the session the PM loads that file as read-only role context to "think as that role" and perform the work directly. The core goal of this practice is to confirm by hand that the definition stays single while only the execution mechanics differ by tool — see Ch.4 §2-A and Ch.4 §2-B for the Claude/Antigravity equivalents.
Codex has no tool for spawning subagents at all. Everywhere this document says "call a role," it means "the PM loads that role's definition file and performs the role", and "run in parallel" means separate sessions spread across multiple terminals/windows, not something happening inside one session. Keep this distinction in mind as you work through the scenarios below.

Setup: Installing the Required Tools

The practice below focuses on the Codex Desktop App and Codex CLI. If you don't have these tools locally yet, the environment-setup automation bundled with this handbook — the setup guide — automatically installs exactly what this chapter's practice needs. Follow the instructions to download and run the script locally.

📦 Before You Run the Script

Read the pre-install checklist first. It lists these prerequisites.

  • An active OpenAI account with Codex access (subscription/account-based plan or an API key — depends on organizational policy)
  • A GitHub account you can run gh auth login with
  • At least 5GB of free disk space
  • Administrator (admin) or sudo privileges
If you don't have a GitHub account yet
① Go to github.com/signup in your browser.
② Enter your email address, password, and username — the username becomes part of your repository URL (github.com/<username>/...), so pick it carefully.
③ Pass the puzzle/code verification that prevents automated signups.
④ Open the verification email sent to the address you signed up with and complete email verification — skipping this can later block gh auth login or repository creation.
⑤ The Free plan is enough — this handbook's practice and PR exercises don't need a paid plan.
Once signup is done, the GitHub CLI (gh) is installed alongside the setup script above, and the gh auth login command below connects your terminal to that account. 
gh auth login
# Follow the prompts: choose GitHub.com → HTTPS → Login with a web browser (recommended)
# When the browser opens, log in with the account you just created and confirm the auth code

Installing on Windows

Since this handbook's path notation follows Windows conventions, Windows users should clone the 5throck/setup repository with the command below, then run PowerShell as Administrator for the commands that follow.

How to Open PowerShell as Administrator
① Open the Start menu and search for PowerShell.
② Right-click "Windows PowerShell" in the search results.
③ Select "Run as administrator" from the menu.
④ Click "Yes" when the User Account Control (UAC) prompt appears.
If the title bar shows something like Administrator: Windows PowerShell, you opened it correctly. Some steps, like winget installs, can error out or silently skip without admin rights. 
git clone https://github.com/5throck/setup.git
cd ./setup
powershell -ExecutionPolicy Bypass -File .\setup-windows.ps1
# Optional flags: -WSL2, -WezTerm, -Docker, -Force (reinstall tools even if already present)

After the script finishes, fully close and reopen your terminal so the PATH changes take effect.

Installing on macOS / Linux

Clone the 5throck/setup repository with the command below. Run setup-mac.sh on macOS and setup-linux.sh on Linux; both support the optional --wezterm and --docker flags.

git clone https://github.com/5throck/setup.git

# macOS
cd ./setup && bash setup-mac.sh

# Linux
cd ./setup && bash setup-linux.sh

Verifying the Installation

Regardless of OS, running setup-common.ts with bun prints a checklist table showing the installation status. Once every item shows ✅, you're ready to start the practice below.

cd ./setup && bun setup-common.ts

Among the tools this project installs, the ones directly relevant to this chapter's practice are: the Codex Desktop App, codex (Codex CLI), plus bun (needed to reference the workspace-common agents/*.md files) and gh (GitHub CLI), used in later chapters.

If something goes wrong during installation, logs are left under %USERPROFILE%\workshop-setup-logs\ on Windows. Check that log first when troubleshooting.
● Beginner Getting Started The first step: load one role definition and have the Codex Desktop App PM perform that role
G-1 Beginner Read a Role Definition and Let the PM Perform It
A developer new to the harness creates a fresh, practice-only empty folder called harness-lab/, first writes a reviewer role as a tool-neutral AGENTS.md specification, then copies that same content into agents/reviewer.md. On the Codex Desktop App, they observe the PM load this file as read-only role context and "think like a reviewer" to perform the review directly. This folder is for practice only, so it stays separate from other project files.
Elements Used
AGENTS.md (Ch.2) Defining Roles (Codex) Performing/Switching Roles (Codex)
Step by Step
  1. ① Create the Practice Folder and Enter It

    Create a new harness-lab folder under your current directory and move into it. Every command afterward runs inside this folder.

    mkdir -p harness-lab
cd harness-lab
  2. ② Write the Common Role Specification — AGENTS.md

    Write the reviewer role as plain text with no tool-specific phrasing, so it reads the same whether opened in Claude, Antigravity, Codex, or any other tool that supports the AGENTS.md standard. This single file becomes the sole source of truth for "what this role does." On macOS/Linux/Git Bash, use the command below as-is.

    cat > AGENTS.md << 'EOF'
## Agent: reviewer

Role: Review text files for typos, logical gaps, and areas for improvement.
Input: Path to the text file to review
Output: A list of typos, logical gaps, and improvement suggestions
Permissions: Read-only — never modifies the file directly.
EOF

    On Windows PowerShell, the cat command itself is an alias for Get-Content, usable for reading files. However, the << 'EOF' heredoc syntax for writing multiple lines directly isn't supported, so build the same content as a quoted here-string (@'...'@) and write it with Set-Content.

    @'
## Agent: reviewer

Role: Review text files for typos, logical gaps, and areas for improvement.
Input: Path to the text file to review
Output: A list of typos, logical gaps, and improvement suggestions
Permissions: Read-only — never modifies the file directly.
'@ | Set-Content AGENTS.md
  3. ③ Move It Into the Workspace-Common Role File — agents/reviewer.md

    Instead of a platform-specific folder like .claude/agents/, Codex references agents/<name>.md at the workspace root as read-only role context. Copy the AGENTS.md specification verbatim into frontmatter format.

    mkdir -p agents
cat > agents/reviewer.md << 'EOF'
---
name: reviewer
description: Reviews text files for typos, logical gaps, and areas for improvement
tools: Read, Grep
tier:
  codex: medium
---

## Role
Review text files for typos, logical gaps, and areas for improvement.

## Input
Path to the text file to review

## Output
A list of typos, logical gaps, and improvement suggestions

## Permissions
Read-only — never modifies the file directly.
EOF
Codex Desktop App — The PM Loads agents/reviewer.md as Role Context and Reviews Directly

Don't pre-create files in a terminal or separate editor. Follow the two steps below exactly — every gray code box can be pasted as-is via its "Copy" button.

  1. ① Open the Project in the Codex Desktop App

    Launch the Codex Desktop App and open the harness-lab/ folder you just created as a project.

  2. ② Create the File to Review + Request the Review via Role Context — Paste the Text Below into the Chat and Send 
    Create notes.txt with the text "This project is very good. This is very good.", then load the reviewer role defined in agents/reviewer.md as read-only context and review notes.txt according to that role.
    The Codex Desktop App's PM does not spawn a separate subagent. Instead, it opens agents/reviewer.md with the Read tool, loads the "role/input/output/permissions" specification into context, and shapes its subsequent response around that role's constraints (read-only, reporting only typos/logical gaps/improvements) — it must also uphold "never actually modify the file" on its own. Instead of a subagent-spawn sequence, the screen shows the PM's tool call reading agents/reviewer.md followed by the review result, all as one continuous session.

Identical on Codex CLI — run codex in a terminal and paste the same sentence from step ② into the chat; the CLI reads agents/reviewer.md the same way and responds in that role. There is no difference between the Codex Desktop App and CLI in how roles are defined and performed — neither has any hooks that fire automatically either.

Verifying the Result — confirm the screen actually shows the PM's tool call reading agents/reviewer.md. The final response should be a list broken into typos, logical gaps, and improvements — if the PM responds with something like "I've fixed it" or edits notes.txt directly, it has failed to honor the "read-only" permission constraint in agents/reviewer.md on its own (Codex has no enforcement mechanism like Claude's tools restriction — the role document's guidance is upheld voluntarily by the PM).
Common Failure — if the PM reviews notes.txt directly without first reading agents/reviewer.md, the step ② request was probably missing the phrase "load the reviewer role defined in agents/reviewer.md as read-only context." Unlike Claude's explicit "subagent call," Codex will simply respond as its default PM persona unless you explicitly ask it to reference the role file.
● Intermediate Daily Workflow A practical pattern where the PM switches, in order, between the writer role and the reviewer role within a single session
D-1 Intermediate writer → reviewer Two-Stage Sequential Role Switching
Having finished G-1, a practitioner in the same harness-lab/ folder first specifies a second role, writer, in AGENTS.md and agents/writer.md the same way as G-1. They observe the Codex PM first draft the text as the writer role, then switch — within the same session — to the reviewer role to critique the result, keeping the order intact. The key difference from Claude/Antigravity is that both roles are just "performed" sequentially by the same PM — no separate instance is ever spawned.

Claude/Antigravity spawn a separate instance for each of writer.md/reviewer.md, but Codex has a single PM session "performing" each role in turn — all four boxes are the same PM.

Elements Used
AGENTS.md (Ch.2) Defining Roles (Codex) Performing/Switching Roles (Codex)
Step by Step
  1. Add to the Common Role Specification — Append a writer Entry to AGENTS.md

    Append the writer role to the same AGENTS.md from G-1. Leave the reviewer entry alone and add only the content below. On macOS/Linux/Git Bash, use the command below as-is.

    cat >> AGENTS.md << 'EOF'

## Agent: writer

Role: Write a short 3-5 sentence draft on a given topic.
Input: Topic, path to save the file
Output: A draft text file
Permissions: Write allowed — saves only to the specified file.
handoff_to: reviewer (hands off to review once the draft is complete)
EOF

    On Windows PowerShell, append the here-string with Add-Content (using Set-Content instead would overwrite the file, so Add-Content is required to avoid wiping out the reviewer entry).

    @'

## Agent: writer

Role: Write a short 3-5 sentence draft on a given topic.
Input: Topic, path to save the file
Output: A draft text file
Permissions: Write allowed — saves only to the specified file.
handoff_to: reviewer (hands off to review once the draft is complete)
'@ | Add-Content AGENTS.md
  2. Add the Workspace-Common Role File — agents/writer.md 
    cat > agents/writer.md << 'EOF'
---
name: writer
description: Writes a short 3-5 sentence draft on a given topic
tools: Write, Read
tier:
  codex: medium
---

## Role
Write a short 3-5 sentence draft on a given topic.

## Input
Topic, path to save the file

## Output
A draft text file

## Permissions
Write allowed — saves only to the specified file.

## handoff_to
reviewer (hands off to review once the draft is complete)
EOF
Codex Desktop App — The Same PM Switches From the writer Role to the reviewer Role

As in G-1, don't prepare files ahead of time. Continue in the same harness-lab/ chat left open from G-1.

  1. ① Request the writer → reviewer Sequential Switch — Paste the Text Below into the Chat and Send 
    Load the writer role defined in agents/writer.md as read-only context, and write a draft on 'the benefits of remote work' into draft.txt in that role. Once that's done, switch to the reviewer role defined in agents/reviewer.md and review draft.txt. Do these two steps in order.
    The PM first reads agents/writer.md, loads the writer role's constraints (write allowed, draft only) into context, and generates draft.txt. Only after that finishes does it newly read agents/reviewer.md and "put on" the read-only reviewer role this time to review draft.txt — no separate instance is spawned; instead, only which role file the same session/same PM references changes. Coordinating the order between the two roles is also this PM's own job.
Since Codex has no parallel spawning at all, a request like "run writer and reviewer at the same time" simply isn't valid — the PM can only perform one role at a time within a single session anyway. Dependent work is therefore always sequential by nature, so results come out sequential even without explicitly saying "do these two steps in order" as in ①, but it's still good practice to spell out exactly which order and which roles to pass through.
Verifying the Result — the chat should show tool calls in this order: reading agents/writer.md → writing draft.txt → reading agents/reviewer.md → review result. After completion, also open harness-lab/draft.txt to confirm the draft was actually saved.

Identical on Codex CLI — using the same agents/writer.md/agents/reviewer.md, pasting the sentence from ① into a terminal switches through the same sequence.

D-2 Intermediate Observing How the Roles and Order Called Vary by Request
This scenario lets you see, on Codex too, the "dynamic team composition" and "varied workflow combinations" covered in Ch.2 §4b. Leave the agents/writer.md·agents/reviewer.md from D-1 untouched and vary only the nature of the request, observing which roles the same PM actually references, how many times, and in what order — the key point is that the role definition files are never re-created. Since Codex has no parallel fan-out, a request like "review from two perspectives at the same time" still ends up being handled by the PM one perspective at a time, sequentially.

Elements Used
Dynamic Team Composition and Varied Workflows
Codex Desktop App — Same Role Roster, Three Different Requests

Continue in the same chat from D-1. Pay attention each time to which role file the PM reads and how many times it switches, as shown in the tool-call output on screen.

  1. ① A Simple Request — Only One reviewer-Role Pass Needed 
    Just scan draft.txt for typos.
    The PM decides there's no need to switch into the writer role for this request and only references agents/reviewer.md, then stops. This is the simplest example showing that even when the same role roster (writer+reviewer) is defined, the PM decides case-by-case, per request, which role to actually "perform."
  2. ② A Compound Request — Combining the writer Role and the reviewer Role Sequentially From Two Angles 
    Write a new draft in draft2.txt on the topic 'the four-day workweek.' Once the draft is done, review it once from a grammar angle and once from a logic angle. Since Codex doesn't support concurrent execution, go through one angle at a time in sequence.
    This time the PM references agents/writer.md to write the draft, then switches to agents/reviewer.md and performs it twice sequentially under different instructions — once as a "grammar angle" and once as a "logic angle." Unlike Claude/Antigravity's "fan-out" (simultaneous parallel review), on Codex this always shows up as a sequential 2x repetition — the same two roles still produce a workflow shape completely different from ①, just like the Claude/Antigravity case.
Comparing ① and ② side by side makes clear that "the role roster (which roles are defined under agents/)" and "the composition actually used for this task (which role gets referenced how many times, in what order)" are two different layers. The former is fixed in the workspace ahead of time, but the latter is decided fresh by the PM for every request — with the constraint that on Codex it is always decided sequentially.

Identical on Codex CLI — using the same agents/writer.md/agents/reviewer.md, pasting the sentences from ①② into a terminal behaves the same way.

Common Failure — even when the PM handles ② sequentially under the hood, asking to "review them at the same time" can make it report the results lumped together as if done simultaneously. On Codex, explicit wording like "in order" or "one angle at a time" keeps the result predictable.

● Advanced Power User Cross-session parallel operation — running the writer role and the reviewer role against two independent files at once, in separate terminals/windows
P-1 Advanced Splitting Independent Work Across Windows — Cross-Session Parallelism
Having finished through D-1, an experienced user wants to work on two independent tasks that don't depend on each other (drafting topic-a.txt and topic-b.txt) at the same time. Since Codex has no feature for spawning teammates in parallel within a single session, they open two separate terminal windows (or Codex CLI sessions) targeting the same harness-lab/ folder and hand off each task independently — the unit of "parallel" here is the session itself, not a teammate.
Elements Used
Parallel Execution — Cross-Session Parallelism (Codex)
Codex CLI — Two Terminals, Two Sessions

Open two terminal windows targeting the same harness-lab/ folder (or use a split window via tmux or similar — Codex CLI itself has no built-in support like Claude Code's teammateMode: "tmux", so you set up the terminal multiplexer yourself).

  1. ① First Terminal — Draft topic-a.txt as the writer Role

    In the first terminal, move into harness-lab/, run codex, and paste the sentence below.

    cd harness-lab
codex
    As the writer role defined in agents/writer.md, write a draft on 'remote work' into topic-a.txt. Once done, switch to the reviewer role in agents/reviewer.md and review it too.
  2. ② Second Terminal — Draft topic-b.txt as the writer Role, at the Same Time

    Open a second terminal separate from ①, move into the same harness-lab/, and run codex again. This session is completely independent from ①'s — it merely looks at the same workspace, sharing neither conversation context nor progress state.

    cd harness-lab
codex
    As the writer role defined in agents/writer.md, write a draft on 'the four-day workweek' into topic-b.txt. Once done, switch to the reviewer role in agents/reviewer.md and review it too.
Because the two sessions run as separate processes, they genuinely proceed at the same time — but this is different in nature from Claude Agent Teams' parallelism, where a single orchestrator coordinates two teammates through a shared task list. Codex's two sessions have no awareness of each other, no shared task list, and no direct session-to-session communication channel like SendMessage. If both sessions touch the same file at once (for example, both trying to edit AGENTS.md), a plain filesystem-level conflict can occur — assigning completely separate target files is just as important a safety practice here as it is for Claude/Antigravity.
If you want to watch both sessions' progress at a glance, splitting the windows side by side with a terminal multiplexer like WezTerm or tmux helps — this is a matter of terminal-environment setup, not a Codex feature itself.
Common Failure — if both sessions try to modify agents/writer.md itself (for example, sending "change the tier" requests from both at once), a write race can occur and one side's change may get overwritten. When running in parallel, have each session touch only its own target file (topic-a.txt/topic-b.txt), and avoid requests that change the role definition file itself in a parallel session.

P-2 Advanced Building Cost Intuition by Comparing Model Tiers
This scenario lets you feel, firsthand and before being told the numbers, what real difference the model tiers (high/medium/low) covered in detail in Chapter 8 make on Codex. Reference the same reviewer role three times, changing only the model, and visually compare response speed and result quality. Note that Codex's model tier names differ from the Claude family's (haiku/sonnet/opus).
Elements Used
Model Tiers (Ch.5)
Codex Model Tier Comparison Chart
Codex Desktop App — Same File, Requesting a Review at Three Model Tiers

Prepare a passage with a logical gap, slightly more complex than G-1's notes.txt. Paste the text below into the chat as-is.

  1. ① Prepare the File to Review 
    Create argument.txt with the following text: "Remote work is always more productive than office work. This is because people who work remotely say remote work is good. Therefore, every company should be fully remote."
  2. ② Review at the low Tier (gpt-5.6-luna)

    Paste the text below into the chat as-is. The PM changes the tier.codex field in agents/reviewer.md to low and then reviews in that role.

    Change the tier.codex field in agents/reviewer.md to low. Then review argument.txt in that reviewer role.
  3. ③ Repeat the Same Request at the medium Tier (gpt-5.6-terra)

    Change tier.codex to medium the same way and review again. Compare against the low result to see whether it pinpoints a logical gap like circular reasoning accurately.

    Change the tier.codex field in agents/reviewer.md to medium. Then review argument.txt in that reviewer role.
  4. ④ Repeat the Same Request at the high Tier (gpt-5.6-sol)

    Change tier.codex to high the same way and review again. Note how response time and depth of critique differ from ②③.

    Change the tier.codex field in agents/reviewer.md to high. Then review argument.txt in that reviewer role.
For a simple typo check the three tiers barely differ, but for work like this — "spotting a flaw in an argument's structure" — the lower the tier, the more clearly it tends to miss calling out circular reasoning as circular reasoning and instead comment only on surface-level wording. Conversely, gpt-5.6-luna responds fastest of the three — going through the speed-versus-depth trade-off yourself makes much clearer why Chapter 5's principle exists: "heavier judgment calls for a higher tier, more routine tasks call for a lower one."
You can simply tell the Codex Desktop App "change the tier.codex field" each time — no need to open the definition file yourself; the PM edits agents/reviewer.md on its own, then reviews in that role.
Common Failure — if the tier.codex field gets a value that doesn't exist (a mistake like using Claude-family names such as haiku/sonnet/opus, for example), the PM may silently ignore it and fall back to a default tier. After finishing ②③④, open agents/reviewer.md yourself and confirm the tier.codex value exactly matches the intended one — low/medium/high.

Wrapping Up the Practice

Once you've completed all five scenarios, decide what to do with the harness-lab/ folder. Since the next chapter (Chapter 5) uses a new practice folder, you don't have to keep it, but if you'd like to compare the AGENTS.md/agents/*.md definitions you built so far, it's worth reviewing them once before deleting.

🧹 Cleaning Up the harness-lab Folder

If you no longer need it, delete the whole folder. On macOS/Linux/Git Bash, use the command below as-is.

cd ..
rm -rf harness-lab

On Windows PowerShell:

cd ..
Remove-Item -Recurse -Force harness-lab
If You'd Like to Keep It — instead of deleting the folder, you can also just leave a local commit with git init && git add -A && git commit -m "harness-lab practice record". Keep it as a reference afterward, and feel free to start the next chapter's practice in a separate new folder.
The second Codex CLI session opened in a separate terminal during P-1 will error on its next command if you delete harness-lab/ out from under it. Make sure both sessions are terminated (Ctrl+C or exit) before cleaning up the folder.
