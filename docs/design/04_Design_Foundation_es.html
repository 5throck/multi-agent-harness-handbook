Filosofía de diseño: una pantalla es un contrato para la tarea

Una regla de diseño es un contrato compartido por personas e IA. Si cada pantalla vuelve a decidir color, espacio, tipografía y prioridad de información, la función puede operar pero la experiencia se dispersa.

Un sistema de diseño se parece a un plano de arquitectura: fija materiales y dimensiones antes de construir. Empieza por la tarea, el éxito, el fallo y la evidencia que revisará una persona responsable.

ElementoIntención
Tarea acción que se debe completar
Jerarquía orden de lectura
Restricciones accesibilidad, pantallas estrechas, texto largo y fallos
Estándar: Solicitud → tarea de usuario → patrón estándar → implementación → revisión

Principios: consistencia, claridad y recuperación

Los principios explican cómo decidir; los tokens dan a la decisión un nombre reutilizable. Un token semántico conserva la intención en código, documentación y modo oscuro.

Nombra un rol en lugar de un color bruto o píxeles arbitrarios. Un cambio de marca o accesibilidad actualizará una definición en vez de reparar cada pantalla.

ElementoIntención
Consistencia un significado tiene un tratamiento.
Claridad una acción principal por pantalla.
Accesibilidad el color no es la única señal.
Recuperación confirma o permite cancelar acciones riesgosas.
Estándar: Principio → token semántico → regla de componente → criterio

Práctica

Nombra un rol en lugar de un color bruto o píxeles arbitrarios. Un cambio de marca o accesibilidad actualizará una definición en vez de reparar cada pantalla.

# design-contract.yaml
screen: report-review
primary_task: approve-or-return-a-report
states: [default, loading, empty, error, forbidden]
components:
  - status-panel
  - review-summary
  - primary-action
acceptance:
  - one-primary-action
  - keyboard-reachable
  - semantic-tokens-only

Guías de diseño: espaciado, jerarquía, lenguaje y respuesta

Las guías de diseño son un lenguaje de trabajo para que personas y pantallas completen la misma tarea de modo consistente. El espaciado muestra relaciones; títulos, cuerpo y texto auxiliar crean orden de lectura. El texto declara primero la acción.

Copia reglas existentes para una pantalla nueva y registra solo diferencias necesarias. No añadas espacios arbitrarios, anchos fijos ni etiquetas de botón ambiguas sin razón de revisión.

ElementRule
EspaciadoUsa menos espacio para relaciones más cercanas.
JerarquíaDa tipografía por rol a título, cuerpo y apoyo.
LenguajeExplica acción y resultado antes de adornos.
RespuestaUsa ancho flexible y reflujo por prioridad.
Guide: Tarea → jerarquía → reglas de espacio y texto → revisión adaptable

Sistema de Color y Accesibilidad

Un sistema de color es un contrato de significado, no una colección de paletas. La paleta base solo ofrece escalas; las pantallas usan tokens semánticos como `text`, `surface`, `border`, `action`, `success`, `warning` y `error`. Así, un cambio de marca o modo oscuro no redefine fallo, advertencia y finalización en cada pantalla.

La accesibilidad es una condición de validación del sistema de color. No comuniques éxito, error o selección solo con color: añade texto, iconos, bordes o patrones. Revisa contraste y foco de teclado para texto, iconos, anillos de foco y límites de error en modo claro y oscuro.

LayerPurpose
Paleta baseDefine escalas; la pantalla no la usa directamente.
Token semánticoExpresa el rol de texto, superficie, borde, acción y estado.
Token de componenteDefine estados de botones, campos y avisos.
Revisión de accesibilidadComprueba pistas no cromáticas, contraste y foco.
Standard: Paleta base → tokens semánticos → estados de componente → revisión clara/oscura

Práctica de revisión de estados de color

Pide a la IA usar tokens semánticos y no valores de color directos. Revisa estados normal, hover, focus, disabled y error en una pantalla; después verifica que el estado y la siguiente acción sigan claros sin color.

{
  "color": {
    "brand": { "$value": "#0969da", "$type": "color" },
    "action-primary": { "$value": "{color.brand}", "$type": "color" },
    "status-error": { "$value": "#cf222e", "$type": "color" },
    "focus-ring": { "$value": "{color.action-primary}", "$type": "color" }
  }
}

Sistema de tipografía y fuentes

Las fuentes son infraestructura de interfaz para velocidad de lectura y jerarquía. Separa roles de cuerpo, título, apoyo y código; administra familia, peso, tamaño, altura de línea y espaciado como tokens. Define cobertura de glifos y fallback multilingüe.

El documento debe leerse cuando una fuente web tarda o falla. Revisa fallback del sistema, código monoespaciado, salto de texto largo y tamaños legibles en tablas y botones.

ElementRule
CuerpoMantén tamaño y altura de línea legibles.
TítuloMuestra estructura con tamaño y peso.
CódigoUsa tipo monoespaciado y reglas de salto.
FallbackConsidera glifos y fallo de carga.
Guide: Rol de fuente → token tipográfico → fallback multilingüe → revisión

Componentes y pantallas estándar

Botones, campos, tarjetas, tablas y avisos son piezas. Lista, detalle, creación, revisión, error y vacío son patrones compuestos. Estandarizar solo piezas deja inconsistentes carga, vacío, prohibido y fallo de guardado.

Para cada componente registra propósito, variantes, estados y nombre accesible. Para cada pantalla registra condición de entrada, siguiente acción, estados y evidencia.

ElementoIntención
Acción principal destaca una decisión.
Formulario error y requisito cerca del campo.
Panel de estado ofrece siguiente acción.
Revisión separa resumen, impacto, aprobación y reversión.
Estándar: Tokens → componentes → patrones de pantalla → acción

Accesibilidad y revisión de salida de IA

Una petición de pantalla limpia cambia de interpretación cada vez. Proporciona tarea, componentes permitidos, prohibiciones, estados, accesibilidad y evidencia de aceptación. Revisa texto largo, teclado, errores y modo oscuro.

Registra qué usuario queda bloqueado, en qué estado y por qué. Conserva evidencia antes y después para que otra persona reutilice la decisión.

ElementoIntención
1. ¿Se ve la tarea y una acción?1. ¿Se ve la tarea y una acción?
2. ¿Hay carga, vacío, error y prohibido?2. ¿Hay carga, vacío, error y prohibido?
3. ¿Existen pistas no basadas en color y teclado?3. ¿Existen pistas no basadas en color y teclado?
4. ¿Se respetan tokens y contratos?4. ¿Se respetan tokens y contratos?
Estándar: Contrato → borrador de IA → vista por estado → revisión → evidencia
