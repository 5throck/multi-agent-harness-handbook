Hermes Agents 운영 부록

Hermes Agent를 기존 워크스페이스 거버넌스 안에서 안전하게 사용하는 경로와 경계를 정리한다.

  • Hermes의 플랫폼 표면
  • 신뢰 설정과 컨텍스트 길이
  • 스킬 미러와 AGENTS.md 원칙
  • 검증과 문제 해결

Hermes는 다섯 번째 플랫폼 디렉터리를 사용한다

현재 표준에서 Hermes Agent는 모델 공급자와 분리된 CLI 하네스다. 프로젝트에서는 `.hermes/skills/`를 우선 스킬 경로로 사용한다. 이 폴더는 `skills/` 단일 출처에서 동기화된 미러여야 하며, 원본 폴더를 직접 가리키게 하면 보안 제외·국가 범위·variant 범위 정책을 우회할 수 있다.

Hermes는 스킬을 디렉터리에서 찾아 /skill-name 형태로 호출한다. 따라서 다른 플랫폼처럼 명령어 미러나 `skills.json` 등록 파일을 만들 필요가 없다. 없는 파일을 억지로 추가하는 것보다 플랫폼이 실제로 읽는 표면만 유지하는 편이 안전하다.

검토 항목의도
프로젝트 스킬 `.hermes/skills/` 미러
호출 `/skill-name`
등록 파일 만들지 않음
명령·프롬프트 미러 만들지 않음
표준: skills/ SSOT → sync-skills → .hermes/skills → /skill-name 호출

신뢰 목록과 컨텍스트 예산은 사용자가 관리한다

Hermes는 프로젝트 스킬을 자동으로 읽기 전에 프로젝트 루트가 사용자 설정의 `skills.trusted_project_dirs`에 있는지 확인한다. 이것은 불편한 설정이 아니라 낯선 저장소의 프롬프트 주입을 막는 안전장치다. 프로젝트 문서는 사용자가 신뢰할 경로를 명시적으로 등록하도록 안내해야 하지만, 저장소가 그 설정을 우회하거나 자동 변경해서는 안 된다.

또한 기본 컨텍스트 파일 길이 제한은 큰 `AGENTS.md`를 조용히 자를 수 있다. 표준은 AGENTS.md를 얇은 안내자(pointer/dispatcher)로 줄이는 방향을 택했다. 운영 중에는 `context_file_max_chars` 설정과 Hermes 로그를 함께 확인하고, 긴 규칙은 포인터가 가리키는 거버넌스 문서로 분리한다.

신뢰는 사용자 소유 설정이다.신뢰는 사용자 소유 설정이다.
AGENTS.md는 첫 화면에서 읽을 포인터와 최소 안전 규칙을 제공한다.AGENTS.md는 첫 화면에서 읽을 포인터와 최소 안전 규칙을 제공한다.
상세 정책은 참조 문서에서 읽는다.상세 정책은 참조 문서에서 읽는다.
컨텍스트 잘림 경고는 배포 전에 확인한다.컨텍스트 잘림 경고는 배포 전에 확인한다.
표준: 신뢰된 프로젝트 → AGENTS.md 포인터 로드 → 참조 문서 선택 로드 → 스킬 실행

실습

또한 기본 컨텍스트 파일 길이 제한은 큰 `AGENTS.md`를 조용히 자를 수 있다. 표준은 AGENTS.md를 얇은 안내자(pointer/dispatcher)로 줄이는 방향을 택했다. 운영 중에는 `context_file_max_chars` 설정과 Hermes 로그를 함께 확인하고, 긴 규칙은 포인터가 가리키는 거버넌스 문서로 분리한다.

# User-side Hermes onboarding
hermes config set context_file_max_chars 100000

# Then add the project root to skills.trusted_project_dirs
# using the Hermes user configuration. Do not commit user configuration
# or bypass the trust control from the project repository.

HERMES.md를 만들지 않는 이유

Hermes의 컨텍스트 탐색은 `HERMES.md`가 있으면 `AGENTS.md`보다 먼저 읽는다. 그래서 별도의 HERMES.md를 만들면 같은 규칙을 두 군데 관리하게 되고, 시간이 지나며 서로 다른 지시가 생긴다. 표준은 Hermes가 AGENTS.md를 직접 읽는다는 사실을 이용해 지시의 단일 출처를 유지한다.

동일한 이유로 `.hermes/skills/`는 복사본이지만 독립적으로 편집하는 작업 공간이 아니다. 스킬 변경은 `skills/`에서 검토하고 동기화 도구로 미러에 반영한다. 미러의 차이는 플랫폼별 맞춤이 아니라 동기화 실패 신호로 다룬다.

검토 항목의도
`HERMES.md` 생성하지 않는다. AGENTS.md를 가리지 않기 위해서다.
`.hermes/skills` 동기화된 배포본이다.
AGENTS.md 얇은 디스패처와 포인터 표를 제공한다.
상세 거버넌스 별도 문서가 단일 출처다.
표준: AGENTS.md 단일 지시 → 포인터 추적 → 기준 정책 → Hermes 실행

운영 전후에는 미러·지시·안전 경계를 검증한다

설치가 되었는지와 안전하게 작동하는지는 다르다. 새 프로젝트에서는 `.hermes/skills`가 생성되었는지, 보안 제외 스킬이 섞이지 않았는지, AGENTS.md가 예상한 포인터를 제공하는지 확인한다. 사용자는 신뢰 경로와 컨텍스트 설정을 검토하고, 팀은 동기화·템플릿·감사 검사를 통과한 결과를 남긴다.

문제가 생기면 먼저 스킬 이름이나 모델을 바꾸기보다 경로와 로드 순서를 확인한다. 프로젝트가 신뢰되지 않았거나 미러가 오래되었거나 AGENTS.md가 잘렸다면, 프롬프트를 바꾸어도 근본 원인은 남는다. 작은 검증 목록을 운영 인수 기준으로 사용한다.

검토 항목의도
1. 프로젝트 루트가 신뢰 목록에 있는가?1. 프로젝트 루트가 신뢰 목록에 있는가?
2. `.hermes/skills`가 SSOT와 동기화되었는가?2. `.hermes/skills`가 SSOT와 동기화되었는가?
3. HERMES.md가 AGENTS.md를 가리고 있지 않은가?3. HERMES.md가 AGENTS.md를 가리고 있지 않은가?
4. 컨텍스트 잘림 경고와 동기화 검증 결과가 없는가?4. 컨텍스트 잘림 경고와 동기화 검증 결과가 없는가?
표준: 스캐폴드 → 신뢰 등록 → 미러 확인 → 컨텍스트 확인 → 스킬 호출 → 감사 증거

  2. `HERMES.md`: 생성하지 않는다. AGENTS.md를 가리지 않기 위해서다.
  3. 4. 컨텍스트 잘림 경고와 동기화 검증 결과가 없는가?
