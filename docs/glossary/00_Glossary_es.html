Conceptos Fundamentales Componentes del Equipo Estructura del Espacio de Trabajo Herramientas y Plataformas

Conceptos Fundamentales

Ingeniería de Arnes Harness Engineering
La disciplina de diseñar a través de qué herramientas, reglas y mecanismos de verificación trabaja un modelo. Es la tercera etapa en la progresión desde la ingeniería de prompts (qué decir) hasta la ingeniería de contexto (qué dar a conocer). Detalles: Capítulo 2 §1
Subagente Subagent
Un agente auxiliar que tiene una ventana de contexto independiente de la sesión principal, maneja una tarea estrecha y devuelve solo un resumen. Es el mecanismo mediante el cual el concepto de "especialista" se implementa en herramientas reales. Detalles: Capítulo 2 §3b
Entrega Handoff
El acto, o el punto, en el que el trabajo se transfiere entre agentes. Un Contrato de Entrega estructura el formato de la información intercambiada — al detallar el propósito, el alcance y los entregables del paso anterior, permite que el siguiente agente comience inmediatamente sin necesidad de hacer preguntas de seguimiento. Detalles: Capítulo 2 §3
Composición Dinámica del Equipo Dynamic Team Composition
El orquestador decide, para cada solicitud, qué subagentes desplegar realmente, cuántas veces y en qué orden. Aunque la plantilla del equipo definida es fija, la configuración de despliegue real varía de tarea en tarea. Detalles: Capítulo 2 §4b · Práctica: Capítulo 4 D-2
Patrón de Orquestación Orchestration Pattern
El conocido conjunto de cinco patrones representativos de Anthropic: encadenamiento de prompts (procesamiento secuencial paso a paso), enrutamiento (clasificar una solicitud y despacharla al agente/modelo apropiado), paralelización (distribución para ejecutar tareas independientes concurrentemente, o votación para repetir la misma tarea y tomar la mayoría), orquestador-trabajadores (descomponer dinámicamente subtareas en lugar de fijarlas de antemano), y evaluador-optimizador (verificar independientemente un borrador antes de incorporarlo — verificar y luego aplicar). Estos pueden combinarse libremente dentro de un solo flujo de trabajo. Detalles: Capítulo 2 §4
Ventana de Contexto / Sobrecarga de Contexto Context Window / Context Overload
La ventana de contexto es el límite en la cantidad de tokens (texto) que un modelo de IA puede procesar a la vez. Dentro de este límite debe contener la definición del rol, la conversación pasada, las instrucciones de la tarea y la salida todo junto; a medida que el contenido crece, la información anterior comienza a desvanecerse — esto se llama sobrecarga de contexto. Distribuir el trabajo por roles para abordar esto es una de las motivaciones centrales detrás de los equipos multiagente. Detalles: Capítulo 1 §Multiagente: El Principio de un Equipo de Expertos
Frontmatter Frontmatter
Un bloque de metadatos escrito en YAML en la parte superior de un archivo de definición de agente (agents/*.md). Define cosas como el nombre del agente, rol, herramientas permitidas (tools) y nivel de modelo (tier) para que puedan analizarse mecánicamente. El campo extends puede usarse para heredar de otro archivo de agente. Detalles: Capítulo 8 §1 Despliegue y el SSOT
Scaffolding Scaffolding
El acto de usar bun scripts/new-project.ts para clonar la configuración completa de una plantilla de variante (agentes, habilidades, comandos, pipeline de gobernanza) en un repositorio git independiente. La idea es: "no se construye un proyecto desde cero — se comienza a partir de un esqueleto pre-diseñado." Detalles: Capítulo 6 §2
Hook Hook
Un script que se ejecuta automáticamente antes o después de que un agente llame a una herramienta en particular. Ejemplo: un hook PostToolUse que ejecuta una verificación de auditoría automatizada después de una edición de archivo. En Claude Code (CLI), los hooks definidos bajo .claude/hooks/ se activan como se espera, pero no se activan en Claude App (Escritorio) — por lo que es importante conocer estas diferencias de comportamiento por herramienta. Detalles: Capítulo 3 §Registros de Auditoría y Observabilidad
Kanban / Límite WIP Kanban / WIP Limit
Un método de control de concurrencia que limita la cantidad de tareas en progreso (Work In Progress) en un momento dado. Al distribuir para ejecutar muchos agentes simultáneamente, establecer un límite WIP previene la contención de recursos y la pérdida de contexto que surgen de demasiada ejecución concurrente. Detalles: Capítulo 2 §Patrones de Orquestación
Modelo de Ticket de Servicio Service Ticket Model
Un modelo operativo que usa la IA puramente como "un servicio que maneja solicitudes conforme llegan" — similar al sistema de tickets de una organización de TI tradicional. El usuario debe dirigir cada solicitud explícitamente, lo que limita la autonomía del equipo de agentes. Este es el enfoque que este manual contrasta con su modelo propuesto de "herramienta de desarrollo + modelo de variante." Detalles: Capítulo 7 · Comparando Estrategias Operativas Empresariales
Ciclo de Vida / Estado Lifecycle / State
Ciclo de vida se refiere a la secuencia completa de etapas por las que pasa un agente, habilidad o script (por ejemplo, Crear → Verificar → Operar → Mejorar → Deprecar). Estado es una instantánea de en qué etapa del ciclo de vida se encuentra ese componente en un momento dado. El campo status en el frontmatter YAML (draft, active, deprecated, retired) almacena el valor del estado. El ciclo de vida puede pensarse como un "mapa del metro," y el estado como el letrero que muestra "en qué estación está el tren actual." Detalles: Capítulo 8 §2 · Distinguiendo Estado de Ciclo de Vida

Componentes del Equipo Multiagente

Orquestador Orchestrator
El rol que divide la tarea general en etapas, llama a los especialistas y se detiene en puntos donde se necesita la confirmación del usuario. Comúnmente denominado "agente PM."
Especialista Specialist
Un agente con una responsabilidad estrecha y claramente definida — como diseño, implementación, prueba o revisión de seguridad — cuyas entradas y salidas están claramente especificadas.
Nivel de Modelo Model Tier
El nivel de costo del modelo (high/medium/low) asignado por rol de agente. Los roles que requieren mucho juicio se asignan como high; el trabajo estandarizado y repetitivo se asigna como low — equilibrando costo y calidad. Se especifica a través del campo tier en el frontmatter de agents/*.md, y la plataforma lo traduce a un nombre de modelo real mediante model: inherit. Detalles: Capítulo 5 §3. Nota: este es un concepto diferente al "3 niveles" de L0→L1→L2 — no los confunda.

Estructura de ai-workspace-standards

SSOT Single Source of Truth
El principio de que una pieza de información dada tiene su copia original en exactamente un lugar. Ejemplo: CONSTITUTION.md es el SSOT para las reglas de todo el espacio de trabajo; context.md es el SSOT para un proyecto individual. Detalles: Capítulo 5 §4
L0 / L1 / L2
La jerarquía de tres niveles que va desde la raíz del espacio de trabajo (L0, la única original) → la instantánea de la plantilla común (L1, templates/common/) → la variante/proyecto (L2, templates/co-*/ o Projects/*/). El flujo siempre se mueve de arriba hacia abajo, y la transferencia L1→L2 es una "bifurcación" que ocurre exactamente una vez, en el momento de la scaffolding. Detalles: Capítulo 8 §1 Despliegue y el SSOT
Modelo de Bifurcación Fork Model
El enfoque por el cual, una vez que L2 se ramifica de L1, evoluciona independientemente sin sincronización inversa automática. Para promoverlo a una plantilla oficial se requiere que un humano ejecute explícitamente l2-to-variant-pipeline.ts.
variante
Una configuración completa de equipo multiagente para un dominio específico — que reside bajo templates/ — que agrupa un PM, agentes especialistas y un pipeline de gobernanza. co-develop, co-design y co-work son ejemplos. Detalles: Capítulo 5 §3
Fase A / Fase B
Las dos etapas de creación de una nueva variante. La Fase A es la etapa de experimentar libremente como un prototipo independiente bajo Projects/; la Fase B es la etapa de promoverlo a una variante oficial templates/ mediante promote-variant. Detalles: Capítulo 11 · Crear una Nueva Variante
Plantilla Base Boilerplate
Un punto de partida pre-construido — definiciones de rol PM, pipeline de gobernanza y cableado de comandos/habilidades — que de otro modo tendrían que escribirse desde cero para cada proyecto. Esta es la esencia de lo que distribuye ai-workspace-standards.
Integración con Contenedores Container Integration
Una dirección para el avance de ai-workspace-standards: el requisito de que un proyecto con scaffolding pueda integrarse con servicios como Open WebUI en un entorno Docker/Kubernetes y ser soportado por usuario individual. Actualmente solo se soporta la integración directa con herramientas locales de codificación con IA. Detalles: Capítulo 8 §5 Hoja de Ruta de Avance
Consolidación de Memoria Memory Consolidation
Una dirección para el avance de ai-workspace-standards: una función que reúne y organiza los archivos memory/MEMORY.md dispersos en proyectos individuales a nivel del espacio de trabajo para que puedan identificarse las tendencias generales. Detalles: Capítulo 8 §5 Hoja de Ruta de Avance

Herramientas y Plataformas

AGENTS.md
Un archivo de estándar abierto leído en común por más de 30 herramientas de codificación con IA. Define reglas neutrales a la herramienta como comandos de compilación/prueba y estilo de código. En este repositorio adicionalmente sirve como "plantilla de agentes." Detalles: Capítulo 2 §AGENTS.md, el Arnes que Cruza Herramientas
teammateMode
El modo de ejecución paralela para Agent Teams (una función experimental). Claude App (Escritorio) solo soporta in-process, mientras que Claude Code (CLI) adicionalmente soporta el modo panel dividido tmux. Detalles: Referencia Común §1
Administrador de Agentes
Una interfaz de nivel superior en Antigravity (Escritorio) para supervisar múltiples espacios de trabajo desde una sola pantalla. El principio es asignar un agente por espacio de trabajo.
/goal / /agent / /agents
Comandos slash en Antigravity CLI (agy) que invocan la orquestación dinámica de subagentes. /goal ejecuta un objetivo hasta su finalización, /agent delega una tarea de larga duración en segundo plano, y /agents enumera el estado de los subagentes creados hasta el momento. Esta capacidad no es exclusiva de agy — Claude Code/App realiza la misma orquestación dinámica mediante la herramienta Agent (Task) y solicitudes en lenguaje natural, mientras que Antigravity (Escritorio) lo hace mediante la GUI del Administrador de Agentes. Estos tres comandos son simplemente los nombres dados a ese comportamiento en la pantalla CLI. Detalles: Referencia Común §2
