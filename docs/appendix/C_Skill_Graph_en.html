Skill Relationship Graph — Structure and Operations

Once skills number in the dozens, "which skill presupposes what" disappears from organizational memory. This document consolidates the concrete structure of the skill relationship graph introduced in Chapter 8 §2 — data sources, schema, relation vocabulary, generation pipeline, validation, and the operational workflow — into a single chapter.

Source: ai-workspace-standards ADR-0060 Skill Relationship Graph as Generated Projection (Amendments 1–6) · ADR-0061 Decision Record Standard · ADR-0072 Skill Term Nodes · scripts/generate-skill-graph.ts v1.10.0

What This Reference Bovers

  • Node/edge schema and the vocabulary of ten typed relations
  • What’s new in 2026-09 (ADR-0072): Korean term vocabulary as term:<용어> nodes from references/terms-ko.json

  • The generation/verification/sync pipeline and the procedure for adding a relation

Overview — Why a Graph

If relations between skills, agents, and ADRs ("this skill must run before that one", "this agent uses that skill") are kept as free text, three things inevitably happen. First, the source changes but the prose stays, so it goes stale. Second, relations scatter across files and become unsearchable. Third, unless a human curates the list, nothing is verified either.

The skill relationship graph solves this by deriving rather than writing. The sources of relations are structured data that already exists (SKILL.md frontmatter, agent files, variant manifests), and the graph is their projection. You can always delete the graph files — rerunning the generator births them again in exactly the same way. That is why ADR-0060 pins the principle under the name Generated Projection.

Data Sources and Priority

The generator scans the following sources in priority order. Earlier sources are more explicitly intentional; later ones more implicitly derived.

  1. SKILL.md frontmatter — prerequisites (mandatory predecessor skills) and typed relates_to (relation vocabulary + target + optional note). The most explicit source.
  2. Each skill's references/terms-ko.json (added 2026-09, ADR-0072) — Korean domain vocabulary as term:<용어> nodes joined to their skill by references edges. An entry may be a plain glossary string or an object with en/mapsTo and an optional nested items map; malformed files are skipped so the build stays deterministic.
  3. Agent files' required_skills — produces agent → skill used_by relations.
  4. variant.json's skill_manifest — the manifest of which skills a variant attaches to which agents and phases. Source of phase relations.
  5. Backtick references in document prose — a document mentioning a skill by its exact backticked name produces a references edge (exact match only, to avoid false positives).
  6. docs/skill-graph.overrides.json — escape hatch to add relations not derivable from the sources above, or to suppress auto-derived ones. Per-scope overrides are also supported.

Edges from frontmatter carry provenance: {file, field, index?}. Tracing "why does this relation exist" always leads back to a specific field of a specific source file.

Node and Edge Schema

The committed graph artifacts are two — machine-readable docs/skill-graph.json and the human-readable relation table docs/skill-graph.md. The top-level JSON structure is {version, nodes[], edges[]}.

{
  "version": "1.7",
  "nodes": [
    { "id": "handbook", "type": "skill", "layer": "common" },
    { "id": "handbook-reviewer", "type": "agent", "layer": "common" },
    { "id": "ADR-0060", "type": "adr", "layer": "L0" }
  ],
  "edges": [
    {
      "from": "handbook",
      "to": "research",
      "type": "requires",
      "provenance": {
        "file": "skills/handbook/SKILL.md",
        "field": "prerequisites",
        "index": 0
      }
    },
    {
      "from": "handbook-reviewer",
      "to": "handbook",
      "type": "used_by"
    }
  ]
}

Nodes carry id, type, and layer. Types include skill, agent, adr, decision, procedure, output_type, and — since 2026-09 (ADR-0072) — term for Korean vocabulary nodes; layers are L0 (workspace root), common (shared template), variant:<name>, and L3 (individual project).

What’s new (2026-09): Korean term nodes (ADR-0072). The k-* skills keep their Korean domain vocabulary in a per-skill data file, references/terms-ko.json — a non-Markdown reference asset, which is exactly why the graph generator (not the document scanner) is what reads it. Each entry becomes a term:<용어> node whose layer matches the owning skill, plus a skill → term references edge. "Which skills talk about 전자공시 or 100대 통계지표" is now a first-class graph query instead of a prose guess. Since generator v1.10.0 the vocabulary is also rendered into docs/skill-graph.md as a Korean Term Vocabulary table (term | layer | referencing skills); docs/skill-graph.json remains the machine SSOT. verify-skill-graph.ts mirrors the new term member of the node-type union and enforces the term invariants — ids properly namespaced term:, no duplicates, and no orphan term node (every term must be referenced by at least one skill edge).

The most common mistake is confusing the direction of requires. A requires B means "you need B before A", not "A produces B". If the direction is unclear, check the source frontmatter via the provenance field.

The Three-Layer Relation Model

Three kinds of relations coexist in the same graph. Their lifespans and trust levels differ, so they are handled as distinct layers.

  • L-A Explicit — typed relates_to in frontmatter. Permanent by intent, the primary source of the graph.
  • L-B Experimental — relations in the overrides file. reason and since are mandatory, and a staleness warning fires after 90 days. It is the waiting room for relations "that probably belong in the graph but are still being observed before entering frontmatter".
  • L-C Projection — the generated graph itself. Always regenerated, with a determinism check confirming "same input → same output" holds.

When an experimental relation is judged stable, move it to frontmatter to promote it to L-A. To remove an L-A relation, delete it from frontmatter — there is no path that edits the graph files directly.

Generation Pipeline

The graph interlocks with the pipeline at four points.

  • scripts/generate-skill-graph.ts — scans sources and produces skill-graph.json/.md. --scope <name> creates a per-template scoped graph (common + each variant, 14 scopes in total).
  • scripts/verify-skill-graph.ts — verifies the committed graph against its sources (drift) and invariants.
  • dev-sync.ts step 4.65 — regenerates and drift-checks all scope graphs on every /sync. Keeping the graph current is baked into the commit flow.
  • new-project.ts step 7.6 — generates the project's docs/skill-graph.json at scaffold time, without waiting for the first /sync.

A scope graph is a scoped view of the unified L0 graph. Because a variant template ships its own scope graph, a project born from it starts with a relation map relevant to itself from day one.

Declarative vs Inferential Strategies

There are two strategies for where relations come from.

  • Declarative — relations are stated directly in frontmatter (Amendment 3). Intent is explicit and validation is simple, but it depends on the discipline of skill authors.
  • Inferential — relations are derived from existing structured data (Amendment 4, co-newbiz precedent), grounded in phase adjacency of procedure schemas or rule predicates. Coverage grows without adding any frontmatter.

The comparison experiment (scripts/experiments/infer-graph-from-phases.ts, read-only) concluded with a split verdict — inference works well in areas rich in procedure schemas, but the declarative strategy wins elsewhere. No new default extraction mode was adopted; the two coexist: derive where schemas exist, declare for the rest.

Decision Chain and Validation

The reason the graph embraces ADRs and decision records is to put "relations" and "rationale" on one map. The decision chain of ADR-0061 — Agent, Skill, Knowledge, Evidence, Rule, Decision — is validated fail-closed by scripts/validate-decisions.ts.

  • Presence of required frontmatter in decision records and references into the evidence ledger
  • Rule ID format and resolvability of skill references
  • Propagation-coupling rule — a skill published to L1 must not relate to targets absent from L1. Otherwise every downstream copy grows dangling edges.

Via supersedes and cites_skill edges, the graph shows "on which skills this decision was made, and which documents it succeeded". It is a structural device preventing relations from accumulating without rationale.

Practical Workflow — Adding a Relation

The minimal procedure when actually adding one relation.

  1. Declare — write the relation in the target skill's SKILL.md frontmatter: 
    relates_to:
  - { skill: research, type: requires }
  - { skill: pdf-export, type: enables, note: "produces layout spec" }
  2. Validate — run bun scripts/validate-skills.ts (relation form checks), then bun scripts/generate-skill-graph.ts.
  3. Confirm — run bun scripts/verify-skill-graph.ts to confirm no drift, and visually check the skill's relation table in docs/skill-graph.md.
  4. Commit — /sync performs all-scope regeneration and verification at step 4.65, so just make sure you did not edit the graph files directly before committing.

For a relation you are not yet sure about, write it in the overrides file instead of frontmatter. Leaving reason and since means the system will ask "still observing?" after 90 days.

Roadmap

The Phase 2+ vision of ADR-0060 is as follows; none of it is implemented yet.

  • Lifecycle state machine — track skill draft/active/retired transitions as graph node state
  • Versioning and migration — tooling to move between graph schema versions
  • Graph intelligence — relation-driven routing suggestions and automatic context bundle composition
  • Audit trail snapshots — point-in-time graph snapshots for querying relation history

The point is that today's design does not block these extensions. Because the graph is a projection, not a primary store, adding consumers or node state only requires changing the sources and the generator.
