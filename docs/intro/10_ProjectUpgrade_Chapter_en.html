Chapter 12

L3 Project Upgrade

Once you've created an L3 project, what happens when the upstream standards (L0/L1) change? The answer is: "nothing happens at all." Because of the fork model discussed in Chapter 10 §1, actually bringing new upstream changes into an already-created L3 project requires a human to explicitly run upgrade-project.ts. This chapter covers that procedure.

Source: ai-workspace-standards/scripts/upgrade-project.ts (as of v1.10.1) - Related: Chapter 10 §1 Deployment and SSOT

What this chapter covers
  • Why "upgrading" in the fork model is a command you run, not something that happens automatically
  • Basic usage of upgrade-project.ts and the principle of running --dry-run first
  • The main file-handling modes: LOCKED, MERGE, DOCS_MERGE, VARIANT_DOCS_SYNC, COMMANDS_SYNC, SYNC_IF_NEWER, PRESERVE, PRUNE, plus TEMPLATE TREE SYNC and ENV_SAMPLE SYNC
  • The external-dependency machinery (2026-11): the external-deps.json manifest, the scaffold fetch, the compat-gated EXTERNAL DEPS pass, and the vendoring guard
  • The automatic git stash snapshot and the --rollback safety net
  • How this is the exact opposite direction from the "promotion" covered in Chapter 13

Why it's needed — the flip side of the fork model

As established in Chapter 10 §1, L1 delivers its content to a project exactly once — at the moment new-project.ts scaffolds it. From that point on, L3 evolves completely independently, and no matter how much L1 changes afterward, nothing is automatically reflected in an L3 project that already exists.

The problem is that, over time, hook scripts get fixed on the L1 side, new skills get added, and security settings get hardened. When you want to bring those changes into an individual L3 project, manually comparing files one by one isn't realistic. upgrade-project.ts automates this reflection process while still honoring the core principle of the fork model — "never blindly overwrite parts that L3 has deliberately changed."

How to use upgrade-project.ts

Start by running --dry-run to preview what will change. It doesn't touch any files — it just prints the plan to the console.

bun scripts/upgrade-project.ts <project-path> --dry-run

If the output looks fine, run it again without --dry-run.

bun scripts/upgrade-project.ts <project-path>
# Optional flags: --variant <variant>  --platform all|claude|antigravity|codex|hermes (comma list ok)
#            --prune-removed  --rollback

--platform follows ADR-0100 (2026-10-10): it takes all (default), a single profile (claude, antigravity, codex, hermes), or a comma-separated list such as claude,codex, and keeps the union of the selected profiles' files while pruning the rest. The breaking change to know: a single codex no longer keeps CLAUDE.md/GEMINI.md — pass codex,claude,antigravity for that (the legacy both value is treated as all with a warning).

--variant is usually unnecessary since it's read automatically from the value recorded in the project's .claude/template-version.txt. For older projects that lack this file, the script prompts for confirmation at runtime and you'll need to specify --variant directly.

The main file-handling categories

The script treats files differently depending on their nature — it isn't a blanket "overwrite everything with the new version."

CategoryBehaviorExample targets
LOCKEDAlways overwritten with the template's content.githooks/* (pre-commit routing, etc.), .gitattributes
LOCKED (merge-aware)Like LOCKED — always takes the template — but merge-aware: regex and allowlist entries (regexes/paths) that exist only in the project are preserved while the managed rules are restored (since v1.10.0; the previous blind overwrite silently dropped project-specific allowlist entries).gitleaks.toml (mergeGitleaksToml())
MERGEOnly the sections wrapped in WORKSPACE-MANAGED/COMMON-CLAUDE/COMMON-GEMINI/COMMON-AGENTS/VARIANT-INJECT/DYNAMIC_SKILLS markers are merged; the rest of the local content is preserved as-isCLAUDE.md/GEMINI.md/CODEX.md (depending on --platform), .gitignore, agents/pm.md
DOCS_MERGEApplies the same managed-block merge to docs — only documents without markers are overwritten wholesale as an exception (added in v1.7.0)AGENTS.md, docs/<variant>.context.md, docs/phase-definitions.md
VARIANT_DOCS_SYNCUpdated only when the file's inline *<filename> version: X.Y footer version (or hash, if absent) is older than the template's (added in v1.7.0)docs/context.md (since v1.9.0), docs/engagement-orchestration.md, docs/team-configuration-guide.md
COMMANDS_SYNCSynchronizes platform command files with the template's content whenever their hashes differ (added in v1.7.0).claude/commands/*.md, .gemini/commands/*.toml (rendered by bun scripts/render-commands.ts)
SYNC_IF_NEWERCopied only when the template version is newer than the project's versionscripts/*.ts (@version comment, including JSDoc headers), agents/*.md (frontmatter version:), skills/*/SKILL.md
PRESERVEListed only, never touchedREADME.md, README_ko.md, src/
PRUNE (optional)When --prune-removed is specified, scripts/agents/skills files that were removed from the template are also removed from the projectSame directories as the SYNC_IF_NEWER targets above
As of the 2026-09-20 upstream, the latest upgrade-project.ts adds newer passes on top of these traditional categories: TEMPLATE TREE SYNC for template files with no dedicated classifier, ENV_SAMPLE SYNC for country-aware .env.sample merging, CONTEXT_COMMONIZATION for pruning duplicate context sections, and GOVERNANCE FILES SYNC for add-if-missing governance files such as LICENSE/SECURITY. The Codex surface is also covered through CODEX.md MERGE and add-if-missing delivery of .codex/config.toml, and the repo-context surfaces ride the same upgrade engine. Update (2026-11): the tool behind them was renamed — graft 0.28 is now trail (ADR-0076) — and the upgrade pass gained two trail-migration tolerance rules: JSON_MERGE drops template hook entries whose repo-relative helper path is missing from the project (so a trail init-rewritten tree never gets graft-era hook entries re-merged), and a project already migrated by trail init (it carries the .trail/ marker) gets the retired graft-era seeds skipped (SEED_SKIP (retired-surface)) — a missing .mcp.json, for example, is not re-seeded.
Two 2026-10 additions ride this same engine. ADR-0101 turns the numbered skeleton sections of CLAUDE.md/GEMINI.md (the content outside the marker zones) into a managed delivery surface: lib/platform-skeleton-merge.ts inserts a missing canonical section at a template-relative anchor and replaces a divergent body only when it contains nothing project-local (guarded, writing a <file>.pre-skeleton.bak snapshot first) — closing the 2026-09-12 "upgrade ate a heading" defect class. And the new opt-in --changelog-entry flag scaffolds an editable chore(upgrade): template sync bullet at the top of the project CHANGELOG's [Unreleased] section (idempotent per template version; refused under --dry-run).

Since v1.10.x, upgrades are also country-profile aware. Before running, the script reads the country= line from the project's .claude/template-version.txt (falling back to the jurisdiction noted in docs/countries/ACTIVE.md) to determine the target country, and preserves that line when it rewrites the file at the end — older versions dropped the line during the rewrite, erasing the project's country provenance. In addition, after all skill-sync passes finish, a registry-driven prune pass runs once more and deletes country-scoped skills (k-dart/k-law/k-kosis) if they were re-injected into a project whose country doesn't match — preventing upgrades from undoing the pruning done at scaffold time. Forks deliberately modified locally, however, are kept with a ⚠️ CONFLICT warning.

If a SYNC_IF_NEWER target has been edited locally but the template's version is newer, the script marks it as ⚠️ CONFLICT but still overwrites it with the template's content in the end. Keep in mind that this is "warn and proceed," not "ask before overwriting" — which is exactly why the safety net described below matters.

External dependencies (2026-11)

One more surface rides the same engine. A project can declare pinned external git dependencies in an external-deps.json manifest at its root, and the distribution rule is settled: never vendor external repos into template trees. External code is cloned from GitHub at a pinned release tag, at scaffold time, into a gitignored project-local directory, and upgrades move the pin only when the dependency's compatibility test passes. The first consumer is ppt-master v6.8.0, the conversion engine behind co-work's deck pipeline, consumed as-is behind an adapter.

What's new (2026-11): the external-dependency machinery landed — a schema-versioned external-deps.json manifest convention (seeded empty at L1, extended per variant), a scaffold-time fetch in new-project.ts §7.9 with the opt-in --strict-external-deps hard-fail flag, a compat-gated EXTERNAL DEPS pass in upgrade-project.ts with --external-deps-only, and a vendoring guard that fails template validation if any install_dir content ever lands inside a template tree.

Each manifest entry records the fields below. pin is the contract — the advisory commit field exists only as a drift tripwire.

FieldMeaning
idStable identifier, unique within the manifest — also the merge key when a variant seed extends the common seed
repohttps GitHub URL, no credentials
pinRelease tag — the version we run; the upgrade pass compares it against upstream tags
commitResolved sha, written back at fetch/update time — advisory drift tripwire only
installClone command template with {pin}/{repo}/{dir} placeholders (depth 1 at the tag)
install_dirProject-relative clone destination — must be gitignored; an external clone must never be committed
consumerFree text naming the consuming pipeline (advisory)
compatibility_testCommand run from the project root; exit 0 = pass — the gate every pin move must clear
propagationEnum; never is the only value for now — external content never crosses the template boundary

Scaffold fetch (§7.9). After project materialization completes, new-project.ts installs every manifest entry into its install_dir and appends the matching .gitignore line. The posture is WARN, not fail — a network-dependent scaffold must not leave the user without a project: on fetch failure the project is still scaffolded, a WARN row lands in the run output, and the documented retry is bun scripts/upgrade-project.ts <project-path> --external-deps-only (the same update pass, fetch-only flavor). --strict-external-deps flips this to hard-fail for CI and provisioning contexts that must not proceed without the dependencies.

The EXTERNAL DEPS upgrade pass. The pass runs after TEMPLATE TREE SYNC, per dependency: git ls-remote --tags resolves the newest release tag (a tag not newer than pin short-circuits to "current"); if a newer tag exists, compatibility_test runs from the project root — on pass the pin moves (manifest pin/commit updated, the clone re-fetched at the new tag), on fail the current pin is held with a WARN row and no changes. Every dependency yields a decision-log row per the unified decision-log convention, --dry-run reports what it would do without touching anything, and --external-deps-only runs just this pass. Existing projects receive the template seeds through this same pass on their next upgrade — the empty L1 manifest, plus variant entries like ppt-master, arrive without any hand-written migration.

Vendoring guard. Three rules keep external code out of the governed trees. Template validation fails if any path inside a template tree matches a manifest install_dir (the fastest way to catch an external/ppt-master/ accidentally committed into a template); project-to-template propagation and the template-to-project tree sync both hard-skip those paths; and install_dir gitignore coverage is auto-appended at scaffold and validated at upgrade. A committed external clone would defeat the whole distribution model — upstream would see our fork as a diff.

The ppt-master entry shows the shape end to end: repo https://github.com/hugohe3/ppt-master (MIT), pin v6.8.0, cloned into external/ppt-master behind the deck pipeline's adapter, with a contract test as its compatibility_test. When ppt-master publishes v6.9.0, the upgrade pass runs the contract test first — the pin moves only on pass, and otherwise holds with a report row.

Safety nets — snapshots and rollback

Before running (when not in --dry-run mode), the script automatically runs git stash push -m pre-upgrade-snapshot-YYYYMMDD to snapshot the current state of your working tree. If you're not happy with the upgrade result, you can revert it immediately with the following command.

bun scripts/upgrade-project.ts <project-path> --rollback

This command finds the pre-upgrade-snapshot-* stash that was just created and restores it via git stash pop. The upgrade itself does not create a commit, so after reviewing the result, you'll need to check the changes with git diff as usual and commit them yourself.

As a final step, .claude/template-version.txt is updated to the new version — with its country= line preserved — and security bootstrap items — .gitleaks.toml, pre-commit hooks, .gitattributes (eol=lf), .gitignore (.env patterns), and git core.hooksPath — are automatically checked (these are the same items covered by the Chapter 3 guardrail principles). If core.hooksPath is misconfigured, the script fixes it on its own.

How this differs from promotion

The "promotion" covered in Chapter 13 and this chapter's "upgrade" sound similar, but they run in exactly opposite directions.

  • Promotion (l3-to-variant-pipeline.ts, Chapter 13) — L3 → L2. Elevates changes from a project you created into the official variant template, turning them into a variant others can use.
  • Upgrade (upgrade-project.ts, this chapter) — L1 → L3. Pulls the latest changes from the official template into a project you've already created.

The two scripts simply move files in opposite directions — neither replaces the other. If you want to contribute back to the template, use promotion; if you want to keep an existing project up to date, use upgrade.

The script behavior described in this chapter (flags, file categories, safety nets) was written by directly examining the source of scripts/upgrade-project.ts (v1.10.1) in the ai-workspace-standards repository. This handbook repository does not include that script, so always cross-check actual execution results against the latest source.
