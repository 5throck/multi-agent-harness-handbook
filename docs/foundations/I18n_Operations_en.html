i18n Design and Content Quality

Design internationalization as a product contract for language, country rules, formatting, and screen states—not as a pile of translated files.

In this chapter
  • Separate locales from country profiles
  • Translatable assets and SSOT
  • Layouts for length, format, and state
  • Parity validation and operations

i18n is broader than a language switch

Internationalization lets people complete the same product task across languages and regions. A locale affects words, dates, numbers, and ordering. A country profile affects regulations, currencies, data providers, and disclosure rules. Combining them makes a text change capable of changing business rules.

Think of a trip: a locale is the language and local notation on a guide; a country profile is the border rule and currency. They may be chosen together, but they have different owners and validation.

Review itemIntent
Locale UI text and date, time, number, currency formatting
Country profile regulation, providers, permissions, disclosure
Content visible text and alternative text
Identifiers keys, filenames, code, and URLs are not translated
Standard: User selection → locale text and formats / country-profile business rules

Create one source of truth for wording and structure

When translations are scattered inside screens, one language easily loses a button, error message, help text, or empty state. Keep a canonical language and manage message keys, screen structure, state lists, and glossary together. A translation should copy the canonical structure and translate only visible language.

A key is a semantic contract, not an opaque developer shortcut. Use names such as `review.approve` and never recycle one key for a new meaning.

Review itemIntent
Canonical language basis for headings, exercises, and code blocks
Message keys stable semantic names
Glossary one expression per concept
Change record distinguish wording changes from structure changes
Standard: Canonical content → message keys and glossary → translations → structure, link, term checks

Treat long translations and regional formats as layout input

A word can expand or contract across languages. Fixed-width buttons and tables clip text or push content off-screen. Format dates and numbers with locale-aware formatters rather than string concatenation, and inspect line breaks in the real edition.

Empty and error states require translation too. Preview long names, zero results, permission denial, and network failure in every language.

Validate parity by user task, not sentence count

Natural prose is not enough if one edition loses a save action, warning, link, or exercise step. Automation compares headings, code blocks, links, and search registration; human review checks terminology, tone, clipping, and country rules.

Finalize the canonical language first and change all editions in one set. Before delivery, exercise language switching, empty and error states, date and currency formatting, and accessible names.
