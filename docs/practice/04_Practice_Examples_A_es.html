El principio detrás de todo el curso — Cada escenario a continuación sigue el mismo orden: primero escribir el rol del subagente como una especificación AGENTS.md neutral a la herramienta, y luego "implementar" esa especificación en la familia Claude como un archivo de subagente predefinido (consulte Cap.2 §5 AGENTS.md). Confirmar manualmente que existe una especificación pero que el método de ejecución difiere según la herramienta es el objetivo central de este ejercicio. Para el equivalente de Antigravity, consulte Cap.4 §2-B.

Configuración: instalación de los programas necesarios

Los ejercicios a continuación se centran en Claude App (Escritorio) y Claude Code (CLI). Si su entorno local aún no tiene estas herramientas, la automatización de configuración del entorno incluida con este manual — la guía de configuración — instalará automáticamente exactamente lo que necesitan los ejercicios de este capítulo. Simplemente siga las instrucciones para descargar y ejecutar el script localmente.

📦 Antes de instalar — Cosas que verificar

Antes de ejecutar el script, lea primero la lista de verificación previa a la instalación. Esta lista los siguientes requisitos previos.

  • Una suscripción activa a Claude Pro/Max y una cuenta de Google para acceso a Antigravity (debe ser un plan basado en suscripción/cuenta, no una clave API individual)
  • Una cuenta de GitHub que pueda usar para ejecutar gh auth login
  • Al menos 5 GB de espacio libre en disco
  • Privilegios de administrador o sudo
Si aún no tiene una cuenta de GitHub
① Vaya a github.com/signup en su navegador.
② Ingrese su dirección de correo electrónico, contraseña y nombre de usuario — el nombre de usuario se usa tal cual en la URL del repositorio más adelante (github.com/<nombredeusuario>/...), así que elíjalo con cuidado.
③ Complete el rompecabezas/verificación de código para evitar registros automatizados.
④ Abra el correo de verificación enviado a la dirección con la que se registró y complete la verificación de correo electrónico — omitir este paso puede bloquear gh auth login o la creación de repositorios más adelante.
⑤ Registrarse en el plan gratuito es suficiente — los ejercicios y la práctica de PR de este manual no requieren un plan de pago.
Una vez completado el registro, el GitHub CLI (gh) se instala junto como parte del script de configuración anterior, y el comando gh auth login a continuación conecta su terminal a esa cuenta. 
gh auth login
# Siga los prompts: elija GitHub.com → elija HTTPS → elija Iniciar sesión con un navegador web (recomendado)
# Cuando el navegador se abra, inicie sesión con la cuenta que acaba de crear y confirme el código de autenticación

Instalación en Windows

Dado que la notación de rutas de este manual está basada en Windows, los usuarios de Windows deben descargar setup-windows.ps1, colocarlo en una carpeta de práctica dedicada (por ejemplo, harness-lab/setup/), abrir PowerShell como administrador, y luego ejecutar el comando a continuación.

Cómo abrir PowerShell como administrador
① Abra el menú Inicio y busque PowerShell.
② Haga clic derecho en "Windows PowerShell" en los resultados de búsqueda.
③ Seleccione "Ejecutar como administrador" en el menú que aparece.
④ Cuando aparezca el aviso de Control de cuentas de usuario (UAC), haga clic en "Sí" para aprobar.
Si la barra de título muestra algo como Administrador: Windows PowerShell, lo ha abierto correctamente. Algunos pasos, como las instalaciones de winget, pueden generar errores o omitirse silenciosamente sin privilegios de administrador. 
cd ./setup
.\setup-windows.ps1
# Indicadores opcionales: -WSL2, -WezTerm, -Docker, -Force (reinstalar herramientas incluso si ya están instaladas)

Después de que el script termine, debe cerrar y volver a abrir completamente su terminal para que los cambios en PATH surtan efecto.

Instalación en macOS / Linux

En macOS, descargue y use setup-mac.sh; en Linux, use setup-linux.sh. Ambos admiten los indicadores opcionales --wezterm y --docker.

# macOS
cd ./setup && bash setup-mac.sh

# Linux
cd ./setup && bash setup-linux.sh

Verificación de la instalación

Independientemente de su sistema operativo, ejecutar setup-common.ts con bun imprime una tabla de verificación que muestra el estado de su instalación. Si cada elemento muestra ✅, está listo para continuar con los ejercicios a continuación.

cd ./setup && bun setup-common.ts

Entre las herramientas que este proyecto instala, las directamente relevantes para los ejercicios de cuatro herramientas de este capítulo son: Claude App (Escritorio), claude (CLI de Claude Code), Antigravity (Escritorio), agy (CLI de Antigravity), bun (necesario para ejecutar subagentes basados en .claude/agents/*.md), y gh (GitHub CLI), que también se utiliza en capítulos posteriores.

El CLI de Antigravity (agy) es un solo binario compilado que no requiere instalación de runtime separada — simplemente descomprímalo y colóquelo en el PATH, y estará listo para ejecutarse. Orientaciones anteriores que aún circulan, como "instalar Gemini CLI globalmente a través de npm", ya no son válidas. Consulte antigravity.google/docs/cli/getting-started para las instrucciones de instalación actuales.
Si tiene problemas durante la instalación, los registros se guardan en %USERPROFILE%\workshop-setup-logs\ en Windows. Verifique estos registros primero al solucionar problemas.
● Principiante Primeros pasos El primer paso: crear un subagente personalizado y observar cómo se invoca desde Claude App
G-1 Principiante Crear y llamar a tu primer subagente personalizado
Un desarrollador que prueba el arnés por primera vez crea una carpeta de práctica nueva y vacía llamada harness-lab/, primero escribe un rol reviewer como una especificación AGENTS.md neutral a la herramienta, y luego lo "implementa" como un subagente predefinido en Claude App (Escritorio) y lo invoca. Dado que esta carpeta está dedicada a la práctica, no se mezclará con otros archivos del proyecto.
Elementos utilizados
AGENTS.md (Cap.2) Definición de un subagente Invocación de un subagente
Paso a paso
  1. ① Crear y entrar en la carpeta de práctica

    Cree una nueva carpeta llamada harness-lab en su carpeta actual y muévase a ella. Todos los comandos a partir de aquí se ejecutan dentro de esta carpeta.

    mkdir -p harness-lab
cd harness-lab
  2. ② Escribir la especificación de rol común — AGENTS.md

    Escriba el rol reviewer como texto plano, libre de cualquier terminología específica de herramientas, para que se lea con el mismo significado ya sea en Claude, Antigravity o cualquier otra herramienta que admita el estándar AGENTS.md. Este único archivo se convierte en la única fuente de verdad de "qué hace este rol", y las dos herramientas a continuación simplemente implementan esa fuente, cada una a su manera. En macOS/Linux/Git Bash, ejecute el comando tal cual.

    cat > AGENTS.md << 'EOF'
## Agent: reviewer

Role: Review text files for typos, logical gaps, and areas for improvement.
Input: Path to the text file to review
Output: A list of typos, logical gaps, and improvement suggestions
Permissions: Read-only — does not modify the file directly.
EOF

    En Windows PowerShell, el comando cat en sí es un alias para Get-Content y puede usarse tal cual para leer archivos. Sin embargo, no admite la sintaxis heredoc (<< 'EOF') para ingresar múltiples líneas directamente, así que construya el mismo contenido como una cadena here-string entre comillas (@'...'@) y escríbalo en el archivo con Set-Content.

    @'
## Agent: reviewer

Role: Review text files for typos, logical gaps, and areas for improvement.
Input: Path to the text file to review
Output: A list of typos, logical gaps, and improvement suggestions
Permissions: Read-only — does not modify the file directly.
'@ | Set-Content AGENTS.md
Claude App (Escritorio) — Implementación de la especificación AGENTS.md como subagente predefinido

No cree el archivo de antemano en una terminal o editor separado. Simplemente siga los tres pasos a continuación — cada cuadro de código gris está pensado para copiarse tal cual con el botón "Copiar" y pegarse.

  1. ① Abrir el proyecto en Claude App

    Inicie Claude App (Escritorio) y abra la carpeta harness-lab/ que acaba de crear como un proyecto.

  2. ② Solicitar la creación del subagente — Pegue el texto a continuación en el cuadro de chat y envíelo 
    Siguiendo exactamente la especificación del rol reviewer escrita en AGENTS.md, crea un subagente reviewer en .claude/agents/reviewer.md. Permite solo las herramientas Read y Grep, y establece el modelo a sonnet.
    Claude App lee la especificación "rol/entrada/salida/permisos" en AGENTS.md y crea directamente .claude/agents/reviewer.md usando la herramienta Write, transfiriendo el contenido al frontmatter YAML (description, tools) y al prompt del sistema — la especificación permanece igual, solo se ha adaptado el formato a la herramienta. Una vez que termine la creación, compare el contenido del archivo mostrado en el chat con AGENTS.md.
  3. ③ Crear un archivo de destino y llamar al subagente — Continúe pegando en el mismo chat y envíe 
    Crea un archivo llamado notes.txt que contenga el texto "Este proyecto es muy bueno. Esto es muy bueno." Luego usa el subagente reviewer para revisar notes.txt.
    Claude App llama a la herramienta Agent (Task) con description="Revisar notes.txt" y subagent_type="reviewer". La pantalla muestra, en orden, el subagente siendo iniciado y, una vez terminado su trabajo, un resultado resumido devuelto a la sesión principal.

Lo mismo aplica en Claude Code (CLI) — ejecutar claude en una terminal y pegar las mismas oraciones de los pasos ②③ en el chat hace que la interfaz de línea de comandos (CLI) lea la especificación AGENTS.md de la misma manera y cree/invoque directamente .claude/agents/reviewer.md. La única diferencia en el CLI es que los ganchos de automatización como PostToolUse se activan adicionalmente (los ganchos no se activan en la App).

Verificación del resultado — Compruebe si harness-lab/.claude/agents/reviewer.md se creó realmente, y si sus campos description, tools y model coinciden con lo que solicitó. La respuesta final debería mostrar una lista dividida en erratas, lagunas lógicas y sugerencias de mejora — si el revisor responde con algo como "Lo corregí", la restricción de tools se aplicó incorrectamente.
Un error común — Si el subagente nunca se invoca y la sesión principal revisa notes.txt directamente en su lugar, generalmente significa que en el paso ② faltó la frase "con el subagente reviewer", o que el paso ③ se solicitó antes de que terminara la creación de .claude/agents/reviewer.md. Confirme que la creación del archivo terminó en la respuesta del paso ② antes de enviar el paso ③.
● Intermedio Flujo de trabajo diario Un patrón práctico donde la sesión principal actúa como orquestador dirigiendo a dos agentes especialistas — escritor y revisor — en secuencia
D-1 Intermedio Canalización de dos etapas escritor → revisor
Un practicante que ha terminado G-1 escribe un segundo rol, writer, en la misma carpeta harness-lab/, siguiendo el mismo enfoque que G-1: primero especificarlo en AGENTS.md, y luego implementarlo como un subagente predefinido en Claude App. Luego hace que dirija una canalización en la que escritor redacta primero y revisor critica el resultado, en orden estricto.
Elementos utilizados
AGENTS.md (Cap.2) Definición de un subagente Invocación de un subagente
Paso a paso
  1. Agregar a la especificación de rol común — Añadir una entrada de escritor a AGENTS.md

    Agregue el rol writer al mismo AGENTS.md creado en G-1. Deje la entrada de revisor tal cual y agregue solo el contenido a continuación. En macOS/Linux/Git Bash, ejecute el comando tal cual.

    cat >> AGENTS.md << 'EOF'

## Agent: writer

Role: Write a short 3-5 sentence draft on a given topic.
Input: Topic, path to save the file to
Output: Draft text file
Permissions: Write access — saves only to the specified file.
handoff_to: reviewer (review follows once the draft is done)
EOF

    En Windows PowerShell, agregue la cadena here-string con Add-Content (debe usar Add-Content en lugar de Set-Content, que sobrescribe el archivo y borraría la entrada de revisor).

    @'

## Agent: writer

Role: Write a short 3-5 sentence draft on a given topic.
Input: Topic, path to save the file to
Output: Draft text file
Permissions: Write access — saves only to the specified file.
handoff_to: reviewer (review follows once the draft is done)
'@ | Add-Content AGENTS.md
Claude App (Escritorio) — La sesión principal despacha llamadas de agente secuencialmente

Al igual que en G-1, no prepare ningún archivo de antemano. Continúe en el mismo chat de harness-lab/ que abrió para G-1.

  1. ① Solicitar la creación del subagente escritor — Pegue el texto a continuación en el cuadro de chat y envíelo 
    Siguiendo la especificación del rol writer escrita en AGENTS.md, crea un subagente writer en .claude/agents/writer.md. Permite las herramientas Write y Read, y establece el modelo a sonnet.
    Claude App lee la especificación de writer en AGENTS.md y crea directamente .claude/agents/writer.md usando la herramienta Write. Se sitúa junto al reviewer.md ya creado en G-1, dentro de la misma carpeta .claude/agents/ — la entrada handoff_to: reviewer en AGENTS.md se materializa en el siguiente paso.
  2. ② Solicitar la canalización secuencial escritor → revisor — Continúe pegando en el mismo chat y envíe 
    Haz que el subagente writer redacte un borrador en draft.txt sobre el tema 'Las ventajas del trabajo remoto', y una vez que termine, haz que el subagente reviewer revise draft.txt. Procede por las dos etapas en orden.
    La sesión principal primero llama a Agent con subagent_type="writer" para generar draft.txt, y solo después de que ese resultado regresa envía la llamada subagent_type="reviewer". Coordinar la dependencia entre los dos especialistas es trabajo de la sesión principal, no de los subagentes.
Llamar a escritor y revisor en paralelo (ambos en un mensaje) puede hacer que revisor intente revisar un draft.txt que aún no existe y falle — las tareas con dependencia siempre deben solicitarse como llamadas secuenciales (la clave está en declarar explícitamente "procede en orden", como en el paso ② anterior).
Verificación del resultado — El chat debería mostrar dos invocaciones de subagente en este orden: llamada writer → completado → llamada reviewer → completado. Si solo aparece una, el orquestador colapsó la canalización en un solo paso, así que verifique si su oración de solicitud decía explícitamente "en orden." Después de la finalización, también abra harness-lab/draft.txt para confirmar que el borrador se guardó realmente.

Lo mismo aplica en Claude Code (CLI) — usando el mismo writer.md/reviewer.md tal cual y pegando las oraciones de los pasos ①② en una terminal produce el mismo despacho secuencial.

D-2 Intermedio Observar cómo cambia la composición del equipo y el flujo de trabajo según la solicitud
Este escenario permite ver de primera mano la "composición dinámica del equipo" y la "combinación de diferentes flujos de trabajo" cubiertos en Cap.2 §4b. Deje los dos subagentes creados en D-1, writer y reviewer, exactamente como están, y simplemente varíe la naturaleza de la solicitud para observar a quién llama realmente el orquestador, cuántas veces y en qué orden — el punto clave es que nunca se define un nuevo subagente nuevamente.
Diagrama de ramificación de enrutamiento dinámico — Mismo equipo, diferentes solicitudes
Elementos utilizados
Composición dinámica del equipo y flujos de trabajo diversos
Claude App (Escritorio) — Mismo equipo, tres solicitudes diferentes

Continúe en el mismo chat donde terminó D-1. Preste mucha atención cada vez a qué subagente se llama, cuántas veces, según lo que se muestra en pantalla.

  1. ① Una solicitud simple — Un caso que solo necesita revisor 
    Solo revisa draft.txt en busca de erratas.
    El orquestador decide que writer no es necesario para esta solicitud y llama solo a reviewer. Incluso con el mismo equipo (escritor+revisor) definido, este es el ejemplo más simple que muestra que el orquestador decide quién se despliega realmente para cada solicitud sobre la marcha.
  2. ② Una solicitud compleja — Combinando escritor y revisor con dos perspectivas 
    Escribe un nuevo borrador en draft2.txt sobre el tema 'La semana laboral de cuatro días.' Una vez que termine el borrador, haz que se revise de forma independiente y simultáneamente desde una perspectiva gramatical y una perspectiva lógica.
    Esta vez, después de una llamada writer (la primera etapa de la canalización), reviewer se llama dos veces a la vez (expansión), cada una con instrucciones diferentes — "perspectiva gramatical" y "perspectiva lógica." Puede ver la canalización (escritor → revisor) y la expansión (revisor ×2 ejecutándose concurrentemente) combinadas dentro de una sola solicitud — los mismos dos subagentes produjeron un flujo de trabajo con una forma completamente diferente a la de ①.
Comparar ① y ② lado a lado deja claro que la "plantilla del equipo" (qué subagentes ha definido) y la "composición real desplegada para esta tarea" (quién es llamado cuántas veces, en qué orden) son dos capas diferentes. La primera se fija de antemano en .claude/agents/, pero la segunda se decide de nuevo con cada solicitud.

Lo mismo aplica en Claude Code (CLI) — usando el mismo writer.md/reviewer.md tal cual y pegando las oraciones de los pasos ①② en una terminal produce el mismo comportamiento.

Un error común — Si el revisor solo se llama una vez en ② aunque dijo "revisar simultáneamente", es probable que su oración de solicitud no distinguiera claramente las dos perspectivas, como "perspectiva gramatical y perspectiva lógica." Intente reformular con las perspectivas separadas más concretamente.

● Avanzado Usuario avanzado Ejecutar escritor y revisor concurrentemente contra dos archivos independientes — operación en paralelo con equipos de agentes de Claude Code
P-1 Avanzado Ejecución de tareas independientes en paralelo — Administrador de agentes vs. Equipos de agentes
Un practicante que ha terminado hasta D-1 intenta ejecutar dos tareas independientes sin dependencia entre ellas — redactar topic-a.txt y topic-b.txt — en paralelo usando equipos de agentes de Claude Code.
Elementos utilizados
Ejecución en paralelo — Escalar a un equipo Ejecución en paralelo
Claude App (Escritorio) — Equipos de agentes, teammateMode: in-process

Active la función experimental de equipos de agentes en la misma carpeta harness-lab/. En la aplicación de escritorio, teammateMode debe ser in-process (tmux no es compatible).

  1. ① Escribir el archivo de configuración (Terminal) — Cree un nuevo .claude/settings.json si no tiene uno, o combine estas dos claves si ya tiene uno

    En macOS/Linux/Git Bash, ejecute el comando tal cual.

    Este comando sobrescribe todo el archivo .claude/settings.json. Si el archivo ya contiene otras configuraciones, se perderá todo el contenido existente, así que haga una copia de seguridad antes o combine el contenido a continuación manualmente si necesita conservar algo. 
    cat > .claude/settings.json << 'EOF'
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  },
  "teammateMode": "in-process"
}
EOF

    En Windows PowerShell, cree el mismo archivo con una cadena here-string.

    @'
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  },
  "teammateMode": "in-process"
}
'@ | Set-Content .claude/settings.json
  2. ② Reiniciar Claude App

    Cierre completamente y vuelva a abrir Claude App para que la configuración surta efecto.

  3. ③ Solicitar el inicio de compañeros de equipo en paralelo — Pegue el texto a continuación en el cuadro de chat y envíelo 
    Inicia dos compañeros de equipo writer en paralelo — haz que uno redacte un borrador en topic-a.txt sobre 'trabajo remoto' y que el otro redacte un borrador en topic-b.txt sobre 'la semana laboral de cuatro días' al mismo tiempo. Una vez que cada archivo esté listo, haz que un compañero de equipo reviewer lo revise, y también muéstrame la lista de tareas compartida.
Con los equipos de agentes activados, múltiples instancias de Claude se ejecutan en paralelo como compañeros de equipo, con las tareas de cada compañero registradas y su estado actualizado en una lista de tareas compartida. Dado que los dos compañeros de equipo writer no tienen dependencia entre topic-a.txt y topic-b.txt, proceden al mismo tiempo, y los compañeros también pueden intercambiar mensajes directos a través de SendMessage. Tenga en cuenta, sin embargo, que algunas navegaciones por teclado (como Shift+Abajo) están limitadas en la aplicación de escritorio.
Para evitar que las listas de tareas se enreden, es más seguro asignar archivos o directorios completamente separados a los compañeros de equipo que inicie en paralelo desde el principio.
Un error común — Si no puede encontrar la función de equipos de agentes o los compañeros nunca se inician, generalmente se debe a una de dos cosas: ① si .claude/settings.json se guardó en relación con la carpeta harness-lab/ (guardarlo en otro lugar significa que no se reconocerá), o ② si Claude App se reinició completamente en el paso ②. Un error de sintaxis JSON (como una coma faltante) que hace que el archivo de configuración se ignore silenciosamente también es común, así que ábralo en un editor y verifique la sintaxis.
Antes/después de la configuración de permisos — El principio de privilegio mínimo

Lo mismo aplica en Claude Code (CLI) — la misma configuración y la misma oración de solicitud funcionan idénticamente. La única diferencia con la aplicación de escritorio es que el CLI adicionalmente permite elegir teammateMode: "tmux", permitiéndole ver la pantalla de cada compañero de equipo lado a lado en paneles divididos de tmux.

Llame al mismo subagente revisor tres veces, cambiando solo el modelo, y compare la velocidad de respuesta y la calidad del resultado con sus propios ojos.

Claude App (Escritorio) — Mismo archivo, solicitudes de revisión con tres modelos diferentes

Prepare un texto un poco más complejo que el notes.txt de G-1 que contenga un defecto lógico. Pegue el texto a continuación en el cuadro de chat tal cual.

  1. ① Preparar el archivo de destino 
    Crea un archivo llamado argument.txt y escribe lo siguiente en él: "El trabajo remoto siempre es más productivo que el trabajo en oficina. Esto se debe a que las personas que trabajan a distancia dicen que el trabajo remoto es bueno. Por lo tanto, toda empresa debería cambiar completamente al trabajo remoto."
  2. ② Revisar con el nivel haiku

    Pegue el texto a continuación en el cuadro de chat tal cual. Claude App cambia el campo model en reviewer.md a haiku, y luego realiza la revisión.

    Cambia el campo model en .claude/agents/reviewer.md a haiku. Luego usa el subagente reviewer para revisar argument.txt.
  3. ③ Repetir la misma solicitud con el nivel sonnet

    De la misma manera, cambie model a sonnet y revise de nuevo. Compare con el resultado de haiku para ver si identifica con precisión defectos lógicos como el razonamiento circular.

    Cambia el campo model en .claude/agents/reviewer.md a sonnet. Luego usa el subagente reviewer para revisar argument.txt.
  4. ④ Repetir la misma solicitud con el nivel opus

    De la misma manera, cambie model a opus y revise de nuevo. Observe cómo el tiempo de respuesta y la profundidad de análisis difieren de ②③.

    Cambia el campo model en .claude/agents/reviewer.md a opus. Luego usa el subagente reviewer para revisar argument.txt.
Para una simple verificación de erratas, los resultados de los tres modelos apenas difieren, pero para una tarea como esta — donde necesita identificar un defecto en la estructura de un argumento — cuanto más bajo el nivel, más pronunciada es la tendencia a perder el razonamiento circular como tal y en su lugar marcar solo problemas superficiales de redacción. Por el contrario, haiku responde más rápido de los tres. Experimentar de primera mano el equilibrio entre velocidad y profundidad hace que quede mucho más claro por qué existe en primer lugar el principio explicado en el Capítulo 5: "cuanto más pesado el juicio que requiere un rol, más alto el nivel; cuanto más rutinaria la tarea, más bajo el nivel."
Simplemente pida a Claude App que "cambie el campo model" cada vez — no hay necesidad de abrir el archivo de definición usted mismo; Claude App lo edita y realiza la revisión por su cuenta.
Un error común — Si el campo model contiene un valor que no existe (un error tipográfico, mayúsculas incorrectas, etc.), la llamada puede fallar o regresar silenciosamente a un modelo predeterminado. Después de terminar ②③④, abra .claude/agents/reviewer.md directamente y confirme que el valor model: coincide exactamente con el haiku/sonnet/opus previsto.
Ver también: Cap.5 §plantillas y variantes — Niveles de modelos

Conclusión de la sesión de práctica

Una vez que haya terminado los cinco escenarios, decida qué hacer con la carpeta harness-lab/. Dado que el siguiente capítulo (Cap.5) usa una nueva carpeta de práctica, no es necesario conservarla, pero si desea comparar el AGENTS.md y las definiciones de subagentes que ha construido hasta ahora, vale la pena revisarlas una vez antes de eliminarlas.

🧹 Limpieza de la carpeta harness-lab

Si ya no la necesita, elimine toda la carpeta. En macOS/Linux/Git Bash, ejecute el comando tal cual.

cd ..
rm -rf harness-lab

En Windows PowerShell

cd ..
Remove-Item -Recurse -Force harness-lab
Si desea conservarla — En lugar de eliminar la carpeta, puede dejar un commit local como registro con git init && git add -A && git commit -m "registro de práctica de harness-lab". Consérvela como referencia posteriormente, y comience los ejercicios del siguiente capítulo en una carpeta nueva separada.
El indicador CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS activado en .claude/settings.json en P-1 se aplica solo a la carpeta harness-lab/, por lo que desaparece junto con la carpeta si la elimina. Si desea seguir usando equipos de agentes en otros proyectos, necesitará agregar la misma configuración por separado al .claude/settings.json de ese proyecto.
