L3 프로젝트 업그레이드

L3 프로젝트를 만든 뒤 상위 표준(L0/L1)이 바뀌면 무슨 일이 일어날까 — 정답은 "아무 일도 안 일어난다"이다. 10장 §1에서 다룬 포크 모델 때문에, 이미 태어난 L3 프로젝트에 새 변경을 실제로 반영하려면 upgrade-project.ts를 사람이 명시적으로 실행해야 한다. 이 장은 그 절차를 다룬다.

소스: ai-workspace-standards/scripts/upgrade-project.ts(v1.10.1 기준) · 관련: 10장 §1 배포와 SSOT

이 장에서 다루는 것
  • 포크 모델에서 "업그레이드"가 왜 자동이 아니라 명령을 실행해야 하는 작업인지
  • upgrade-project.ts의 기본 사용법과 --dry-run 우선 원칙
  • LOCKED·MERGE·DOCS_MERGE·VARIANT_DOCS_SYNC·COMMANDS_SYNC·SYNC_IF_NEWER·PRESERVE·PRUNE와 TEMPLATE TREE SYNC·ENV_SAMPLE SYNC 등 주요 파일 처리 방식
  • 외부 의존성 매커니즘(2026-11): external-deps.json 매니페스트, 스캐폴드 패치, 호환성 게이트를 통과해야만 핀을 옮기는 EXTERNAL DEPS 패스, 벤더링 가드
  • 자동 git stash 스냅샷과 --rollback으로 되돌리는 안전장치
  • 13장에서 다루는 "승격"과 방향이 정반대라는 점

왜 필요한가 — 포크 모델의 이면

10장 §1에서 확인했듯, L1은 new-project.ts로 프로젝트를 스캐폴딩하는 시점에 딱 한 번만 내용을 전달한다. 그 이후 L3는 완전히 독립적으로 진화하며, L1이 아무리 바뀌어도 이미 만들어진 L3에는 아무것도 자동으로 반영되지 않는다.

문제는 시간이 지날수록 L1 쪽에서 훅 스크립트가 고쳐지고, 새 스킬이 추가되고, 보안 설정이 강화된다는 점이다. 이런 변경을 개별 L3 프로젝트에 반영하고 싶을 때 파일을 하나하나 손으로 대조하는 건 현실적이지 않다. upgrade-project.ts는 이 반영 작업을 자동화하되, 포크 모델의 핵심 원칙 — "L3가 의도적으로 다르게 고친 부분은 함부로 덮어쓰지 않는다" — 은 그대로 지킨다.

upgrade-project.ts 사용법

가장 먼저 --dry-run으로 무엇이 바뀔지 미리 확인한다. 실제로 파일을 건드리지 않고 콘솔에 계획만 출력한다.

bun scripts/upgrade-project.ts <project-path> --dry-run

출력 내용에 문제가 없으면 --dry-run을 빼고 다시 실행한다.

bun scripts/upgrade-project.ts <project-path>
# 선택 플래그: --variant <variant>  --platform all|claude|antigravity|codex|hermes (comma list ok)
#            --prune-removed  --rollback

--platform은 ADR-0100(2026-10-10)을 따른다. all(기본값), 프로필 하나(claude, antigravity, codex, hermes), 또는 claude,codex 같은 쉼표 목록을 받으며, 선택한 프로필의 파일 합집합을 유지하고 나머지는 제거한다. 알아둘 주요 변경: codex 하나만으로는 CLAUDE.md/GEMINI.md를 더 이상 유지하지 않으므로, 그렇게 하려면 codex,claude,antigravity를 전달한다(구 both는 경고와 함께 all 취급).

--variant는 프로젝트의 .claude/template-version.txt에 기록된 값을 자동으로 읽어오므로 대부분 생략해도 된다. 이 파일이 없는 오래된 프로젝트라면 실행 시 확인 프롬프트가 뜨고, --variant를 직접 지정해야 한다.

Codex 표면도 CODEX.md MERGE와 .codex/config.toml add-if-missing 대상으로 포함되며, 저장소 맥락 표면도 같은 업그레이드 엔진으로 전달된다. 업데이트(2026-11): 이 표면의 도구 이름이 바뀌었습니다 — graft 0.28이 trail이 되었습니다(ADR-0076) — 그리고 업그레이드 패스에 trail 마이그레이션 관용 규칙 둘이 추가되었습니다: JSON_MERGE는 프로젝트에 존재하지 않는 저장소 상대 헬퍼 경로를 참조하는 템플릿 훅 항목을 버리고(trail init으로 재작성된 트리에 graft 시절 훅 항목이 다시 병합되지 않음), trail init으로 이미 마이그레이션된 프로젝트(.trail/ 마커 보유)는 은퇴한 graft 시절 시드를 건너뛰습니다(SEED_SKIP (retired-surface)) — 예를 들어 사라진 .mcp.json은 다시 시딩되지 않습니다.
2026-10에는 같은 엔진에 두 가지가 더해졌다. ADR-0101은 CLAUDE.md/GEMINI.md의 번호 매겨진 스켈레톤 섹션(마커 영역 밖의 내용)을 관리 대상 전달 표면으로 만든다. lib/platform-skeleton-merge.ts가 없는 표준 섹션은 템플릿 기준 앵커에 삽입하고, 어긋난 본문은 프로젝트 고유 내용이 없을 때만 교체한다(가드 적용, 교체 전에 <file>.pre-skeleton.bak 스냅샷 작성) — 2026-09-12에 관찰된 "업그레이드가 제목을 삼키는" 결함 계열을 닫은 것이다. 그리고 새로운 옵트인 플래그 --changelog-entry는 프로젝트 CHANGELOG의 [Unreleased] 섹션 맨 위에 편집 가능한 chore(upgrade): template sync 불릿을 만들어 준다(템플릿 버전별 멱등, --dry-run에서는 거부).

v1.10.x부터 업그레이드는 국가 프로필(국가 스코프 자산)도 인식한다. 실행 전 프로젝트의 .claude/template-version.txt에서 country= 줄을 읽어(없으면 docs/countries/ACTIVE.md의 관할 표기로 대체) 대상 국가를 파악하고, 마무리 시 이 줄을 그대로 보존한다 — 구버전은 이 파일을 재작성하면서 country= 줄을 지워버려 국가 소속 정보를 잃게 했다. 또한 스킬 동기화가 모두 끝난 뒤 레지스트리 기반 prune가 한 번 더 실행되어, 국가 스코프 스킬(k-dart/k-law/k-kosis)이 해당 국가가 아닌 프로젝트에 다시 주입됐다면 삭제한다 — 스캐폴딩 시점의 정리 결과를 매번 업그레이드가 되돌리는 사태를 막기 위함이다. 단, 로컬에서 의도적으로 고친 포크는 ⚠️ CONFLICT 경고와 함께 그대로 보존된다.

SYNC_IF_NEWER 대상 파일을 로컬에서 직접 고쳐 쓴 상태인데 템플릿 쪽 버전이 더 높으면, 스크립트는 ⚠️ CONFLICT로 표시하면서도 결국 템플릿 내용으로 덮어쓴다. "덮어쓰기 전에 물어봐 주는" 동작이 아니라 "경고만 하고 진행하는" 동작이라는 점을 기억해야 한다 — 그래서 아래 안전장치가 중요하다.

외부 의존성 (2026-11)

같은 엔진을 타는 표면이 하나 더 있다. 프로젝트는 루트의 external-deps.json 매니페스트에 핀으로 고정된 외부 git 의존성을 선언할 수 있고, 배포 규칙은 정해졌다. 외부 저장소를 템플릿 트리 안에 벤더링하지 않는다. 외부 코드는 스캐폴딩 시점에 GitHub에서 릴리스 태그를 핀으로 고정해 클론하고, gitignore된 프로젝트 로컬 디렉터리에 둔다. 업그레이드는 의존성의 호환성 테스트가 통과할 때만 핀을 옮긴다. 첫 소비자는 co-work 덱 파이프라인의 변환 엔진인 ppt-master v6.8.0이며, 어댑터 뒤에서 있는 그대로 소비한다.

새 소식(2026-11): 외부 의존성 매커니즘이 도착했다 — 스키마 버전이 매겨진 external-deps.json 매니페스트 규약(L1에서는 빈 배열 시드, variant마다 확장), new-project.ts §7.9의 스캐폴드 시점 패치와 옵트인 하드 실패 플래그 --strict-external-deps, upgrade-project.ts의 호환성 게이트가 걸린 EXTERNAL DEPS 패스와 --external-deps-only 플래그, 그리고 install_dir 내용이 템플릿 트리 안에 들어오면 템플릿 검증을 실패시키는 벤더링 가드.

매니페스트 항목 하나하나는 아래 필드를 기록한다. pin이 계약이고, 자문용 commit 필드는 드리프트 트립와이어로만 쓰인다.

필드의미
id매니페스트 안에서 유일한 안정 식별자 — variant 시드가 공통 시드를 확장할 때의 병합 키이기도 하다
repohttps GitHub URL, 자격 증명 없음
pin릴리스 태그 — 우리가 실행하는 버전. 업그레이드 패스가 이 태그를 upstream 태그들과 비교한다
commit해석된 sha, 패치/갱신 시점에 기록 — 자문용 드리프트 트립와이어일 뿐
install{pin}/{repo}/{dir} 플레이스홀더를 넣는 클론 명령 템플릿(태그 기준 depth 1)
install_dir프로젝트 상대 클론 대상 — gitignore 필수. 외부 클론은 절대 커밋하지 않는다
consumer소비 파이프라인 이름을 적는 자유 텍스트(자문용)
compatibility_test프로젝트 루트에서 실행하는 명령, exit 0 = 통과 — 핀을 옮길 때마다 통과해야 하는 관문
propagation열거형, 현재는 never가 유일한 값 — 외부 콘텐츠는 템플릿 경계를 절대 넘지 않는다

스캐폴드 패치(§7.9). 프로젝트 구체화가 끝나면 new-project.ts가 매니페스트 항목마다 install_dir에 설치하고 그에 맞는 .gitignore 줄을 덧붙인다. 자세는 WARN이지 실패가 아니다 — 네트워크에 의존하는 스캐폴딩이 사용자를 프로젝트 없이 남겨두면 안 되기 때문이다. 패치가 실패해도 프로젝트는 여전히 스캐폴딩되고, 실행 출력에 WARN 행이 남으며, 문서화된 재시도 경로는 bun scripts/upgrade-project.ts <project-path> --external-deps-only(같은 갱신 패스의 패치 전용 형태)다. 의존성 없이는 진행하면 안 되는 CI·프로비저닝 맥락에서는 --strict-external-deps가 이 자세를 하드 실패로 바꾼다.

EXTERNAL DEPS 업그레이드 패스. 이 패스는 TEMPLATE TREE SYNC 다음에 의존성별로 실행된다. git ls-remote --tags로 최신 릴리스 태그를 확인하고(pin보다 새롭지 않은 태그는 "current"로 짧게 끝난다), 더 새로운 태그가 있으면 프로젝트 루트에서 compatibility_test를 돌린다 — 통과하면 핀을 옮기고(매니페스트의 pin/commit 갱신, 클론을 새 태그로 다시 패치), 실패하면 현재 핀을 그대로 두고 WARN 행만 남긴다. 의존성마다 통합 결정 로그 규약에 따라 결정 로그 행이 하나씩 생기고, --dry-run은 아무것도 건드리지 않고 예정된 동작만 보고하며, --external-deps-only는 이 패스만 실행한다. 기존 프로젝트는 다음 업그레이드에서 같은 패스를 통해 템플릿 시드를 받는다 — 비어 있는 L1 매니페스트와 ppt-master 같은 variant 항목이 손으로 쓴 마이그레이션 없이 도착한다.

벤더링 가드. 세 가지 규칙이 외부 코드를 통제된 트리 밖에 묶어 둔다. 템플릿 트리 안의 어떤 경로가 매니페스트 install_dir과 일치하면 템플릿 검증이 실패한다(템플릿에 실수로 커밋된 external/ppt-master/를 잡는 가장 빠른 방법). 프로젝트→템플릿 전파와 템플릿→프로젝트 트리 동기화는 양방향 모두 이 경로를 건너뛴다. 그리고 install_dir의 gitignore 커버리지는 스캐폴드 시점에 자동으로 덧붙고 업그레이드 시점에 검증된다. 커밋된 외부 클론은 배포 모델 전체를 무너뜨린다 — upstream은 우리 포크를 하나의 diff로 보게 된다.

ppt-master 항목이 이 모양을 끝까지 보여준다. repo https://github.com/hugohe3/ppt-master(MIT), pin v6.8.0, 덱 파이프라인 어댑터 뒤의 external/ppt-master에 클론, 그리고 compatibility_test로서의 계약 테스트. ppt-master가 v6.9.0을 내놓으면 업그레이드 패스는 먼저 계약 테스트를 돌린다 — 통과할 때만 핀이 움직이고, 그렇지 않으면 보고 행과 함께 핀을 유지한다.

안전장치 — 스냅샷과 롤백

실행 전(--dry-run이 아닐 때) 스크립트는 자동으로 git stash push -m pre-upgrade-snapshot-YYYYMMDD를 실행해 현재 작업 트리 상태를 스냅샷으로 남긴다. 업그레이드 결과가 마음에 들지 않으면 다음 명령으로 즉시 되돌릴 수 있다.

bun scripts/upgrade-project.ts <project-path> --rollback

이 명령은 방금 만든 pre-upgrade-snapshot-* 스태시를 찾아 git stash pop으로 복원한다. 업그레이드 자체는 커밋을 만들지 않으므로, 결과를 확인한 뒤에는 평소처럼 git diff로 변경 내용을 검토하고 직접 커밋해야 한다.

마무리 단계로 .claude/template-version.txt가 새 버전으로 갱신되며 이때 country= 줄은 그대로 보존되고, .gitleaks.toml·pre-commit 훅·.gitattributes(eol=lf)·.gitignore(.env 패턴)·git core.hooksPath 같은 보안 부트스트랩 항목이 자동으로 점검된다(3장 가드레일 원칙과 동일한 항목들이다). core.hooksPath가 잘못돼 있으면 스크립트가 스스로 고쳐준다.

승격과의 방향 차이

13장에서 다루는 "승격"과 이번 장의 "업그레이드"는 이름이 비슷해 보이지만 방향이 정반대다.

  • 승격(l3-to-variant-pipeline.ts, 13장) — L3 → L2. 내가 만든 프로젝트의 변경을 공식 variant 템플릿으로 끌어올려, 다른 사람도 쓸 수 있는 베리언트(variant)로 만드는 작업.
  • 업그레이드(upgrade-project.ts, 이 장) — L1 → L3. 공식 템플릿의 최신 변경을 이미 만들어진 내 프로젝트에 끌어오는 작업.

두 스크립트는 서로 반대 방향으로 파일을 흘려보낼 뿐, 어느 한쪽이 다른 쪽을 대체하지 않는다. 템플릿에 기여하고 싶다면 승격을, 이미 만든 프로젝트를 최신 상태로 유지하고 싶다면 업그레이드를 쓴다.

이 장의 스크립트 동작(플래그, 파일 분류, 안전장치)은 ai-workspace-standards 저장소의 scripts/upgrade-project.ts(v1.10.1) 소스를 직접 확인해 작성했다. 이 핸드북 저장소에는 해당 스크립트가 포함돼 있지 않으므로, 실제 실행 결과는 반드시 최신 소스와 대조해 확인한다.
